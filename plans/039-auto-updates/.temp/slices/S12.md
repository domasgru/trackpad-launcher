# S12: The docs match what shipped

## Goal

Every document says what the code now does. `docs/architecture.md` and `docs/domain-model.md` were rewritten with the plan, so read them against the shipped code and correct any drift. `docs/product-overview.md`, `README.md` and `Scripts/release.sh`'s header still describe the update card, and this slice rewrites them. This brief covers only the documents. The rest of the plan's last slice needs a person (the update key, the performance baseline, the by-hand checks), and the orchestrator reports those as open.

## Requirements

The privacy rule, verbatim from the plan: "Trackpad Launcher makes no network calls but one kind: a copy signed with a Developer ID in /Applications that can write to its own bundle checks a public update list on GitHub at each start and every 24 hours, and downloads a new version from GitHub releases; no logging."

R15: "The settings window MUST show no update card, no update setting and no update status."

## Design

### Recorded as reversed

| Standing text | Where | Becomes |
|---|---|---|
| "The user decides when", "never in the background" | `README.md:17-18, 34, 69-72`, `docs/product-overview.md:8`, `Scripts/release.sh` header | Automatic: it checks at each start and every 24 hours, downloads in the background, installs when the app is not in use, and restarts silently, with nothing to press. |

Specifically:

- `README.md:17-18`: updates come on their own, with nothing to press and nothing shown.
- `README.md:34`: a development build never checks for updates, and never shows the move dialog. Keep it true.
- `README.md:39` and the release section: a release also adds an item to `appcast.xml`. Name `--feed-only` as the way to finish a release whose feed push failed. Say the update key's private half lives in the login keychain and must be backed up with `generate_keys -x`, because it cannot rotate.
- `README.md:71-72`: replace with how automatic updates work, in the README's plain voice: what a copy needs (Developer ID, /Applications, can write to its own bundle), and that drafts and pre-releases never appear because only the release command writes the feed.
- `docs/product-overview.md:8`: the privacy rule above, verbatim.
- `Scripts/release.sh` header: add the feed, the update key, the build-number rule (Sparkle compares `CFBundleVersion`), `card-contract`, the order "publish, then feed", and `--feed-only <version>`. It currently says every older copy offers the release "the next time its settings window opens": keep that for older copies, and add that automatic copies learn of it from the feed.

### Writing

These are plain, present-tense documents: what is, not what changed. Follow `dev-workflow:writing-for-agents` for the two `docs/` files. No history of the card in the README. Never mention plans, slices or requirement numbers in the README, `product-overview.md` or the script header.

## Rules that apply

- `docs/architecture.md` opening: "The decisions that hold across the whole codebase. Feature-level decisions live in their plan under `plans/` and then in the code."
- `docs/domain-model.md` opening: "Use these words, with these meanings, everywhere: docs, plans, code, UI." So: *update check*, *automatic update*, *hand-over*, *newer version*.
- Change no Swift, no test, no `project.yml`. `Scripts/release.sh` changes only in its header comment.
- Do not touch `docs/performance.md`: its new baseline needs a person's measurement session. Do not launch the app, build it, or run `Scripts/perf`: a Trackpad Launcher opened by hand stops the copy the user is running.
- Do not commit: the orchestrator commits your work.
- Worktree guard: write each Bash command with literal arguments, no shell variables, `$(…)` or loops; create and edit files with Write and Edit; absolute paths.
