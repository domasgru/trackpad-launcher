# Plan: A new copy survives stopping the copy before it

## Problem statement

After an in-app update, the new version often crashes within a second of starting, and nothing is left running: the old version has already ended, so gestures are gone until the user opens the app by hand. The same crash hits any opening of a copy while another runs, such as `make run` beside the installed app.

**How an update reaches it.** `Lifecycle.replaced()` ends the old copy only after macOS reports the new one started, so the new copy usually finds the old one alive. Its `.runWithWindow` route calls `SystemRunningCopies.stop`.

**Root cause.** `SystemRunningCopies.stop` keeps the `NSKeyValueObservation`s in `watches` but holds the observed `NSRunningApplication`s only in the local `apps`. `NSKeyValueObservation` does not retain the object it observes. `stop` runs inside the open Apple Event's handler (`applicationDidFinishLaunching`), so when that event's autorelease pool drains, an `NSRunningApplication` can deallocate with its observers still registered. The Swift helper then calls `removeObserver` on the object mid-dealloc. `LaunchWatch` already avoids this by keeping `process` beside its observations.

**Evidence.**

- Eight local crash reports from 1.0.0 to 1.0.10 share this stack: the main thread, within about a second of launch, `NSKVODeallocate` in the Apple Event handler's autorelease pool drain. It ends either in `-[NSRunningApplication removeObserver:forKeyPath:]` (SIGSEGV) or in a rethrown exception (SIGABRT). One is a release build in /Applications, the rest are mostly development builds.
- `repro.sh` against a Release build of the real app under its own bundle identifier: with the old copy alive at the new copy's `stop`, the new copy died in 15 of 15 rounds, all 15 reports with this stack (11 SIGSEGV, 4 SIGABRT).
- With the old copy ended right after opening the new one, 0 of 12 rounds crashed, and a copy opened alone survives. The crash depends on the old copy still running when the new one looks, which is why updates crash often rather than always.

**Test coverage.** No test should have caught it as things stand: `InMemoryRunningCopies` replaces the adapter in every `Lifecycle` test, and `RunningCopiesFamilyTests` and `RunningCopiesOrderTests` cover only the pure rules and `others()`. Nothing runs the real `stop`.

## Requirements

### R1. Every observed process outlives its observation
`SystemRunningCopies` MUST keep each `NSRunningApplication` it observes alive until that application's observation has been invalidated, on every path, including when the last copy exits. Invalidating MUST come before releasing the application.

#### Scenario: The update hand-over
- **GIVEN** a copy of the app is running
- **WHEN** a new copy starts as a new instance and stops the running copy
- **THEN** the running copy exits, and the new copy stays running with its resident built
- **AND** `repro.sh <app> 15 stopped` reports 15 new copies alive and 0 dead, and no new crash report appears

### R2. `stop`'s contract is unchanged
`RunningCopies.stop` MUST keep its documented behaviour: it stops each listed copy at once and calls `exited` once, on the main actor, when every listed copy has exited, synchronously when none still runs. Observable behaviour other than the crash MUST not change.

### R3. A test runs the real `stop` against a real process
A test in `LauncherPlatformTests` MUST start a real throwaway app process and stop it through `SystemRunningCopies`, with an autorelease pool draining around the `stop` call as the Apple Event's does. It MUST crash or fail against today's code and pass with the fix. It MUST NOT touch any process outside its own fixture: its identifier family MUST be the fixture's alone.

## Non-goals

- **Relaunching the app after an update, or a watchdog that restarts a crashed copy.** The crash has one known cause and this removes it. A restart mechanism would add a new moving part that hides failures rather than preventing them, and this is the user's alternative idea only if the cause could not be found.
- **Changing the hand-over order in `Lifecycle` or `ApplicationsUpdater`.** Ending the old copy only once the new one has started is deliberate: a copy that waited to be stopped would never end if the new one failed to start, and gestures keep working until the swap.
- **`GitHubReleases.ByteWatcher`.** It also observes without retaining, but the failure here is specific to `NSRunningApplication`'s `removeObserver` override, downloads have shipped without a matching report, and the task outlives the watcher's use. No evidence of a defect.
- **A fix for versions already released.** The crash is in the code of the copy that starts, so the first update to a version with this fix is already protected. Nothing needs backporting.

## Implementation Decisions

- **The fix is confined to the real adapter's implementation; its interface does not move.** `SystemRunningCopies` keeps `init(bundleIdentifier:)`, `others()`, `stop(_:then:)` and `endThisCopy()` exactly as they are, and so do the `RunningCopies` port, `Lifecycle`, `InMemoryRunningCopies`, the exit counter, `family(of:)` and `started(_:before:)`. The crash is a lifetime error inside `stop`; the port's contract (R2) is already right, and nothing above the adapter changes.

- **A stop under way holds each copy's application beside its observation, in a watch that invalidates before it lets go.** In place of the array of bare `NSKeyValueObservation`s, the adapter keeps one watch per listed copy still running. A watch is a small private main-actor class that owns the `NSRunningApplication` and the observation of its `isTerminated`; its `invalidate()` invalidates the observation (Foundation's `invalidate()` is itself idempotent, so the watch keeps no flag); its deinit calls `invalidate()`. A class, not a struct, deliberately: a class's deinit body runs while its stored properties are still alive, so the observation is invalidated while the watch still retains the application, whichever path releases the watch (completion, a later `stop` replacing the set, the adapter's own deinit). A struct gives no say in which member goes first, and application-first recreates the crash on the completion path: the prototype's application-first struct aborted inside completion, under `swift_arrayDestroy`, with the reports' stack. Completion invalidates every watch explicitly and then drops the set, before calling `exited`, in the manner of `LaunchWatch.stop`: that is the mechanism the next reader sees, and the deinit is the guarantee behind it, the only one on the path a later `stop` takes. One copy cannot tell these shapes apart, two can: the main-queue block that completes the stop captures the application whose exit it reports, so on a one-copy list that application outlives completion whatever the watch does, while the first copy of two is, by then, held by its watch alone. The shape, from the prototype that reproduced the crash with the old shape and ended cleanly with this one:

  ```swift
  @MainActor private final class Watch {
      let app: NSRunningApplication           // retained: an observation does not retain its object
      let observation: NSKeyValueObservation
      func invalidate() { observation.invalidate() }
      isolated deinit { invalidate() }        // runs before `app` is released, whichever path drops the watch
  }
  ```

- **Everything else in `stop` is as today.** The listed copies are resolved to applications by pid and those already terminated are dropped; with none left, `exited` runs synchronously; each remaining application is force-terminated and then observed with `.initial` and `.new`; each exit counts once per pid; the handler hops to the main actor through the main queue, where completion runs outside any KVO dispatch; a second `stop` while one is under way replaces the set, as today, and the replaced watches are now released safely. The adapter stays the only file that force-terminates (the source-scan confinement).

- **The test fixture gains a runnable pair: a release copy and a Debug copy.** `BundleFixture`'s existing bundles exist to be copied, archived and verified: their executable is a text file and every item carries the quarantine attribute, so LaunchServices would never run them. The fixture gains a second kind of bundle that macOS does launch: its executable is a shell script, mode 755, that loops over `sleep 1` for about two minutes and then ends, so a test that dies before stopping it leaves nothing behind for longer than that, and so its own argv names the bundle (no `exec`: the process LaunchServices knows is the shell, and `pgrep -f` on the bundle's executable path finds it, an independent read of the process table); nothing in it is quarantined; `LSBackgroundOnly` is set so it never shows in the Dock or takes focus. The test makes two such bundles at different paths: the release copy's identifier is the fixture's identifier with a suffix unique to this test, and the Debug copy's is that with `.debug` appended, the one family `family(of:)` derives, as the installed release and a Debug build are. An adapter built on the release identifier therefore lists exactly that pair and nothing else, whatever else runs on the Mac, the same test in another worktree's session at the same moment included; and the family is the fixture's alone, never `com.domasgru.TrackpadLauncherApp` or its `.debug` twin, since an adapter built on either would force-terminate the user's installed app and any session's Debug copy. Two minutes is deliberately longer than the test's 30 s bound on `exited`, so a copy ending of its own accord can never stand in for the stop.

- **The test launches each copy with `/usr/bin/open -g`, one `open` process per copy, not with `NSWorkspace.openApplication`.** Both are LaunchServices launches, so each process gets the registration `others()` reads (`runningApplications(withBundleIdentifier:)`), and `open -g -n` is how `repro.sh` gets its two copies up. `openApplication` was measured and rejected: its completion for an app that never checks in with LaunchServices, which a script app never does, arrives only after LaunchServices' 30 s launch timeout (30.04 s and 30.10 s measured, with the process already listed after 0.06 s), and a second launch request from the same client waits behind that completion, whether of the same bundle, of another bundle with the same identifier or of its `.debug` twin. `open` returns in about 50 ms, each `open` is its own client, and both copies are listed within a second. The test waits, bounded, for `others()` to list two copies, polling it briefly as the fixture's existing `bundles(identifiedBy:within:)` polls, and takes the pids themselves from the process table through `pgrep -f` on the two bundles' executable paths. It keeps the pids and sends each `SIGKILL` on teardown if it is still alive, so a failing test never leaves a process; a `sleep 1` child of a killed shell lasts at most a second longer.

- **The autorelease pool drain is the test's own, around the `stop` call.** The crash needs the applications' last autoreleased references to go while the observations are live; in the app the Apple Event handler's pool does that at the end of `applicationDidFinishLaunching`. The test reproduces exactly that: `stop` is called inside an explicit `autoreleasepool` block, whose end drains synchronously before anything is awaited. The prototype showed this drain kills an unfixed process at once with the crash reports' stack (`NSKVODeallocate` → `-[NSRunningApplication removeObserver:forKeyPath:]` → `NSInvalidArgumentException`) and leaves a fixed one alive.

- **The test awaits the exit on the main actor without blocking the thread.** macOS pushes `isTerminated` through the main run loop: the prototype got no push while its main thread was blocked, and the push at once when the run loop ran. The test is main-actor (the adapter is) and awaits `exited` through the suite's existing bounded-await helper, at its default 30 s, never through a semaphore or `waitUntilExit`; the helper only suspends, and it is the harness that keeps the main run loop turning, which was verified under `swift test` in a throwaway package: a main-actor test runs on the main thread, a run-loop timer fires while it awaits, and the exit push for a script app LaunchServices launched arrived on the main thread. `exited` itself records how many times it ran and whether it ran on the main thread; the helper wakes the test once and would hide a second call. The independent truth that the processes are gone is `kill(pid, 0)` failing with `ESRCH`, not AppKit's view of it, re-read for up to 2 s because launchd, not the test, reaps them and `kill` still succeeds on a zombie; the prototype saw `ESRCH` at once.

- **No docs change.** The glossary already says an update "stops the old one" and the architecture already lists "the termination of other running copies" among the pushes; neither the domain nor a core decision moves. The rule this fix follows, keep an observed AppKit object alive beside its observation and invalidate before releasing it, is a coding rule that both observers of `NSRunningApplication` now embody; it lives in the adapter's doc comments and here.

## Testing Decisions

### Strategy

One seam, existing: the public surface of `SystemRunningCopies` built on the fixture's identifier through `init(bundleIdentifier:)`, as `LauncherKit/Tests/LauncherPlatformTests/RunningCopiesFamilyTests.swift` builds it on Finder's. `others()` and `stop(_:then:)` run for real against two real processes macOS launched, a release copy and a Debug copy of the fixture: two, because one copy cannot tell a correct release order from a wrong one (the completing block holds the last application through completion) and because the contract is plural. The test observes what `Lifecycle` observes, `exited` and when it comes, plus what the operating system observes, which processes exist, read from the process table with `pgrep` and `kill(2)` rather than from AppKit. It misses only the route into `stop` (the `.runWithWindow` route and the Apple Event handler's own pool), which `Lifecycle`'s tests cover over `InMemoryRunningCopies` and which the slice's end-to-end run confirms. The new test resembles `LauncherKit/Tests/LauncherPlatformTests/SystemTrackpadPreferencesTests.swift` (the real adapter, a push macOS delivers after a child process acts, awaited on the main actor under a time limit) and borrows the bounded-await helper in `LauncherKit/Tests/LauncherPlatformTests/BoundedWait.swift` and the bundle making and tool running in `LauncherKit/Tests/LauncherPlatformTests/BundleFixture.swift`. Nothing we own is faked, and no system boundary either: the processes are real, LaunchServices launches them, the KVO push is macOS's. The one deliberate stand-in is the autorelease pool: the test's own `autoreleasepool` block drains where the Apple Event handler's would. Against today's adapter the test crashes the test process at that drain, with the crash reports' stack, which is the red R3 asks for; against the fixed adapter it passes.

## Further Notes

- **What the prototypes established** (command-line programs and a throwaway Swift Testing package, since removed, against script bundles under `com.example.TrackpadLauncherFixture.plan035…` in a temp folder, never the app's family):
  - LaunchServices launches such a bundle and lists its pid under the identifier; `NSRunningApplication(processIdentifier:)` returns a fresh instance each call, never the workspace's, so nothing else in the process keeps the adapter's instance alive, which is why the drain is fatal and the test deterministic.
  - Observe-without-retain plus a pool drain aborts with the reports' stack. With two copies, a struct that releases the application before its observation aborts at completion instead, under `swift_arrayDestroy`, with the same stack; the watch shape survives both the drain and completion, `exited` runs once, a fresh `NSRunningApplication(processIdentifier:)` is already nil and the family's list already empty right after the push, and `kill(pid, 0)` fails with `ESRCH` at once.
  - The push needs the main run loop: none arrived while the main thread was blocked, one at once when the run loop ran. Under `swift test`, a main-actor test runs on the main thread, a run-loop timer fires while it awaits, and the exit push arrived on the main thread, so the harness turns the loop.
  - `NSWorkspace.openApplication`'s completion for a script app arrives after 30 s (LaunchServices' launch timeout for an app that never checks in), with the process listed after 0.06 s; a second launch request from the same client, of the same bundle, of another bundle with the same identifier, or of its `.debug` twin, waits behind that completion. Two `open -g` processes get a release copy and a Debug copy running within a second, each `open` returning in about 50 ms.
  - `lsappinfo info -pid <pid>` prints `type="Foreground"` for an app with a regular activation policy and `type="UIElement"` for a background one; `lsappinfo list` names every running app's `bundleID`.
- **Why the red is a crash and not a failure.** Swift Testing's exit tests (`#expect(processExitsWith:)`) could run the stop in a child process and turn the pre-fix crash into an ordinary failure that leaves the rest of the suite running. Not chosen: the body would run in a fresh child whose main-actor and run-loop behaviour for a LaunchServices push is unverified, R3 accepts a crash, and a red here is the production crash itself, so a crashed run is an honest signal. Worth revisiting only if the test ever has to stay red for long.
- **T2 reuses T1's processes rather than made-up pids.** A pid that merely looks unused could belong to a live application, which `stop` would force-terminate; the only pids the test may hand to `stop` are its own fixture's. T2's first case therefore runs in the same test function after T1's `exited`, when LaunchServices has already noticed the deaths (the prototype saw the family's list empty right after the push), and requires that before calling `stop`; a copy killed by hand and not yet noticed would be observed, not dropped, and `exited` would come late.
- **`LaunchWatch` is unchanged.** It already keeps `process` beside its observations and invalidates in `stop`. The two observers of `NSRunningApplication` now follow the same rule in their own code; if a third appears, the watch type is the shape to share, and that is the moment to move it out of the adapter.
- **The end-to-end run needs a build under a throwaway identifier, and `repro.sh` needs to look at R1's THEN.** The Info.plist takes `$(PRODUCT_BUNDLE_IDENTIFIER)`, so a command-line override gives the build: the perf build's command line (Release, `CODE_SIGN_IDENTITY="Apple Development"`, so the copy reads as a development build and runs where it is) plus `PRODUCT_BUNDLE_IDENTIFIER=com.example.TrackpadLauncherRepro` and its own derived-data path; that identifier is outside the app's family, so the rounds never touch the installed app or a Debug copy, as `repro.sh`'s header says. As written, `repro.sh` counts a round as alive when any pid other than the old copy's survives, which neither sees the old copy exit nor the new copy become resident (a copy stuck in `.replacingOthers` is alive, with no gestures, which is the user's symptom). The slice extends it: a round passes only when the old pid is gone (`kill -0` fails) and the new pid's `lsappinfo info -pid` shows `type="Foreground"`, which the settings window's opening makes of an `LSUIElement` app and which a copy stuck before `othersExited` never reaches; the summary line keeps its shape with that stricter meaning of alive. The signal is checked first on a copy opened alone. This run is a confirmation at the whole-app level of what T1 proves at the adapter's, the actual route and the actual pool, not a second proof of R1.
- **Teardown uses `kill(2)`, never AppKit's terminate.** The adapter is the one place that force-terminates, and the test should not duplicate its act; `SIGKILL` by pid is the operating system's own backstop, and the script's bounded loop is the backstop behind that. A leftover is looked for through LaunchServices by identifier (`lsappinfo list`), not with `pgrep` on `sleep`, which would match any process's sleep.
