# S5: Make the change easy: a window swipe's start waits for the model's answer

## Goal

A prefactor with one small visible change. Today the recognizer decides alone that a slide up or down is a window swipe. After this slice, a slide up or down begins **unconfirmed**. It is a window swipe only once the main actor answers its start with "yes", and a "no" turns it into exactly the slide the window swipe setting off would have made. The model answers "yes" to every start for now, so behaviour stays as today except for one thing: a window swipe blocks clicks and scrolling from the frame **after** its start, not on the start frame. The next slice (S6) makes the model answer "no" when the frontmost app has fewer than two windows. All paths below are under `LauncherKit/` unless they start with `docs/` or `plans/`.

## Requirements

Delivered here only in the part the answer protocol carries: a start is answered once, by its own handling; a declined slide is exactly the setting-off slide, at the recognizer; blocking applies once confirmed, from the frame after the start.

- **R1 (part):** "A window swipe MUST start only when the frontmost app has at least two windows (R13). Deciding this MUST add no delay the user can notice." (S5 builds the question and answer; S6 makes the model ask the windows.)
- **R2:** "The first movement past 3 mm MUST decide whether a slide is sideways (a swipe) or up or down (a window swipe when R13 and R14 allow; otherwise as R16 describes with the setting off). The decision MUST hold until both fingers lift. A window swipe MUST never turn into a swipe, nor a swipe into a window swipe."
- **R13 (part):** "the slide MUST NOT be a window swipe. … The slide MUST then behave exactly as it does with the window swipe setting off (R16): it scrolls once the blocking window has passed, and it never becomes a swipe, since its first movement was up or down."
- **R15:** "Click blocking MUST apply for the whole of a window swipe, as for a swipe: clicks, scrolling and the system's trackpad swipes are blocked, and the blocking window is held open until both fingers lift. … It MUST be cancelled when a third finger lands outside the anchor corner while both are down, or a click reaches apps; a cancelled window swipe MUST keep the window in front as it is at that moment, without the lift's reordering, and be silent."

## Design

### The idea, and why blocking starts one frame late

Whether a slide up or down is a window swipe depends on the frontmost app's windows, which only the main actor reads. The slide's blocking is decided frame by frame on the frame thread. So the recognizer still begins a `.swiping` slide for `.windowSwipe` and reports `.windowSwipe(.began)`, but that `Swipe` is born **unconfirmed**:
- Its phases are reported as usual (`.began`, `.moved`, `.ended`, `.cancelled`).
- It blocks only by the **thumb rules**, which are exactly the flags the spoiled slide of the setting off would give on that frame.

`GestureRecognizer.answerWindowSwipe(began:isWindowSwipe:)` settles it:
- `true` confirms it. From the next frame on it blocks like any `.swiping` slide, until both fingers lift.
- `false` turns the state into the one `beginOrSpoil` would have returned with the setting off. That is `.spoiled(thumb)` under the slide's thumb. If that thumb has gone, it is instead a rest of every contact down, as the spoiled state's own exit (`restOrIdle`) gives it, a thumb that rolled out of the corner included.

The answer names its start by the `FrameTime` of the frame that began it. An answer to an earlier start, one that arrives after its slide ended, and a second answer all change nothing. A swipe (sideways) is born confirmed.

Why the unconfirmed start frame must not block: the scroll filter never relaxes a scroll it has once stilled. If a slide started blocked and was released on a decline, a declined slide after the 3 s blocking window would stop scrolling, which R13 forbids. The accepted cost is that after the blocking window, a scroll or press in the start frame reaches apps; such a press cancels the window swipe (T35 (a)). Within the blocking window nothing changes, because the thumb rules already block.

### Recognizer (`Sources/LauncherCore/GestureRecognizer.swift`)

```swift
// Swipe gains:
//     let began: FrameTime        // the frame time beginOrSpoil began it on
//     var isConfirmed: Bool       // true for .swipe, false for .windowSwipe at begin
// Blocking: a confirmed .swiping blocks (both flags true, as today); an unconfirmed one falls to the thumb rules on
// swipe.thumb: the flags the spoiled slide of the setting off gives on the same frame.

/// The model's answer to the window swipe start reported on the frame at `began`. true confirms it: from the next
/// frame it blocks clicks, scrolling and the system's swipes until both fingers lift. false turns the slide into
/// what the window swipe setting off makes of it: `.spoiled` under the slide's thumb, or, once that thumb has gone,
/// a rest of every contact down as `restOrIdle` gives it (a thumb that rolled out of the corner counts as one of
/// them), so it never becomes a swipe and a thumb tap under it may swap as it would there. Changes nothing
/// unless an unconfirmed slide that began at `began` is in progress: an earlier start's answer, an answer after the
/// slide ended and a second answer are ignored. (Exactly the setting-off state when it arrives before the next
/// frame; a thumb that lifted and landed again before a late false is taken as the slide's thumb.)
public mutating func answerWindowSwipe(began: FrameTime, isWindowSwipe: Bool)
```

Notes from the current code:
- The blocking computation at the end of `step` sets both flags true for any `.swiping`. Make that apply only to a confirmed `Swipe`. For an unconfirmed one, apply the existing thumb-rule branch with `swipe.thumb?.id` as the thumb. `State.thumb` currently returns nil for `.swiping`, so either extend it for an unconfirmed swipe or compute it at the blocking site.
- On a false answer, "every contact down" is the set of contacts down on the last frame stepped, after the edge filter: `previouslyDown`. With the thumb still present (`swipe.thumb != nil`) the state becomes `.spoiled(thumb)`. With no thumb it becomes `Self.restOrIdle(of: previouslyDown ?? [])`.
- After a decline the recognizer emits no further `.windowSwipe` phase for that slide, so no `.ended` or `.cancelled` follows. The model only ever saw a `.began` it did not confirm. Check against the reference recognizer that this is what T67 (a) expects: "every recognition equals the reference's, the start's own `.windowSwipe(.began)` aside".
- An unanswered or unconfirmed slide that ends normally still reports `.ended` (T67 (c)).

### The port (`Sources/LauncherCore/Ports.swift`)

`TrackpadHardware` gains a protocol requirement, written inside the protocol body and not in an extension, so that a call through `any TrackpadHardware` reaches the adapter:

```swift
@MainActor public protocol TrackpadHardware: AnyObject {
    /// … existing doc, plus: A `.windowSwipe(.began)` asks whether its slide is a window swipe. Once the call returns,
    /// the adapter answers that start, true only if `confirmWindowSwipe(on:)` was called during it, and the trackpad's
    /// recognizer takes the answer before its next frame: confirmed, the slide blocks until both fingers lift;
    /// declined, it goes on as with the window swipe setting off.
    var onEvent: (@MainActor (TrackpadEvent) -> Void)? { get set }
    // connected(), run(_:handMode:blockClicks:slides:swaps:), playFeedback(_:on:): unchanged.

    /// Only while `onEvent` is handling a `.windowSwipe(.began)` from `trackpad`: makes that slide a window swipe.
    /// Anywhere else, including an event a test injected, it does nothing.
    func confirmWindowSwipe(on trackpad: TrackpadID)
}
```

Also update the `SwipePhase.began` doc (in `Gesture.swift` or wherever `SwipePhase` lives): "One of two fingers under an anchored thumb moved past 3 mm. Travel is 0 here: the 3 mm do not count. A window swipe's start is a question: it is a window swipe only if the model confirms it while handling this phase (`TrackpadHardware.confirmWindowSwipe(on:)`)."

### `WindowSwipeConfirmation` (new, `Sources/LauncherCore/`, its own file)

This is the main-actor half of the answer. It is one rule both hardware adapters share, as they already share `TrackpadEvent.init(_:on:)` and `TouchFrame.Press.init(holding:buttonDown:)`.

```swift
/// The main-actor half of the answer to a window swipe's start, one rule both hardware adapters share, as they share
/// `TrackpadEvent.init(_:on:)`: every event reaches `onEvent` through `deliver`, and a start comes back with its answer
/// for the adapter to send to that trackpad's recognizer.
@MainActor public final class WindowSwipeConfirmation {
    public init()
    /// Hands `event` to `handler`; nil drops it. For a `.windowSwipe(.began)`, returns whether `confirm(on:)` named the
    /// event's trackpad while `handler` ran, so false when it did not, or `handler` is nil. nil for every other event,
    /// which gets no reply.
    public func deliver(_ event: TrackpadEvent, to handler: (@MainActor (TrackpadEvent) -> Void)?) -> Bool?
    /// What the adapter's `confirmWindowSwipe(on:)` calls. Counts only while `deliver` hands over a start from
    /// `trackpad`; any other call does nothing, and nothing carries over to the next start.
    public func confirm(on trackpad: TrackpadID)
}
```

### Real adapter (`Sources/LauncherPlatform/FrameStream.swift`, `MultitouchTrackpads.swift`)

```swift
/// The answer to one window swipe start: the frame time the start was reported on, and whether it is a window swipe.
struct WindowSwipeAnswer: Sendable { let began: FrameTime; let isWindowSwipe: Bool }

final class DeviceSession: Sendable {
    /// `deliver` now also carries, for a frame that reported `.windowSwipe(.began)`, the reply for that start: called
    /// once on the main actor, it records `WindowSwipeAnswer(began: frame.time, isWindowSwipe:)`. nil for every other
    /// event.
    init(trackpad: TrackpadID, recognizer: GestureRecognizer, pointerCurves: [PointerCurve.Point], clickTap: ClickTap?,
         deliver: @escaping @Sendable (TrackpadEvent, _ reply: (@Sendable (Bool) -> Void)?) -> Void)
    // Writer: the main actor, through a reply. Reader: this device's frame callback, which reads it before taking the
    // recognizer's lock and hands it to `answerWindowSwipe(began:isWindowSwipe:)` before `step`. Never cleared: the
    // recognizer ignores an answer it has already taken or that names another start.
    // private let answer = Mutex<WindowSwipeAnswer?>(nil)
}
```

`MultitouchTrackpads` holds one `WindowSwipeConfirmation`. In the hop on the main actor, after the existing generation check (`self.runs == generation`), it calls `let answer = confirmation.deliver(event, to: onEvent)`, then `reply?(answer)` when both exist. Its `confirmWindowSwipe(on:)` only forwards to `confirmation.confirm(on:)`. An event from a replaced run is still dropped before `deliver`, reply and all, because its session is gone. The `.trackpadsChanged` events from IOKit and wake may go through `deliver` too (they get nil); keep it simple. Add no timer, queue or wait.

### In-memory adapter (`Tests/LauncherCoreTests/InMemoryAdapters.swift`, `InMemoryTrackpads`)

- Hold a `WindowSwipeConfirmation`. In `touch(_:on:)`, hand every event to `onEvent` through `confirmation.deliver(_:to:)`.
- When the answer is non-nil (a `.windowSwipe(.began)`), give it straight to the running recognizer with the start frame's time: `running[id]?.answerWindowSwipe(began: sampled.time, isWindowSwipe: answer)`. This happens between frames, before the next frame is stepped. Append the answer to a new `private(set) var windowSwipeAnswers: [Bool]`.
- `inject(_:)` also goes through `deliver`, and its answer goes nowhere.
- `confirmWindowSwipe(on:)` forwards to `confirmation.confirm(on:)`.
- Guard against the recognizer having been replaced by a `run` inside `onEvent`: answer only the recognizer that stepped the frame. If `running[id]` was replaced, the new recognizer has no such start, so `answerWindowSwipe` ignores it anyway.

### The model (`Sources/LauncherCore/Launcher.swift`)

In `windowSwipe(_:)`, `case .began:` first calls `hardware.confirmWindowSwipe(on: event.trackpad)`, before any guard. That confirms every start, which keeps today's behaviour, message rows and all. S6 replaces this with the real rule.

### Test drivers (`Tests/LauncherCoreTests/Fixtures.swift`, and private drivers in other test files)

- Every recognizer driver (`fired`, `phases`, `windowPhases`, `swaps`, `perFrame`) takes `answering: Bool? = true`. After stepping a frame whose recognition has `windowSwipe == .began`, a non-nil `answering` is passed to `answerWindowSwipe(began: frame.time, isWindowSwipe:)` before the next frame. With nil, starts are never answered.
- A small shared helper keeps this in one place, for example an extension on `GestureRecognizer` in `Fixtures.swift`: `mutating func step(_ frame: TouchFrame, answering: Bool?) -> Recognition`.
- Recognizer tests that build a `GestureRecognizer` directly and step it go through the same helper with the default (confirm), so every existing recognizer row keeps its meaning. Grep `GestureRecognizer(` under `Tests/`. Today that is `WindowSwipeRecognizerTests`, `EdgeContactRecognizerTests`, `GestureRecognizerTests`, `SwapRecognizerTests`, `ClickBlockingRecognizerTests` and `DockSwipeBlockingRecognizerTests`. Those with `slides: [.swipe]` or `[]` never see a window swipe start, so they are unaffected, but use the helper wherever a window swipe can begin.
- `DeviceSession` test helpers (`Tests/LauncherPlatformTests/DeviceSessionTravelTests.swift`) take the new `deliver` signature. T17 there should answer each start true so that its travel comparison is unchanged.

## Rules that apply

- `docs/architecture.md` Shape: "`LauncherCore` (domain types, pure policy, ports, the model; imports Foundation and Observation only)". `WindowSwipeConfirmation` lives in `LauncherCore` and imports nothing else.
- `docs/architecture.md` Shape: "Every port has exactly two adapters: the real one in `LauncherPlatform` and an in-memory one in the tests." Both adapters implement `confirmWindowSwipe(on:)`, and no third adapter appears.
- `docs/architecture.md` Concurrency: "Multitouch frames are recognised on the framework's own thread; only recognised events hop to the main actor … One thing hops back: the model's answer to a window swipe's start … The model gives it while it handles the start; the adapter replies once that call returns, and the frame thread hands the reply to that trackpad's recognizer before its next frame. The recognizer ignores an answer to any other start. Until the answer arrives the slide blocks only by the thumb rules, and the frame thread never waits for it. State shared with that thread lives behind a `Mutex` with one writer." The answer slot is a `Mutex` with the main actor as its only writer, and the frame thread never blocks on or polls for the answer.
- `docs/architecture.md` Concurrency: "No timers, no polling, no background loops: every input is a push". Do not use a semaphore, dispatch wait, timer or sleep.
- `docs/architecture.md` Language: "Swift 6 language mode with complete strict concurrency". The reply closure is `@Sendable`; the slot and the session stay `Sendable`.
- Recognizer doc: "Owned by exactly one frame thread (real adapter) or by the test (in-memory adapter); never shared." `answerWindowSwipe` is called under the session's recognizer lock, on the frame thread, before `step`.
- `docs/domain-model.md` *Blocking window*: "held open for the whole of a swipe, a window swipe or a swap series". A confirmed window swipe keeps both flags true until both fingers lift.
- The source scan (`Tests/LauncherCoreTests/SourcePolicyTests.swift`) bans timers, `asyncAfter`, `Task.sleep` and logging. It also reads comments, so comments must not spell a confined API name.
