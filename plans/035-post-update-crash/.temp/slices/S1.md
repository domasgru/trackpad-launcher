# S1: A new copy survives stopping the copy before it

## Goal

After an update, or `make run` beside the installed app, the new copy stops the old one and stays running with its resident built, instead of crashing within a second. `SystemRunningCopies` keeps each stopped copy's `NSRunningApplication` alive beside its observation and invalidates before letting go. A real-process test in `LauncherPlatformTests` runs the real `stop` against a release copy and a Debug copy of a fixture app LaunchServices launched, with the pool drain the Apple Event handler makes: red (a crash with the crash reports' stack) before the fix, green after. `repro.sh` is made stricter and run end to end after the fix.

## Requirements

**R1. Every observed process outlives its observation.** `SystemRunningCopies` MUST keep each `NSRunningApplication` it observes alive until that application's observation has been invalidated, on every path, including when the last copy exits. Invalidating MUST come before releasing the application.

Scenario, the update hand-over:
- GIVEN a copy of the app is running
- WHEN a new copy starts as a new instance and stops the running copy
- THEN the running copy exits, and the new copy stays running with its resident built
- AND `repro.sh <app> 15 stopped` reports 15 new copies alive and 0 dead, and no new crash report appears

**R2. `stop`'s contract is unchanged.** `RunningCopies.stop` MUST keep its documented behaviour: it stops each listed copy at once and calls `exited` once, on the main actor, when every listed copy has exited, synchronously when none still runs. Observable behaviour other than the crash MUST not change.

**R3. A test runs the real `stop` against a real process.** A test in `LauncherPlatformTests` MUST start a real throwaway app process and stop it through `SystemRunningCopies`, with an autorelease pool draining around the `stop` call as the Apple Event's does. It MUST crash or fail against today's code and pass with the fix. It MUST NOT touch any process outside its own fixture: its identifier family MUST be the fixture's alone.

## Design

### Root cause

`SystemRunningCopies.stop` keeps the `NSKeyValueObservation`s in `watches` but holds the observed `NSRunningApplication`s only in the local `apps`. `NSKeyValueObservation` does not retain the object it observes. `stop` runs inside the open Apple Event's handler (`applicationDidFinishLaunching`), so when that event's autorelease pool drains, an `NSRunningApplication` can deallocate with its observers still registered. The Swift helper then calls `removeObserver` on the object mid-dealloc. `LaunchWatch` already avoids this by keeping `process` beside its observations.

### The adapter: `LauncherKit/Sources/LauncherPlatform/SystemRunningCopies.swift`

- **The fix is confined to the real adapter's implementation; its interface does not move.** `SystemRunningCopies` keeps `init(bundleIdentifier:)`, `others()`, `stop(_:then:)` and `endThisCopy()` exactly as they are, and so do the `RunningCopies` port, `Lifecycle`, `InMemoryRunningCopies`, the exit counter (`Remaining`), `family(of:)` and `started(_:before:)`.
- **A stop under way holds each copy's application beside its observation, in a watch that invalidates before it lets go.** In place of the array of bare `NSKeyValueObservation`s, the adapter keeps one watch per listed copy still running. A watch is a small private main-actor class that owns the `NSRunningApplication` and the observation of its `isTerminated`; its `invalidate()` invalidates the observation (Foundation's `invalidate()` is itself idempotent, so the watch keeps no flag and no optional); its deinit calls `invalidate()`. A class, not a struct, deliberately: a class's deinit body runs while its stored properties are still alive, so the observation is invalidated while the watch still retains the application, whichever path releases the watch (completion, a later `stop` replacing the set, the adapter's own deinit). A struct gives no say in which member goes first, and application-first recreates the crash on the completion path.
- **Completion invalidates every watch explicitly and then drops the set, before calling `exited`**, in the manner of `LaunchWatch.stop`: that is the mechanism the next reader sees, and the deinit is the guarantee behind it, the only one on the path a later `stop` takes. Both stay.
- One copy cannot tell these shapes apart, two can: the main-queue block that completes the stop captures the application whose exit it reports, so on a one-copy list that application outlives completion whatever the watch does, while the first copy of two is, by then, held by its watch alone.
- The shape, from the prototype that reproduced the crash with the old shape and ended cleanly with this one:

  ```swift
  @MainActor private final class Watch {
      let app: NSRunningApplication           // retained: an observation does not retain its object
      let observation: NSKeyValueObservation
      func invalidate() { observation.invalidate() }
      isolated deinit { invalidate() }        // runs before `app` is released, whichever path drops the watch
  }
  ```

- **Everything else in `stop` is as today.** The listed copies are resolved to applications by pid and those already terminated are dropped; with none left, `exited` runs synchronously; each remaining application is force-terminated and then observed with `.initial` and `.new`; each exit counts once per pid; the handler hops to the main actor through the main queue, where completion runs outside any KVO dispatch; a second `stop` while one is under way replaces the set, as today, and the replaced watches are now released safely.
- The adapter stays the only file that force-terminates (source-scan confinement, see Rules).
- **Doc comments** on the adapter's watch say why the application is kept and why invalidation comes first (an observation does not retain its object; `NSRunningApplication` crashes in `removeObserver` mid-dealloc), so the next reader does not simplify it away.
- `LaunchWatch` is unchanged. Do not share the watch type with it.

### The fixture: `LauncherKit/Tests/LauncherPlatformTests/BundleFixture.swift`

`BundleFixture`'s existing bundles exist to be copied, archived and verified: their executable is a text file and every item carries the quarantine attribute, so LaunchServices would never run them. Leave `makeBundle` alone. Add a second kind of bundle that macOS does launch:

- Its executable is a shell script, mode 755, that loops over `sleep 1` for about two minutes and then ends, so a test that dies before stopping it leaves nothing behind for longer than that. **No `exec`:** the process LaunchServices knows is the shell, so its argv names the bundle, and `pgrep -f` on the bundle's executable path finds it, an independent read of the process table.
- Nothing in it is quarantined.
- `LSBackgroundOnly` is set in its Info.plist, so it never shows in the Dock or takes focus.
- The test makes two such bundles at different paths: the release copy's identifier is `BundleFixture.identifier` with a suffix unique to this test, and the Debug copy's is that with `.debug` appended, the one family `family(of:)` derives. An adapter built on the release identifier therefore lists exactly that pair and nothing else, whatever else runs on the Mac, the same test in another worktree's session at the same moment included. The family is the fixture's alone, never the app's. A per-run unique suffix (for example from a UUID) is what "unique to this test" must mean, because another worktree can run the test at the same moment.
- Two minutes is deliberately longer than the test's 30 s bound on `exited`, so a copy ending of its own accord can never stand in for the stop.
- `BundleFixture.run(_:_:)` is private, throws on non-zero exit, and has no stderr handling. `pgrep` exits 1 on no match, so give the fixture what the test needs without weakening `run` for existing callers. `/usr/bin/open` and `/usr/bin/pgrep` are the tools.

### The test: new file in `LauncherKit/Tests/LauncherPlatformTests/` (for example `SystemRunningCopiesStopTests.swift`)

- **Launch with `/usr/bin/open -g`, one `open` process per copy, not with `NSWorkspace.openApplication`.** Both are LaunchServices launches, so each process gets the registration `others()` reads (`runningApplications(withBundleIdentifier:)`). `openApplication` was measured and rejected: its completion for an app that never checks in with LaunchServices, which a script app never does, arrives only after LaunchServices' 30 s launch timeout, and a second launch request from the same client waits behind that completion, whether of the same bundle, of another bundle with the same identifier or of its `.debug` twin. `open` returns in about 50 ms, each `open` is its own client, and both copies are listed within a second.
- The test waits, bounded, for `others()` to list two copies, polling it briefly as `BundleFixture.bundles(identifiedBy:within:)` polls, and takes the pids themselves from the process table through `pgrep -f` on the two bundles' executable paths.
- **Teardown:** it keeps the pids and sends each `SIGKILL` on teardown if it is still alive, so a failing test never leaves a process; a `sleep 1` child of a killed shell lasts at most a second longer. Teardown uses `kill(2)`, never AppKit's terminate: the adapter is the one place that force-terminates, and the test must not duplicate its act. A leftover is looked for through LaunchServices by identifier (`lsappinfo list`), not with `pgrep` on `sleep`.
- **The autorelease pool drain is the test's own, around the `stop` call.** `stop` is called inside an explicit `autoreleasepool` block, whose end drains synchronously before anything is awaited. The prototype showed this drain kills an unfixed process at once with the crash reports' stack (`NSKVODeallocate` → `-[NSRunningApplication removeObserver:forKeyPath:]` → `NSInvalidArgumentException`) and leaves a fixed one alive.
- **The test awaits the exit on the main actor without blocking the thread.** macOS pushes `isTerminated` through the main run loop: no push arrives while the main thread is blocked. The test is main-actor (the adapter is) and awaits `exited` through the suite's existing bounded-await helper `awaiting(_:within:start:)` in `BoundedWait.swift`, at its default 30 s, never through a semaphore or `waitUntilExit`. The helper only suspends; the harness keeps the main run loop turning (verified: under `swift test` a main-actor test runs on the main thread, a run-loop timer fires while it awaits, and the exit push for a script app LaunchServices launched arrives on the main thread).
- `exited` itself records how many times it ran and whether it ran on the main thread; the helper wakes the test once and would hide a second call.
- The independent truth that the processes are gone is `kill(pid, 0)` failing with `ESRCH`, not AppKit's view of it, re-read for up to 2 s because launchd, not the test, reaps them and `kill` still succeeds on a zombie.
- **T2 reuses T1's processes rather than made-up pids.** A pid that merely looks unused could belong to a live application, which `stop` would force-terminate; the only pids the test may hand to `stop` are its own fixture's. T2's first case runs in the same test function after T1's `exited`, and requires `others()` to be empty before calling `stop`; a miss reads as a failed precondition, not as R2 failing.
- Why the red is a crash and not a failure: exit tests (`#expect(processExitsWith:)`) were considered and not chosen. Do not use them. Against today's adapter the test crashes the test process at the drain.
- Nothing in the test names `com.domasgru.TrackpadLauncherApp` or its `.debug` twin.
- Resembles `SystemTrackpadPreferencesTests.swift` (the real adapter, a push macOS delivers after a child process acts, awaited on the main actor under a time limit: `@MainActor @Suite(.timeLimit(.minutes(1))) struct`) and `RunningCopiesFamilyTests.swift` (adapter built through `init(bundleIdentifier:)`). `Process.start()` in `ProcessWait.swift` starts a process and returns a closure that waits for its exit without turning the run loop.

### `plans/035-post-update-crash/repro.sh`

As written it counts a round as alive when any pid other than the old copy's survives, which neither sees the old copy exit nor the new copy become resident (a copy stuck in `.replacingOthers` is alive, with no gestures, which is the user's symptom). Extend it: a round passes only when the old pid is gone (`kill -0` fails) and the new pid's `lsappinfo info -pid` shows `type="Foreground"`, which the settings window's opening makes of an `LSUIElement` app and which a copy stuck before `othersExited` never reaches. The summary line keeps its shape (`ending=... rounds=... new-copy-alive=... new-copy-dead=...`) with that stricter meaning of alive. The worktree guard applies to your commands, not to the script's own contents: the script may use shell variables, but edit it with Edit. Update its header comment to say what alive means.

`lsappinfo info -pid <pid>` prints `type="Foreground"` for an app with a regular activation policy and `type="UIElement"` for a background one.
