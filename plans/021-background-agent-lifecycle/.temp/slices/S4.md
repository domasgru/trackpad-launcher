## Goal

*Quit Trackpad Launcher* turns starting at login off, but only when it is on, and only then does the next opening by hand turn it back on. The user's own off in Login Items is never overridden, including by an upgrade. Any copy inside /Applications is treated as installed, whatever its build. A development build outside /Applications never touches starting at login.

## Requirements

- **R5 (in part).** The first run from /Applications MUST make Trackpad Launcher start at every login (a development build inside /Applications included: it is `installed`).
- **R11 (in part).** Pressing *Quit Trackpad Launcher* turns starting at login off (see R12).
- **R12.** Pressing *Quit Trackpad Launcher* MUST turn starting at login off, only if it was on at that moment. Trackpad Launcher MUST NOT start at the next login after a Quit. Opening it by hand after a Quit MUST start it. It MUST turn starting at login back on only when that Quit was what turned it off.
  - Quit, then restart → not running. Quit, restart, then open by hand, then restart again → after the second restart it runs in the background with no window.
- **R13.** When the user turned Trackpad Launcher off under *System Settings → General → Login Items*, Trackpad Launcher MUST NOT turn it back on, whatever happens: opening it by hand, the first run of a newer version, or opening it after a Quit. When the user turns it back on there, R12 applies again.
  - Off, then opened by hand → still off. Off, then Quit and reopened → still off. Off, back on, then Quit and reopened → on. Off, then a newer version installed into /Applications and opened → still off.
- **R18 (in part).** Which copies count as outside /Applications: anything not inside /Applications at any depth; ~/Applications counts as outside.
- **R23 (in part).** A development build is a build not signed for release, for example one run from Xcode. (Here: outside /Applications it leaves starting at login alone.)
- **R25.** Upgrading from a version with the menu bar icon MUST keep every setting and keep starting at login as it was. The menu bar icon MUST be gone from the first start of the new version.
  - A menu bar version, with gestures assigned, was replaced by this version; the user logs in → it runs with no menu bar icon and no Dock icon, and every gesture brings its assigned app to front.

## Design

### `StartAtLogin` (LauncherCore, `Lifecycle.swift`)

Starting at login is owned by `StartAtLogin`, whose one remembered fact ("Trackpad Launcher turned it off itself") has **its own `UserDefaults` key beside the `settings` record, never inside it**: the mover and the running copy then never write the same record, an older build's save cannot drop the fact (`Settings` ignores unknown keys), and a move never creates or spends a first run. Name the key in the code (e.g. `"startAtLoginTurnedOffByQuit"`); it is present only while remembered (remove it to forget, so "only `settings` remains in the suite" after a resume).

`StartAtLogin` has three intents and only ever asks "is it `.enabled` now?" (`item.isOn`), so the disputed status after a user's own choice cannot mislead it:

```swift
/// Starting at login: the one owner of "Trackpad Launcher turns back on only what it turned off itself" (R5, R12,
/// R13, R20, R25). Its one fact is its own key in the app's defaults domain, beside the `settings` record.
/// A development build outside /Applications leaves starting at login alone: every intent is a no-op for
/// `.development`.
@MainActor public final class StartAtLogin {
    public init(item: any LoginItem, defaults: UserDefaults, placement: Placement)

    /// The first run: turn it on and forget any stale fact. A user's earlier off stands: macOS refuses.
    public func enrol()        // item.register(); forget()

    /// Quit, or a move: if it is on now, remember that Trackpad Launcher turned it off, then turn it off.
    public func suspend() {
        // guard item.isOn else { return }
        // remember()            // first: a crash before unregister leaves it on and remembered; resume converges
        // item.unregister()
    }

    /// Opened by hand: turn it back on only if Trackpad Launcher turned it off. The fact stays until macOS accepts.
    public func resume() {
        // guard isRemembered else { return }
        // if item.register() { forget() }     // register first: a crash before forget re-registers, harmlessly
    }
}
```

Crash order: remember before unregistering, register before forgetting, so every crash point converges on the next opening by hand. All three intents are no-ops when `placement == .development`.

### `LoginItem` port gains

```swift
@MainActor public protocol LoginItem: AnyObject {
    /// `.enabled`: the next login starts it. Every other status (never registered, the user's off) is off.
    var isOn: Bool { get }
    @discardableResult func register() -> Bool   // as in S1
    /// This process keeps running. A no-op when not registered.
    func unregister()
}
```
`SystemLoginItem`: `isOn = SMAppService.mainApp.status == .enabled`; `unregister()` = `try? SMAppService.mainApp.unregister()` (`kSMErrorJobNotFound` ignored; `SMAppService` stays confined to this file).

### Wiring

- `Lifecycle.quit()`: `guard launcher != nil; startAtLogin.suspend(); end()`. So `Lifecycle.init` gains `startAtLogin: StartAtLogin`. (S5 will also give it `placement:` and `installer:`; the final init is `init(placement:copies:installer:startAtLogin:makeResident:)` — order parameters so those insert cleanly.)
- `Launcher.openedByHand()`: the first time in this process, on a first run: `enrol()`, ask, save (as now); **on any other run: `startAtLogin.resume()`**. Every time: the window opens.
- AppDelegate: one `StartAtLogin(item: SystemLoginItem(), defaults: .standard, placement: placement)` shared by `Lifecycle` and `Launcher`.

### `Placement`, `Location`, `Build`, `DiskImage` (LauncherCore)

```swift
public enum Build: Equatable, Sendable {
    case release
    /// Not signed with a Developer ID: Xcode, the perf build, an ad-hoc binary. Never `#if DEBUG`.
    case development
}

public struct DiskImage: Hashable, Sendable {
    public let volume: URL
    public init(volume: URL)
}

/// Where this copy lies, read once at start. (S5 adds `ThisCopy.location()`, which fills it from macOS.)
public struct Location: Equatable, Sendable {
    /// `Bundle.main.bundleURL`: a hidden translocation mount when macOS translocated a quarantined copy.
    public let running: URL
    /// The bundle the user opened, where Finder shows it; `running` when not translocated.
    public let original: URL
    /// What macOS says, stored: never inferred by comparing two spellings of a URL.
    public let isTranslocated: Bool
    /// The disk image `original` lies on; nil anywhere else.
    public let diskImage: DiskImage?
    public init(running: URL, original: URL, isTranslocated: Bool, diskImage: DiskImage?)
}

/// Where this copy stands for an opening by hand (R5, R18, R23). One rule, pure.
public enum Placement: Equatable, Sendable {
    /// Inside /Applications, at any depth, not translocated, whatever the build: its first run starts it at login (R5).
    case installed
    /// A development build anywhere else: it runs where it was built and leaves starting at login alone (R23).
    case development
    /// A release build anywhere else: a disk image, ~/Downloads, ~/Applications, a translocated copy.
    case elsewhere

    public init(build: Build, location: Location, applications: URL = URL(filePath: "/Applications")) {
        // !location.isTranslocated && location.running's standardized path lies under `applications`' → .installed
        //     (component-wise, so /ApplicationsOld is not inside, `..` is resolved, and a trailing slash never matters)
        // build == .development → .development
        // else → .elsewhere
    }
}
```

Rationale: `installed` when the running bundle is not translocated and lies anywhere inside /Applications, whatever its build (R18 says "outside /Applications", so /Applications/Utilities is inside; R5 binds every first run from /Applications). Otherwise `development` when the build is not signed with Developer ID, never `#if DEBUG`, so the perf build is development too. Otherwise `elsewhere`, ~/Applications included. A translocated copy reads `elsewhere` even when its original is in /Applications. Paths compared standardized.

Until S5, the AppDelegate builds `Location(running: Bundle.main.bundleURL, original: Bundle.main.bundleURL, isTranslocated: false, diskImage: nil)`.

### `CodeSignature` (LauncherPlatform, new `CodeSignature.swift`)

Confines `SecCode*` / `SecStaticCode*` / `SecRequirement*`. The Developer ID requirement (probed true for Developer ID apps and false for Apple-Development-signed and ad-hoc builds):

`anchor apple generic and certificate 1[field.1.2.840.113635.100.6.2.6] exists and certificate leaf[field.1.2.840.113635.100.6.1.13] exists`

```swift
public enum CodeSignature {
    /// SecCodeCopySelf against the requirement. A build not signed for release reads as `.release` when `arguments`
    /// hold `--as-release-build` (exact match), so the move and the login rules can be checked by hand without a
    /// Developer ID certificate; a release build ignores the argument (it is already `.release`).
    public static func buildOfThisProcess(arguments: [String]) -> Build
    /// Any bundle or binary on disk (SecStaticCodeCreateWithPath); a test runs it on its own ad-hoc binary and expects
    /// `.development`. Unsigned or unreadable → `.development`.
    static func build(of url: URL) -> Build
}
```

### Tests: the harness

- **`InMemoryLoginItem`** gains `unregister()` (records `"unregister"`, turns off), and **models both ways macOS may report the user's off** (F25 is disputed), selectable per test:
  - *refused*: the user's off reads `isOn == false` and `register()` returns false, staying off (`.requiresApproval`);
  - *accepted after removal*: the user's off reads `isOn == false` and `register()` returns true and turns it on (`.notRegistered` after removal from the list).
  - A helper for "the user turns it off / back on in Login Items" that is not recorded as a call by us.
  - `calls` is the ordered log of our `register`/`unregister` calls.
- **`LifecycleWorld`** builds each process's `StartAtLogin` over the Mac's login item, the Mac's defaults suite and a placement (default `.installed`; settable per process).
- **Every crash point (T23).** One ordered effect log is shared by the login item, the copies, the Accessibility ask and the first save (and S5's installer later). It snapshots what outlives a process — the suite's persistent domain (all keys, bytes), the login item's status, the permission grants — before and after each effect, and a `LifecycleWorld(restoring:)` builds a Mac from any snapshot. A guarantee that must hold however the process ends is checked at every snapshot, which covers any random kill between two writes.
- `InMemoryRunningCopies` from S3 is unchanged.

## Rules that apply

- `docs/architecture.md` § Shape: "`LauncherCore` (…; imports Foundation and Observation only)". `Placement`, `Location`, `StartAtLogin` live in Core; `UserDefaults` is Foundation, fine. "Framework and wire types never cross a port: … `UserDefaults` keys … stay inside adapters." (`StartAtLogin` is a Core concrete type over a `UserDefaults` it is given, as `SettingsStore` is; its key stays private to it.)
- § Shape: "Concrete types that can be pointed at a temp directory or a throwaway `UserDefaults` suite are not put behind a port." `StartAtLogin` takes the suite directly.
- § Shape: "Every port has exactly two adapters."
- § Shape lists Security (the code signature) among `LauncherPlatform`'s frameworks.
- § Privacy: "A source-scan test … fails the build on any banned API; add to its list rather than adding prose."
- Domain model, *Starting at login*: "Whether macOS starts Trackpad Launcher at login, as *System Settings → General → Login Items* shows it. The first run from /Applications turns it on. *Quit Trackpad Launcher* turns it off when it is on, and the next opening by hand turns it back on only when that Quit turned it off. Trackpad Launcher never turns back on what the user turned off in Login Items, whatever happens. A development build outside /Applications never changes it. Trackpad Launcher never relaunches itself after a crash or a force quit."
- Domain model, *Development build*: "A build not signed with a Developer ID, such as one run from Xcode or the performance build. It never shows the move dialog and runs where it was built; opened by hand, it stops any other running Trackpad Launcher. Outside /Applications it never changes starting at login."
- Domain model, *First run*: "It turns starting at login on when the copy is inside /Applications …"
- First run stays derived from the absence of the `settings` record; no second "has run"/"prompted" boolean. Undecodable data loads as defaults, not as a first run.
- Core doc comments never spell a confined API name (the source scan reads comments): don't write `SMAppService` or `SecCode` in `LauncherCore`.
