# Grounding index: 5-finger gesture and the swipe switcher

The artifact the runners, the judge and the test planner start from. Paths are relative to the worktree root unless absolute. `how.md` and `why.md` beside this file hold the traced model of the existing code and the rationale behind its shape; read them before the code.

## 1. Facts a design decision rests on

Standing: **probed** (what a probe printed on this machine, naming it; conclusions are marked as such), **sourced** (file and heading), **disputed** (none this round).

### Frontmost app

- F1 **probed** (`probes/frontmost-probe/output.txt`): from a plain, non-active CLI process, `NSWorkspace.shared.frontmostApplication` returned the active app (Google Chrome) with `bundleIdentifier`, `bundleURL` (`/Applications/Google Chrome.app`), `localizedName`, pid, `activationPolicy=0` (regular) and `isActive=true`; `Contents/Info.plist` existed under that URL, so `AppCatalog.entry(at:)` can parse it into an `AppEntry`. `menuBarOwningApplication` agreed. The `didActivateApplicationNotification` observer compiled and registered but saw 0 activations because nobody switched apps during the 6 s window: *not observed*, not "never fires".
- F2 **sourced** (`LauncherKit/Sources/LauncherPlatform/LaunchOverlay.swift`, `makePanel` comment "The app is never active, so it never deactivates either"; `LauncherPanel.swift` `styleMask: [.borderless, .nonactivatingPanel]`; `MenuBarShell.makeActions` `chooseOtherApp` calls `NSApp.activate()` only around the `NSOpenPanel`): Trackpad Launcher never activates except while the Other… file chooser is up. Conclusion: a read of `frontmostApplication` at swipe begin names the user's app, with the one exception of a swipe made while the Other… chooser is open, when it may name Trackpad Launcher itself.
- F3 **sourced** (`docs/domain-model.md` *Installed apps*, *Assignment*; `Apps.swift` `AppCatalog.locate`, `isInTrash`): identity is the bundle ID; "missing" is no copy outside the Trash. The switcher row's "missing apps left out" (R4) is `catalog.locate(assigned) == nil`, the rule rows already use.

### Icons at 80 pt

- F4 **probed** (`probes/icon-render-probe/output.txt`, two fresh processes): 160 px (80 pt @2x) Display P3 bitmap of the frontmost app's icon via `NSWorkspace.icon(forFile:)`: **220.9 ms** on the first draw in a cold process, 0.6 ms the second time; 21.0 ms first draw in the second process (system cache warm). Via `NSRunningApplication.icon` for the same frontmost app: **0.1 ms** first and second draw, both runs (32 representations already loaded). Ten installed apps never drawn by the process: first draws 4.1–136.0 ms, median 21.9 ms (run 1); 0.6–8.1 ms, median 0.7 ms (run 2). One other running, non-frontmost app via `NSRunningApplication.icon`: 25.1 ms (run 1), 0.7 ms (run 2). Conclusions: (i) the switcher list's icons must be drawn ahead of the swipe, as `LaunchOverlay.prepare(for:)` already does for the tap targets, or the first swipe stalls for up to ~0.2 s; (ii) the frontmost app's icon, which is unknown until the swipe begins, drew in 0.1 ms through `NSRunningApplication.icon` in both runs, so drawing it at begin is viable, with the caveat that another running app's first draw took 25 ms cold, so "fast for the frontmost" rests on two observations, not a guarantee.
- F5 **sourced** (`plans/004-launch-icon-animation/plan.md` "The icon is ready before the gesture"; `LaunchOverlay.prepare(for:)`, `renderOffMain`, `renderIcon`): the existing pattern draws icons off the main actor into a `[URL: CGImage]` cache keyed by bundle location, replaced per prepare, and renders a missing one on the spot at play time. `AppIcons` (`LauncherUI`) does the same at 16 pt with Info.plist-modification stamps and appearance.

### Event delivery from the frame thread

- F6 **probed** (`probes/task-order-probe/output.txt`): 5 trials × 5000 `Task { @MainActor in … }` created in a loop on one `userInteractive` background thread all arrived on the main actor in creation order (`inOrder=true`, 5000/5000 each). `DispatchQueue.main.async` + `MainActor.assumeIsolated`: the same. Conclusion: the hop the hardware adapter uses today (`MultitouchTrackpads.run`, `deliver: { Task { @MainActor in … } }`) kept order under load on this toolchain; the language does not document an ordering guarantee for unstructured tasks, while libdispatch documents FIFO for a serial queue. A swipe delivers began / moved / ended at ~100 Hz from one frame thread, so a design either relies on the probed order, uses the documented FIFO path (`DispatchQueue.main.async`, already used in `SystemAppScanner.handleChange`), or makes each event self-describing so reordering is harmless.
- F7 **sourced** (`plans/001-trackpad-launcher-app/development-logs.md` Plan: "the main-actor hop lives in the hardware adapter so the in-memory adapter delivers gestures synchronously"; `Tests/LauncherCoreTests/InMemoryAdapters.swift` `InMemoryTrackpads.touch` calls `onEvent` inline): the hop belongs to the adapter; the model and its tests are synchronous. Any new event kind keeps that split.
- F8 **sourced** (`plans/002-gesture-click-blocking/plan.md` Design > Problem: "a `CGEventTimestamp` that is not known to share a base with `FrameTime` (grounding Q1: never compare them)"; Alternatives "A deadline instead of a per-frame flag"): the frame clock and the event-tap clock are not comparable. Scroll suppression, like click blocking, must ride on a per-frame flag read at the event, not on a deadline.

### Recognition and the existing state machine

- F9 **sourced** (`LauncherKit/Sources/LauncherCore/GestureRecognizer.swift` lines 26–85, 114–126): `State` is `idle | armed(Anchor) | tapping(Anchor, Tap) | spoiled(Anchor)`; every non-idle state carries the anchor; anchor maintenance (lines 35–38) resets to `.idle` the moment the anchor lifts, its ID is reused, or it leaves `corner.holds`; `.tapping` spoils on `press == .click`, on `frame.time - tap.start > 400 ms`, or on any down finger > 3 mm from its landing point; `.spoiled` recovers to `.armed` only on a frame where every down contact is the anchor; `blocksClicks` is `anchor.landedAt` within 3 s **and** another contact down. Consequences for this plan: (i) the 400 ms spoil ends a two-finger rest that R3 says may still become a swipe ("no time limit"); (ii) the 3 mm spoil is exactly where a swipe must begin instead; (iii) a swipe state cannot carry a required `Anchor` because R8/R9 say the thumb may lift; (iv) `blocksClicks` must be true throughout a swipe (R13) independent of the anchor and the window.
- F10 **sourced** (`GestureRecognizer.swift` lines 27–32; `Touch.swift` doc on `Touch`): per frame, `lifted = before − down ∪ reused`, `landed = .landing ∪ not-in-before`; a reused ID lifts and lands anew in one frame; the first frame is detected by `previouslyDown == nil`; a `.down` thumb on the first frame anchors with `landedAt = nil` (no blocking window).
- F11 **sourced** (`Surface.swift`: `SurfacePoint` x 0 = left edge, 1 = right edge in both hand modes; `SurfaceSize.distanceMM`, `widthMM`/`heightMM`; `GestureRules` constants): travel in trackpad millimetres is `Δx × widthMM` of a normalised point; "right moves the selection right" in both hand modes falls out of the fixed x axis (R6).
- F12 **sourced** (`Tests/LauncherCoreTests/TouchScript.swift`, `Fixtures.swift`): frames 10 ms apart; `tap(fingers:atMM:stagger:hold:dragMM:click:)` moves fingers along x by `dragMM` over the hold (the drag is applied to every finger of the tap, ending one frame before the lift); `rollThumb`, `liftThumb`, `wait`; `HandFrames` for hand-built interleavings. Fingers are placed 8 mm apart at (62 + 8i, 45). A swipe script needs sideways travel to arbitrary distances with holds, a vertical variant, a thumb lift mid-swipe, a third finger landing mid-swipe and a press mid-swipe: the builder has no "move then hold then move" primitive today.
- F13 **sourced** (`Gesture.swift`: `case one = 1, two, three, four`, `init?(fingerCount:)`; `GestureRecognizer.step` line 64 `fired = Gesture(fingerCount: tap.touched.count)`; `Launcher.makeRows` over `Gesture.allCases`; `LauncherView` `"gesture-\(gesture.fingerCount)"`): a fifth case flows through recognition, rows, pickers and persistence by construction; the illustration is looked up by finger count and a missing SVG draws nothing (`TemplateImage.nsImage` returns nil).
- F14 **sourced** (`MultitouchTrackpads.swift` `feedbackActuation = 6`, comment "Chosen by feel: 3 weak, 4 medium, 6 strong"; `TrackpadHardware.playFeedback(on:)` has no strength parameter; `actuatorActuate(actuator, id, 0, 0, 0)`): the gesture haptic is actuation 6; a lighter tick (R7) is a different actuation ID through the same actuator.

### Click blocking and the event tap

- F15 **sourced** (`ClickTap.swift` lines 11–70, 84–127): one active session tap, head insert, mask from `PointerEvent.tapTypes` (buttons 1,2,3,4,25,26; drags 6,7,27; pressure 34), on its own `userInteractive` thread; `handle` reads `anyTrackpadBlocksClicks()` before the filter lock; verdicts `pass | drop | passAsMove` (the last rewrites `type` only). `PointerEvent.init?` returns nil for every other type, and the tap is sent only masked types. `tapCreate`/`CGEventTapCreate` are confined to this file by `SourcePolicyTests`.
- F16 **sourced** (`ClickFilter.swift`): the pure filter owns the whole-press rule per button keyed by `PressID(button, number)`; `holding` summarises for the frame thread; `forgetHeldPresses()` on tap-disable. `PointerEvent` is documented as "Everything the click tap is ever told about"; `decide` switches exhaustively.
- F17 **sourced** (`Tests/LauncherCoreTests/SourcePolicyTests.swift` lines 13–55, 65–70, 111–126): `scrollWheel` and `ScrollWheel` are **banned** under rule "R6 never scrolling"; `.post(tap:`, `CGEventPost`, `postToPid` banned ("never synthesise"); timers, `asyncAfter`, `Task.sleep`, display links banned; `nonisolated(unsafe)` banned. The confined list is `AXIsProcessTrusted`, `notify_register` → `SystemAccessibilityPermission.swift`; `tapCreate`, `CGEventTapCreate` → `ClickTap.swift`. The self-check forbids a token being both banned and confined (case-sensitive substring) and pins the kept bans. The scanner is a substring match over `LauncherKit/Sources` and `TrackpadLauncher/`, comments included, tests excluded. Consequence: suppressing scrolling requires moving `scrollWheel` (and `ScrollWheel` if any API spelled that way is used) from `banned` to `confined`, with `ClickTap.swift` (or whichever single file owns scroll parsing) as `onlyIn`, and amending `PointerEventTests.ignoresEverythingElse`, which asserts `.scrollWheel` parses to nil, and `maskCoversPressesTheirReleasesDragsAndPressureOnly`, which pins the mask bits.
- F18 **probed** (`probes/scroll-tap-probe/output.txt`): `CGEventType.scrollWheel = 22`; field raw values DeltaAxis1 11, DeltaAxis2 12, PointDeltaAxis1 96, PointDeltaAxis2 97, IsContinuous 88, ScrollPhase 99, MomentumPhase 123; `CGScrollPhase` began 1, changed 2, ended 4, cancelled 8, mayBegin 128; `CGMomentumScrollPhase` none 0, begin 1, continuous 2, end 3. Live built-in-trackpad sequences (356 events, all `isContinuous = 1`): a flick is `began → changed… → ended (zero deltas)`, then ~7 ms later `momentum begin → continuous… → end (zero deltas)`, momentum events carry `phase = 0` and last ~0.9–1.0 s; fingers resting then scrolling give `mayBegin` ~17 ms before `began`; resting then lifting without scrolling gives `mayBegin → cancelled` with no `began`; events are 4–12 ms apart in a gesture, 8–17 ms in momentum; the integer `d1` is often 0/±1 while `p1` carries the magnitude. A locally built line-unit event (a wheel mouse) has `isContinuous = 0`; a pixel-unit one has 1. Setting phase, momentum and continuous fields round-trips; zeroing `DeltaAxis1`, `PointDeltaAxis1` and `FixedPtDeltaAxis1` reads back 0/0/0.0. An active `.defaultTap` session tap over `scrollWheel` was created from the AX-trusted process (as was a listen-only one); 0 disabled notices. Not observed: a live `isContinuous = 0` event (no wheel mouse connected), Magic Mouse events, Magic Mouse vs trackpad attribution. Conclusions: the wheel-mouse exemption (R12) is `isContinuous == 0`; momentum suppression (R14) needs one bit of memory per gesture because momentum events arrive after the fingers lifted (when `blocksClicks` is already false); "suppress" can be implemented as drop (return nil, as `.drop` does today) or as zeroed deltas passed through (fields are settable in-process), and the two differ in whether apps see a gesture's `began`/`ended` bracket.
- F19 **sourced** (`plans/002-gesture-click-blocking/plan.md` Tradeoffs: "We accept a mask that includes drags and pressure. While blocking is armed, the tap wakes for every drag and pressure change in the session"): the cost model for adding scroll events to the mask is already accepted for drags; scroll events add ~100–250 Hz while scrolling, each a few lock reads.
- F20 **sourced** (`Launcher.swift` `reconcile()`: `hardware.run(active ? connected : [], handMode:, blockClicks: active && granted)`; `Ports.swift` `TrackpadHardware.run` contract): the tap exists iff gestures are active, access is granted and a trackpad runs; "without the Accessibility permission nothing is suppressed and the swipe still works" (R12) holds by the same structure.
- F21 **sourced** (`FrameStream.swift` `DeviceSession.blocking` writer = that device's frame callback, reader = tap thread; `anyTrackpadBlocksClicks()` copies sessions out before reading each flag): the per-trackpad flag the tap reads is `Recognition.blocksClicks`; a swipe-wide block (R13) is that flag staying true, which needs no new channel.

### Persistence

- F22 **probed** (`probes/settings-decode-probe/output.txt`): a plist record saved by today's `Settings` (handMode + `[Gesture: AssignedApp]` with cases 1–4) **fails** to decode into a `Settings` that gained `switcherList: [AssignedApp] = []` under synthesized `Codable` (`keyNotFound "switcherList"`), and `SettingsStore.load()` would then return `Settings()`, silently dropping every assignment. A hand-written `init(from:)` using `decodeIfPresent(…) ?? []` decodes the old record (`handMode=right`, `two=Arc`, `switcherList=0`) and round-trips the new shape (`five=Arc`, two list entries). An old record's `assignments` decode into the enum with a fifth case. Conclusion: `Settings` needs a tolerant decoder for every key added after the first release; `LaunchTuning`'s Debug `init(from:)` (`LaunchTuning.swift` lines 49–75) is the in-repo precedent.
- F23 **sourced** (`Settings.swift`: "Undecodable data loads as `Settings()`, not as a first launch"; `PersistenceTests.undecodableRecordLoadsAsDefaultsNotAsFirstLaunch`): the first-launch fact is the absence of a record; nothing here changes.

### Model, window and rendering

- F24 **sourced** (`Launcher.swift`): one `@MainActor @Observable` model; `fire` is the only path that pulses, fronts, animates and closes the window; `rows` and `prepareLaunchAnimations` are re-derived in `resolveRows()` on start, assignment change and window open; `Window` is `closed | open | heldOpen`; every stored field has one writer. `docs/architecture.md` Shape: "One `@MainActor @Observable` model owns every decision. Platform adapters sense and act behind small ports; the AppKit/SwiftUI shell renders the model's state and forwards user intents."
- F25 **sourced** (`docs/architecture.md` Shape, bullet 4): "Every port has exactly two adapters: the real one in `LauncherPlatform` and an in-memory one in the tests. Concrete types that can be pointed at a temp directory or a throwaway `UserDefaults` suite are not put behind a port, unless they deliver asynchronously." Framework types never cross a port (bullet 3). `LauncherCore` imports Foundation and Observation only (`SourcePolicyTests.coreImportsOnlyFoundationAndObservation`).
- F26 **sourced** (`LaunchOverlay.swift` `makePanel`): the configuration that floats above full-screen apps on every Space without activating, taking focus or receiving clicks: `NSPanel(styleMask: [.borderless, .nonactivatingPanel])`, `isOpaque = false`, clear background, `hasShadow = false`, `ignoresMouseEvents = true`, `level = .screenSaver`, `collectionBehavior = [.canJoinAllSpaces, .fullScreenAuxiliary, .stationary, .ignoresCycle]`, `hidesOnDeactivate = false`, `animationBehavior = .none`, `isReleasedWhenClosed = false`, shown with `orderFrontRegardless()` and never made key; the first window-server window costs ~27 ms, so `init` warms one up. `LaunchFlight.display(for:among:)` picks the display under `NSEvent.mouseLocation` with `NSMouseInRect` (top edge in, bottom edge out) and the nearest display otherwise; Reduce motion is read fresh from `NSWorkspace.shared.accessibilityDisplayShouldReduceMotion`. The launcher panel (`LauncherPanel.swift`) is the Liquid Glass precedent: `NSGlassEffectView` (`.regular`, corner radius 26) inside a rounded `masksToBounds` clip so the shadow follows the rounded edge, `level = .popUpMenu`, `canBecomeKey = true` (the switcher must not copy that: R10 "never take focus").
- F27 **sourced** (`docs/architecture.md` Concurrency): "No timers, no polling, no background loops: every input is a push"; "Animation is Core Animation keyframes … No code of ours runs per frame, and display links are banned." A switcher highlight driven by finger frames is input-driven work (~100 Hz while the fingers move), not a per-display-frame loop; springs and fades at the ends and on dismissal are animations the render server plays. `Observations` loops (`MenuBarShell`) are the existing bridge from model state to AppKit; SwiftUI views observe the `@Observable` model directly (`LauncherView`).
- F28 **sourced** (`LauncherPanel.fitToContent`: `hosting.fittingSize`, x clamped into the visible frame, top edge kept; `LauncherView` `.frame(width: 266).fixedSize(horizontal: true, vertical: true)`; `MenuBarShell.refit()` on window open and when activity or the Accessibility grant changes): the window is sized to its content's fitting size and only its x is clamped; nothing caps its height. R22 (the list scrolls inside the window when it would not fit) needs a height cap derived from the screen's visible frame and a scrolling region whose fitting height stops growing at that cap, plus a refit when the list changes.
- F29 **sourced** (`AppPicker.swift`; `Apps.swift` `InstalledApps.pickerMenu(checking:)`, `PickerItem`; `plans/003-dropdown-recents-performance/plan.md` "App picker, shell and composition root"): the picker is an `NSPopUpButton` whose `NSMenuDelegate.menuNeedsUpdate` rebuilds items from `installedApps.pickerMenu(checking:)` with `cachedIcon(for:)` (never draws on the click path); the menu shape (recent, divider, others, divider, Other…, None) is a pure core function tested through a string projection (`RecentAppsTests.menu`). R18's "Add app…" menu (recent, others, Other…, no None, listed apps checked and disabled) is a second shape of the same data; `PickerItem.app(_, checked:)` has no disabled flag today.
- F30 **sourced** (`LauncherView.swift`, `docs/menubar-window.png`, `assets/*.svg`, `project.yml` `sources: - path: assets includes: ["*.svg"] buildPhase: resources`): the window is one glass card holding the rows (illustration left, picker right), the hand-mode toggle, a divider, the hint or notice, then Quit; illustrations are 48×31 template SVGs (thumb dot at (8,8), finger marks as ringed dots) loaded from `Bundle.main` and mirrored with `scaleEffect(x: -1)` for left hand; the hint interpolates `HandMode.cornerName` and two mark images. New SVGs dropped into `assets/` ship automatically. The repo has no `gesture-5.svg` and no swipe illustration (human-established).
- F31 **sourced** (`MenuBarShell.swift`): the window closes on outside mouse-down (global monitor while open), on resign-key (except the status-button click) via `dismissWindow()`, on Escape and icon click via `closeWindow()`; a fired gesture closes it through the model. `NSApp.activate()` is called only around `NSOpenPanel` in `chooseOtherApp`, after `closeWindow()`, and `openWindow()` follows the chooser.
- F32 **sourced** (`plans/004-launch-icon-animation/plan.md` "The overlay" and `development-logs.md` Plan: "the overlay keeps its own set because the probe found a closed panel staying in `NSApplication.shared.windows`"; "A process's first window-server window costs about 27 ms"): panel lifetime is owned explicitly and warmed up; relevant to R10's "appear as the swipe begins with no perceptible delay" and "gone within 200 ms".

### Human-established facts (from the task brief; not re-probed)

- F33: on the hardware, a thumb anchored plus two fingers sliding produces ordinary two-finger scrolling (horizontal and vertical) and nothing else; no Spaces or page-swipe gesture fires. ## 3. What a test can produce for real, and what needs a fake or a manual check

**Real, in-process, synchronous (LauncherCoreTests):**
- Every recognizer scenario of R1, R3, R6 (travel values), R8, R9, R13's frame-side flag: scripted `TouchFrame`s through `GestureRecognizer.step`, reading the per-frame result. `TouchScript` needs a sideways-move-and-hold primitive (or hand-built `HandFrames`) for swipes, vertical movement, a mid-swipe thumb lift, a mid-swipe third finger and a mid-swipe press.
- The whole app through `World`: in-memory hardware steps the real recognizer and delivers swipe events inline (as `touch` does for gestures today); `RecordingSystemActions` records fronted apps; `InMemoryTrackpads.feedback` records pulses (and can record their kind); the frontmost app is whatever the test's fake answers; the switcher's row, selection and highlight are readable as model state or as a recording fake's calls. R4, R5, R6 (selection per travel), R7 (tick count), R8, R9, R11, R13 (press verdicts via `pressVerdicts`), R17, R18, R19, R20 (list order), R21, R23 (relaunch over the throwaway suite, plus an old-format record) all run here.
- Pure functions: travel → selected index and highlight offset (R6's 12 mm / 6 mm / ends rule); the Add-app menu shape (R18) through the same string projection `RecentAppsTests` uses; the hint copy per hand mode (R24) as a pure value like `HandMode.cornerName`.
- The scroll filter's decisions as a pure table (R12 wheel exemption by `isContinuous`, R13, R14 momentum memory), and in LauncherPlatformTests the parse of synthetic scroll `CGEvent`s built with `CGEvent(scrollWheelEvent2Source:…)` plus `setIntegerValueField` for phase/momentum/continuous (F18), the mask bits, and what "suppress" does to an event (dropped, or zeroed deltas).
- `Settings` decoding of a record saved by today's build (F22) and the round trip of the new shape.
- `AppCatalog` over the World's temp tree for missing/recovered switcher-list apps (R17, R4).

**Needs a fake:** the frontmost app (a port or injected reader; the real one is `NSWorkspace`), the switcher presentation (observable model state rendered by the shell, or a recording adapter), haptic kinds (recorded), the hardware's swipe-event hop (the in-memory adapter delivers inline).

**Manual only:** the panel's look in light and dark, the glass highlight, the spring at the ends, Reduce motion rendering, the 80 pt icons, appearance "with no perceptible delay" and disappearance within 200 ms, full-screen apps and a second display (R10); real scrolling, momentum and a wheel mouse under the tap in Safari (R12–R14); the haptic feel of the tick against the gesture haptic (R7); drag-to-reorder in a non-activating key panel (R20); the window scrolling on a 13" display with 30 apps (R22); the two new SVGs beside the existing ones (R2, R16); the hint and Accessibility hint copy as rendered (R15, R24).

**Open after grounding (design decisions, not missing facts):**
- O1 How the recognizer's states change so a two-finger rest has no time limit (R3) while a tap keeps its 400 ms (plan 002 R2 still requires that a two-finger rest that *lifts* after 400 ms without moving fires nothing: `twoFingersHeldFiveHundredMillisecondsFireNothing`), a swipe survives the anchor lifting (R8, R9) and still ends "nothing further until every non-thumb finger has lifted", and the thumb may re-land as a fresh anchor (R9 "Thumb lands again") with the right `landedAt` for click blocking afterwards. `why.md` adds: name the swipe state's exit conditions explicitly, since a swipe-wide block has no 3 s cap and a stuck state would block clicks and scrolling until the next touch or `run` (plan 002 chose under-blocking as the safe direction everywhere else).
- O2 Whether swipe events carry travel in mm and the main actor maps travel to selection (keeps the 12 mm rule pure and testable in core, and the recognizer ignorant of the row length), or the recognizer is told the row length.
- O3 Delivery mechanism for the swipe stream (F6): rely on observed `Task` ordering, use the documented FIFO dispatch path, or make events self-describing.
- O4 "Suppress" a scroll event as drop or as zeroed deltas (F18), and the exact momentum memory rule (which event's verdict the momentum follows, given the fingers have lifted by the time momentum begins).
- O5 Whether the switcher is model state rendered by `LauncherUI` (like the launcher window) or an effect behind `SystemActions` played by `LauncherPlatform` (like the launch animation), and where the frontmost-app read sits (a `SystemActions` member, or its own port).
- O6 What the switcher does when no frontmost app can be determined (F1 shows one always exists in practice; Finder is always running), and when the frontmost app is Trackpad Launcher itself (F2: the Other… chooser is open).
- O7 How the window caps its height and scrolls the list (F28), and how the Add app… menu reuses the picker machinery with a disabled state (F29).
- O8 The actuation ID for the light tick (F14: 3 weak, 4 medium) and whether `playFeedback` takes a kind or gains a sibling.
- O9 Whether `List`/`ForEach.onMove` drag reordering works inside the non-activating key `LauncherPanel` while the app is inactive (not probed; needs a person dragging). If not, the row needs its own drag mechanism.
- O10 The 5-finger and swipe illustrations do not exist (F30); they are drawn in the implementation in the style of `gesture-4.svg` (48×31, `#232323`, thumb dot r = 4 at (8,8), finger marks r = 4.75 ring + r = 2.75 dot).

Risks carried into the design: F4's "fast for the frontmost icon" rests on two runs; F6's ordering is observed, not documented; F35's unmerged branch touches the same window; the real trackpad's frame rate while fingers are still is not stated in code (frames are known to flow while contacts rest: `ClickBlockingRecognizerTests.expiryIsSeenOnAFrameWhereNothingButTheClockMoved` encodes the assumption, and plan 002 states ~100 Hz while touching); the wheel-mouse exemption rests on a synthetic `isContinuous = 0` event (F18); the tap will wake for every scroll event in the session while armed (F19).

**Plan-text gaps `why.md` found (for Phase D, not for the design):** plan 006's amendments paragraph names plan 002's R1, R4, R6 and R11 but not R9, whose "MUST NOT read, record or change … scrolling" R12–R14 override in substance (the design reads scroll events and their momentum, and changes those of a suppressed scroll); plan 001 R11's bullet "fingers that drag or scroll while the thumb is anchored" MUST NOT fire a gesture survives textually (a swipe is not a tap gesture, so this reads as scoping); `docs/architecture.md` "Privacy and permissions" says Accessibility is used "only to block trackpad clicks during gestures", a cross-cutting sentence this plan changes.
