| # | Fact | Standing |
|---|---|---|
| N1 | By default URLSession sends `User-Agent: <process> (unknown version) CFNetwork/3860.700.1 Darwin/25.6.0` (for an app: its name and build, plus the CFNetwork and **Darwin (macOS) version**) and `Accept-Language: en-US,en;q=0.9` (the user's languages). | N2 | A per-request `User-Agent` and `Accept-Language` replace the defaults (also when set as the configuration's `httpAdditionalHeaders`), and per-request headers are carried across a redirect. | probed: `urlsession-probe.out` (b), (b2), (e) |
| N3 | `timeoutIntervalForRequest` is an idle timer, reset whenever data arrives: a body that stalls fails with `NSURLErrorTimedOut` (-1001) after the interval (3.1 s for 3 s); a body trickling slower than the interval in total but never idle that long completes. | N4 | An ephemeral session "doesn't store caches, credential stores, or any session-related data to disk ... (The default/shared session uses disk caches and shared cookie storage, which R3 forbids.) | sourced: SDK `NSURLSession.h` `ephemeralSessionConfiguration`, `HTTPCookieStorage`, `URLCache` (Xcode 27.1 SDK on this Mac) |

### Replacing and relaunching

| # | Fact | Standing |
|---|---|---|
| R-1 | `FileManager.replaceItemAt` of a bundle-shaped directory on this Mac's data volume (same volume as /Applications): over 1500 replacements and 9.1 M concurrent observations, the destination was **never** missing or half-filled, and afterwards it has the staged directory's inode, with nothing left in the staging folder. *Conclusion*: a single rename-swap; a crash at any instant leaves either whole copy at the destination. | probed: `probes/replace-atomicity.swift` → `.out` |
| R-2 | When **another process** replaces a running app's bundle in place and opens that path, `openApplication(at:)` starts a **new** process from the new bundle, with the default configuration and with `createsNewApplicationInstance = true`; the old process keeps running and gets no reopen. (Plan 021's F6 found the same.) | probed: `probes/relaunch/relaunch.sh` → `.out` |
| R-3 | When the **running app itself** replaces its own bundle and calls `openApplication(at: <its own path>)` with the **default** configuration, LaunchServices answers with the caller's own pid and delivers a **reopen to the old process**; no new process starts. With **`createsNewApplicationInstance = true`** a new process starts from the new bundle (version 2) and the old one keeps running. Today's `ApplicationsInstaller.openInstalledCopy()` uses the default configuration. | probed: `probes/relaunch/self-relaunch.sh` → `.out` (ad-hoc signed probe apps in /tmp) |
| R-4 | *Conclusion from R-3 and E6*: if the old process opens its replaced bundle with `createsNewApplicationInstance = true`, the new process is an opening by hand from /Applications → `.runWithWindow` → it force-stops the old process, waits for its exit, builds its resident and opens its settings window, whose first opening checks again (R9). The old process keeps its gestures until stopped. | conclusion |
| R-5 | No stock command-line tool on this Mac does an atomic directory exchange: `mv` has no exchange/swap option. `/usr/bin/perl` 5.34 runs (a deprecated runtime). `/usr/bin/osascript -l JavaScript` with the ObjC bridge can call Foundation's `replaceItemAtURL:...` and did an atomic swap (inode swap) when run as `/bin/sh -c '/usr/bin/osascript -l JavaScript -e "$1" "$2" "$3"' sh <script> <dest> <staged>`; paths with quotes, spaces and `$(touch pwned)` passed through intact with nothing executed; a **missing** destination crashed osascript (SIGSEGV, non-zero exit). | R-6 | The running process's own bundle path is replaced underneath it: its executable stays mapped from the old inode, but anything it loads lazily from `Bundle.main` afterwards (resources, a plist read) comes from the **new** bundle. | conclusion (from R-1's inode swap and how bundles resolve paths); not probed |

## What a test can produce for real, and what needs a fake or a manual check

**Real in `swift test`:**
- Version parsing and comparison, release-list parsing from JSON fixtures shaped like G3, choosing the offer (pure functions in `LauncherCore`).
- The update's state machine in the model, end to end, with in-memory adapters that hold each completion (check result, download progress/finish/failure, verification result, install outcome) so a test can withhold, deliver late, or deliver after close; synchronous, as `LifecycleWorld` / `World` do today. Quit/close policy through `Lifecycle.shouldEnd` and the Quit intent.
- The request a real URLSession sends: tests are not source-scanned, so a test can run a local HTTP listener on 127.0.0.1 and assert the exact headers, the absent query string and cookie (N1, N2), the stall failure with a short injected timeout (N3), progress and cancellation.
- Unpacking (either V4 format) and the swap in temp folders on the real file system (`BundleFixture`, `ApplicationsInstallerTests` pattern); the admin script run unprivileged through `TestAdministrator` (`PrivilegedInstallTests` pattern), including paths with shell metacharacters.
- Genuineness, negative cases: ad-hoc fixtures, a wrong identifier, a wrong version, a tampered resource. Positive case: only against a real notarised Developer ID app found on the machine (skipped when none, as `CodeSignatureTests` does), with the team read from it at runtime.

**Needs a fake (in-memory adapter):** the network itself (GitHub), LaunchServices relaunch, `forceTerminate`, the admin prompt, the login item.

**Manual only:** a real end-to-end update between two published, notarised releases (needs two GitHub releases); the Accessibility/Screen Recording grants and the login item after an update (O2, O3); the administrator prompt on a standard account; a restart during the swap; Little Snitch / `nettop` view of the request (R3's scenario); the card against the Figma design.

## Open questions

- **O1. The Figma design (node 2143-1845) was not inspected in Phase A:** no Figma tool is available to this session. R5 and the plan's Solution describe the available state (text left, *Update now* right, own rounded group, first group). Measurements, button style, and the downloading/installing/failed states' look are to be read from Figma at implementation time.
- **O2. Does the `SMAppService.mainApp` login item survive an in-place replacement at the same path, and would an unregister/register handover (E9) make macOS show a "login item added" notification on every update?** Not probeable without a Developer ID build and a real login. Plan 021 left the same question open (its F38 / open question 5).
- **O3. Do the Accessibility and Screen Recording grants survive?** V5 supports yes (the designated requirement is version-free); TCC itself is not probed. R10 and the domain model's "later runs never ask" mean a lost grant could not be re-requested.
- **O4. The admin path and R13's restart scenario.** The move's admin script is two renames (E8). R-5 shows an atomic swap is reachable as root through `osascript` JavaScript (stock tool, one call), or through running a trusted executable of our own as root; or the gap can be accepted as plan 021 did. Which, if any, is a design decision.
- **O5. Where and how each release declares its minimum macOS** (G3: no field). Asset name, release body, or a separate manifest asset (a second request, which R3's "only the public list of releases" may forbid).
- **O6. The asset format.** The DMG exists today; installing from it means mounting it. A zip (`ditto`, child process) or an Apple Archive (in-process) of the stapled app both verify (V4). Which the release publishes, and whether the DMG stays the website download, is a design decision.
- **O7. `--as-release-build`.** A development build launched with it reads `.release` (E2) but has no Developer ID team (V2). R2 says a development build makes no network request; how the gate treats this hook is a design decision.
- **O8. The running version's source** (E12: never read today): `Bundle.main` Info.plist read once at start, or the signing information. R-6 says a lazy read after the swap would see the new bundle.
- **O9. Unverified pipeline behaviour** carried from `how.md`: whether `notarytool submit --wait` exits non-zero on "Invalid"; whether actool adds `CFBundleIconName` for `AppIcon.icon`.
- **O10. Logout during an install** relies on the move's unverified logout signals (`why.md` What We Don't Know; plan 021 open question 4).
