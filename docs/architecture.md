# Architecture

The decisions that hold across the whole codebase. Feature-level decisions live in their plan under `plans/` and then in the code.

## Language, platform, toolchain
- Swift 6 language mode with complete strict concurrency, on the Xcode 26 toolchain (macOS 26 SDK). Deployment target macOS 26, universal binary (arm64 + x86_64).
- Build: a local SwiftPM package holds every library and test target, with Sparkle built from its pinned source by one script, its user interface, legacy parts and downloader service left out and its installer launcher service kept (the process that asks for an administrator, so the prompt never blocks the main thread), and vendored in the package as a binary target beside its two signing tools and a manifest of the tag and flags; an xcodegen-generated Xcode project, written from `project.yml`, the one tracked source of the Info.plist, builds only the app bundle (Info.plist, resources, hardened runtime, signing, archiving). `swift test` runs the whole behavioural suite; `xcodebuild` is used only for the bundle. The Debug configuration builds the app under its own bundle identifier, the release's with `.debug` appended, so macOS keeps a Debug build's permission grants, settings and login item apart from the installed release's; the Release configuration, the notarized release and the perf build alike, keeps the release identifier.
- Tests use Swift Testing.

## Shape
- Three `@MainActor @Observable` models own every decision. `Lifecycle` owns the process: what it does when it starts, is opened again or is asked to quit, and moving it into /Applications; it builds `Launcher`, which owns gestures, settings and the settings window, only once the process runs gestures. `Updater` owns every update decision: the login start's check and its retry when a connection returns, the window's check and its dropping, the card, an update's verdict and the order of the hand-over. It exists only in a copy truly signed with a Developer ID that lies in /Applications; only one that can replace its own bundle updates at a login start. `Lifecycle` starts it once the process is resident and ends the process when it asks; `Launcher` reports the settings window's edges through one closure and knows nothing about updates. Sparkle sits behind one port, built on demand for one check or one update and released at its end, and what depends on its private behaviour sits in one type, proven against one pinned version. An update never opens the new version itself: the moment the update is prepared, the old copy leaves a one-shot launchd job and ends, Sparkle installs at that end, and the job opens whichever copy /Applications holds with `--after-update`: silently, or with its settings window when the window was open or the card asked. The bundle never declares `NSSupportsSuddenTermination`, and no code enables sudden termination: a move's opening, and an older version's update card, make the new process a child of the old in LaunchServices, and when a foreground app ends, loginwindow force-quits, 3 s later, every child of it that is a UI element without a visible window and declares sudden termination, which the new version is for its first moments; the opened copy's own declaration decides, so the rule protects even the first update from a version that still declares it. Without the declaration a logout, restart or shutdown reaches the app as the quit event, which `Lifecycle` answers at once. The source-scan test keeps the key out of `project.yml` and the API out of the code. At most one Trackpad Launcher runs gestures: an opening by hand stops every other running copy, Debug or release, and waits for their exit. Platform adapters sense and act behind small ports; the AppKit/SwiftUI shell renders the models' state and forwards user intents. Policy lives in pure functions and value types; the shell stays thin.
- Modules by ownership, not by execution order: `LauncherCore` (domain types, pure policy, ports, the models; imports Foundation and Observation only), `LauncherPlatform` (the real adapters over AppKit, Core Animation, IOKit, CoreGraphics (the window list), CoreServices (FSEvents, MDItem, Apple events), ServiceManagement, Security (the code signature, Authorization, two private translocation functions), Sparkle, built without its user interface (the update check, its download and install, one file; the update archive's expansion, streamed from its file, one more), Network (the path monitor, one file), launchd's job submission (one file), DiskArbitration, the Accessibility element API, two private LaunchServices functions, one private Accessibility function and the private MultitouchSupport framework), `LauncherUI` (the settings window shell, the move dialog and SwiftUI views, plus the window previews it captures with ScreenCaptureKit, a rendered asset like the icons it draws), and the app target (composition root and the app delegate only). `CardContract` and its `card-contract` tool hold a frozen copy of what every shipped update card demands of a release; the release runs them, and the app never links them.
- Framework and wire types never cross a port: `MTTouch`, `CFTypeRef`, `CGEvent`, `CFMachPort`, `UserDefaults` keys, `NSRunningApplication`, `NSImage` stay inside adapters and views. External data is parsed into domain types at the adapter.
- Every port has exactly two adapters: the real one in `LauncherPlatform` and an in-memory one in the tests. Concrete types that can be pointed at a temp directory or a throwaway `UserDefaults` suite are not put behind a port, unless they deliver asynchronously: those sit behind a port so the model's tests stay synchronous.

## Concurrency
- `LauncherCore` and `LauncherPlatform` are nonisolated by default; the model, the ports and the public surface of every real adapter are `@MainActor`. `LauncherUI` and the app target use main-actor default isolation.
- Multitouch frames are recognised on the framework's own thread; only recognised events hop to the main actor: a fired tap, a swap, and the begin, moves and end of a swipe or of a slide up or down that may be a window swipe, in frame order on the main queue and never from a session a later `run` replaced. Nothing about updates runs on that thread or for a frame, in any update state: the source-scan test keeps every update token out of the frame-path files. One thing hops back: the model's answer to a window swipe's start, whether the slide is a window swipe, which only the main actor can tell because it reads the frontmost app's windows. The model gives it while it handles the start; the adapter replies once that call returns, and the frame thread hands the reply to that trackpad's recognizer before its next frame. The recognizer ignores an answer to any other start. Until the answer arrives the slide blocks clicks and scrolling only by the thumb rules, and Dock swipes as any thumb touch does, and the frame thread never waits for it. State shared with that thread lives behind a `Mutex` with one writer.
- Work that would delay a click (folder scans, Spotlight reads, icon drawing) runs off the main actor in explicitly concurrent functions, including inside `LauncherUI`; only its results hop back. The update's signature check is one exception: it runs on the main actor, with the expansion of the downloaded archive into a scratch folder before it and, for a refused update only, the archive's removal after it, all inside Sparkle's download-finished callback, before any installer exists, and once per release; the check itself takes 18 to 31 ms and the expansion a fraction of a second, so that no unchecked update is ever prepared. The first scan and the first icon pass are another: they run, and are waited for, before gestures run and before the settings window can show, so no click can arrive before their results exist. The other exception is `AppIcons.iconDrawingIfMissing(for:)`, which draws a missing icon on the main actor, but only for the closed button showing a row app outside the list that was just picked through Other…. The launch overlay, and the launch bounce, which shares its icons, likewise draw an icon at gesture time only when the off-main pass has not drawn one yet (the app moved, or a sharper display was connected since). The switcher's icons are drawn before any swipe: every running Dock app's in the first icon pass at start, and each newly launched app's off the main actor on the workspace's launch notification, again on an appearance change; a swipe begins by reading the running apps from LaunchServices, a few milliseconds at most, and draws an icon on the main actor only for an app whose pass has not finished yet or that no pass covers (a frontmost menu bar app, from the running app's already-loaded icon). With the swipe setting off nothing is drawn or observed for the switcher. Every slide up or down reads the frontmost app's windows when it starts, and a window swipe raises them, through the Accessibility API on the main actor: synchronous calls into another app, about a millisecond in all, the whole read held to 0.2 s by giving each call what is left of that budget as its messaging timeout, after which that app gets no further raises until it is read again; the window list's first call in the process (about 50 ms) is paid off the main actor at launch. A swipe's start reads the windows of its row's apps away from the main actor, one GCD work item per app rather than the cooperative pool, because a call into an app that does not answer blocks its thread until its budget runs out and must hold up no other read; each read is held to 0.2 s from the swipe's start the same way, no Accessibility element leaves its work item, and only the read's result hops back. Window previews are captured off the main actor inside `LauncherUI`, and only the pictures hop back.
- No timers, no polling, no background loops: every input is a push (frames, cfprefs KVO, IOKit notifications, workspace notifications, the TCC Darwin notification, FSEvents for the app folders, user events, Apple events, the termination of other running copies, the move's install and eject completions, the settings window's edges, Sparkle's answers, a network path change while a failed login check waits, and, only while a launch is watched (its launch bounce shows, or the hide background apps setting waits for its first window), its launch's progress (`openApplication`'s answer, KVO on the launched process, an Accessibility window observer), and, only while a launch bounce shows, pointer moves). This is what keeps idle CPU at zero. Time passes only on Core Animation's clock, with one exception, confined to one owner: the hand-over job's waits, which run after this process has decided to end: first for the old process to end, with no limit, so that a late end still installs and still comes back, then for at most 6 s for the install. Sparkle arms no timer: its schedule is declared off, and no updater object outlives its one check or update. On Core Animation's clock a deadline is an animation on a layer of the effect it belongs to, its completion is the push, and it cannot outlive that effect. A launch watch's deadlines (its cap, its wait after the app finished launching, the interval between its window-list re-reads) are on a zero-size layer of the watch's own, in a one-point window that is never ordered in, made with the first watch and closed with the last; the layer goes when the watch ends, so a bounce-less watch keeps time the same way a bounce does. Two deadlines lie outside both, and neither fires. The lift window: a frame thread stamps its end on the process's monotonic clock (read at receipt, never the frame's own time, which is the driver's clock) and the click tap's thread compares the stamp with that clock when an event arrives; the gate it held open closes on the next frame or event. And a window read's 0.2 s: stamped on the same clock when the read is asked for, carried into each Accessibility call as its messaging timeout, and compared when the read ends, a read that ends late counting as unanswered. The one repeating read is bounded the same way: a watched launch whose app finished launching but whose next window it cannot be told of (no Accessibility, or the app's Accessibility server not answering yet) re-reads the window list every 50 ms on that watch's clock, for at most the 2 s it then waits. The one extra thread is the click tap's run loop, which exists only while click blocking is armed and serves two event taps. One, over presses and their releases, is on for as long as it exists, and only a click wakes it. The other, over drags, pressure, scrolling and the system's gesture events, is turned on by that thread only while some trackpad is in a thumb touch (from a thumb in the anchor corner until its pad is empty) or in its lift window (the 0.5 s after fingers lift under the thumb, in which the system's tap actions are blocked), or while a press, a scroll gesture with its momentum or a Dock swipe is still withheld or altered, and turned off once none is, so ordinary pointing, dragging and scrolling never reach the app. A lift window's end is noticed on the next frame or the next event, never by a timer; a port left on while nothing touches the pad is sent nothing but a mouse's own events (a wheel, a drag), the first of which closes it. A trackpad's frame thread only wakes that thread when what it needs flips, a lift window ending included; no frame thread enables or disables a tap.
- Animation is Core Animation keyframes, which the render server plays. Whatever an animation leaves behind is cleaned up from its completion callback. Two animations never complete, both in the settings window and both removed with their card and never from a completion: the gear (the Accessibility hint's), a repeating rotation the render server plays for as long as its card is in the window, the window closed included; and the update card's arrow, a repeating drift the render server plays while its card is in a window that is on screen with Reduce motion off, removed when the card leaves the window, the window leaves the screen or Reduce motion turns on, and added again on the reverse. No code of ours runs per display frame, and display links are banned along with timers. Code may run per input event while the effect it serves is on screen: the switchers' highlight on trackpad frames, the launch bounce's row on pointer moves.
- Developer tools live in `#if DEBUG` and never ship. Today that is the animation tuner in `LauncherPlatform`: a SwiftUI window over `LaunchTuning`, whose defaults are the shipped launch animation, launch bounce, pick animation and update card arrow drift. The settings window's pick animation and arrow drift read the tuner through one Debug-only hook on the shell that the composition root wires; Release builds never set it. A Debug build launched with `-PreviewUpdateCard YES` shows the update card without an update, since only a Developer ID copy checks for one.

## Privacy and permissions
- The app may ask for two permissions, both optional. Accessibility, asked for on first launch, is used only to block trackpad clicks, suppress trackpad scrolling, block the system's desktop and Mission Control swipes during gestures and block the system's tap actions (the click Tap to click makes, Look up, Smart zoom) under the anchored thumb and in the half second after fingers lift under the thumb, to list the frontmost app's windows when two fingers start sliding up or down under the thumb, to raise and restore them during a window swipe, to count the windows of the apps in the switcher's row when a swipe begins, and to notice the first window of an app a gesture is launching, while its launch is watched (its launch bounce shows, or the hide background apps setting waits for that window). Screen Recording, asked for only from the screen recording hint's button and never by a gesture, is used only to take one picture of each listed visible window when a window swipe begins; the pictures are kept in memory and dropped when the window swipe ends, never streamed, recorded, encoded or written to a file. The app never asks for Input Monitoring or any other permission and never reads keyboard events. It reads the pointer's position only while a launch bounce shows, to keep the icon above it, through NSEvent monitors that exist only then; it keeps nothing it reads. Without Accessibility everything works except click blocking, scroll suppression, Dock swipe blocking, tap-action blocking, switching windows and window stacks, so with Tap to click or Look up: Tap with three fingers on, a gesture also clicks or looks up; without Screen Recording the window switcher shows app icons instead of previews. Hiding background apps (the setting's hide of every other Dock app, and the app's own hide for its settings window) is the public, prompt-free hide of a running app and needs no permission. The permission checks and their TCC push, screen capture, the event taps, the scroll-event API and the hiding of apps are each confined to one file by the source-scan test; the Accessibility element API with the window list to two (the switchers' window reads and the launch watch); pointer-move events to the launch bounce's overlay (and the click tap, which only rewrites to one); the NSEvent monitors to the launch bounce's overlay.
- Trackpad touches come from `MultitouchSupport.framework` via `dlopen` (no link flags, no entitlements, no permission); it is Apple-signed, so the hardened runtime needs no library-validation exception. The ⌘-Tab order comes from two private LaunchServices functions resolved with `dlsym` from the LaunchServices already loaded (no link flag, no permission), confined to one adapter file by the source-scan test; when either is missing, the order falls back to the app in front at launch and the activations observed since, then launch order. A window's number comes from the private `_AXUIElementGetWindow`, resolved the same way and confined to the window adapter's file; when it is missing, windows are matched to the window list by their frames, and by their titles where the list names windows, and a window that matches none is not listed.
- No network code of our own. Trackpad Launcher makes no network calls but one kind: a copy signed with a Developer ID in /Applications checks a public update list on GitHub at each login start, if it can write to its own bundle, and each time its settings window opens, and downloads a new version from GitHub releases at a login start or when the user presses *Update now*, which reads the list once more first, through Sparkle, confined to one file: a fixed address with no query string of ours, fixed headers that name neither the user, the Mac nor any version, cookies refused and nothing cached. No logging of any kind in our code (`print`, `NSLog`, `os_log`, `Logger`); Sparkle writes to the local unified log, with no off switch, and sends nothing. No files written other than:
  - settings in `UserDefaults`;
  - the app's own bundle copied into /Applications when the user chooses *Move to Applications*;
  - Sparkle's own: its update cache under `~/Library/Caches/<bundle id>/org.sparkle-project.Sparkle/`, where a download sits at `PersistentDownloads/<random>/<host name> <build>/<file>` and a refused one is removed, its keys in the app's defaults domain, and an empty cookie jar under `~/Library/HTTPStorages`;
  - a scratch folder the update's signature check expands the downloaded archive into, removed inside the same call.

  The unprivileged file operations of the move are confined to one file. The administrator's, one atomic exchange, are confined to the one script that runs them, in one more file. A source-scan test in `LauncherCoreTests` fails the build on any banned API; add to its list rather than adding prose.

## Distribution
- Direct download only, as a disk image: the app and the image are each signed with Developer ID, notarized with `notarytool` and stapled; hardened runtime, no entitlements. One command builds it from the repository. Never sign with `--deep`; the main executable is signed last, and the export re-signs Sparkle's nested helpers.
- Releases are GitHub releases on the public repository, tagged `v<version>`, each carrying the disk image and `TrackpadLauncher-<version>-macOS-<minimum>.aar`, an Apple Archive of the stapled app. That asset name, the one bundle in it, `TrackpadLauncher.app`, and the repository's path are a contract with every shipped version's update card, and every release runs `card-contract` on the archive to keep it. The same archive is Sparkle's download, signed with the update key by the vendored `sign_update`, whose private half never enters the repository and cannot be rotated. `appcast.xml`, committed at the repository's root and served by `raw.githubusercontent.com`, is the update list, a contract with every automatic copy; only the release command writes it, and each release adds an item and keeps the older ones. The disk image ships the bundle as `Trackpad Launcher.app`, because Finder, the Dock and Spotlight show a bundle's file name, never its `CFBundleDisplayName`; an update goes over the installed copy, whatever it is named, so copies installed as `TrackpadLauncher.app` keep that name. The release command, `Scripts/release.sh patch` (or `minor`, `major`; alone, it releases the version already set), releases main: it checks every credential, the update key included, and that main is clean and equal to origin's, runs the tests, raises the version and the build number, builds, notarises and checks, and only then pushes the version commit and publishes the release, after it has uploaded both assets, and last commits the feed, so the feed never names an asset that does not exist yet; a failure before the push undoes the version commit, and a rejected push of the feed undoes the local feed commit, so main still equals origin's and `--feed-only <version>` finishes the release. A feed that is byte-identical to the one committed publishes nothing and succeeds. A release's version is above every earlier one's, and so is its build number, which is what Sparkle compares.
