# Domain model

The glossary for Trackpad Launcher. Use these words, with these meanings, everywhere: docs, plans, code, UI.

## Trackpad Launcher
The product. A macOS background app that brings apps to the front with trackpad gestures. It has no menu bar icon; it shows in the Dock and in ⌘-Tab only while its settings window is open, minimised or hidden included. At most one Trackpad Launcher recognises gestures at any moment.

## Login start
Trackpad Launcher started by macOS at login, while starting at login is on. A login start is silent wherever the copy lies: no window, no Dock icon, no dialog and no permission prompt, and the app in front stays in front; gestures work from that moment. It never does the first run's work. A window that was open at logout does not come back. A login start of a copy that can replace its own bundle makes an *update check* and, finding a *newer version*, a *login update*. For the hand tests, a release copy started with `--at-login` reads as a login start.

## Opened by hand
Any other start or opening of Trackpad Launcher: from Spotlight, Finder, Launchpad, the Dock or Xcode, by a move finishing, or by an older version's update card opening the new version. A *hand-over* is not an opening by hand, though one that brings the settings window opens it the same way and makes no update check. Opened by hand from inside /Applications, at any depth, or as a development build, it stops every other running Trackpad Launcher (another build, Debug or release, a copy from another place, the menu bar version) and then runs with its settings window open; opening the running copy again brings that same window to the front, restored if minimised. A release build opened by hand anywhere else shows only the move dialog.

## First run
The first opening by hand on a Mac that holds no saved Trackpad Launcher settings. It turns starting at login on when the copy is inside /Applications, asks for the Accessibility permission when it is missing, and opens the settings window. Later runs never ask for the permission; the Accessibility hint shows instead.

## Starting at login
Whether macOS starts Trackpad Launcher at login, as *System Settings → General → Login Items* shows it. The first run from /Applications turns it on. *Quit Trackpad Launcher* turns it off when it is on, and the next opening by hand turns it back on only when that Quit turned it off. Trackpad Launcher never turns back on what the user turned off in Login Items, whatever happens. A development build outside /Applications never changes it. Trackpad Launcher never relaunches itself after a crash or a force quit; only a *hand-over* opens it, once, after an update.

## Quit Trackpad Launcher
The red button at the end of the settings window, the only control of the app's own that stops it: at once, with no confirmation, the window and the Dock icon go and no gesture is recognised until it is opened again. It turns starting at login off. Every other way to quit, *Close Settings* (⌘Q) in the app menu and *Quit* in the Dock icon's menu, only closes the settings window. It works at once in any update state: a download dies with the app, nothing restarts it, and the app stays stopped until it is opened. Logging out, restarting and shutting down end Trackpad Launcher without asking and with no delay from an update.

## Move dialog
The dialog a release build opened by hand outside /Applications shows before anything else: Trackpad Launcher needs to be in the Applications folder, with *Move to Applications* (the default) and *Quit*. It shows in front of the app that was in front, with the keyboard focus. ~/Applications counts as outside. Until it is answered, the copy recognises no gesture, asks for no permission, does not register for login and opens no settings window; a copy already running elsewhere keeps its gestures. *Quit*, or cancelling the administrator prompt, stops it with nothing changed. *Move to Applications* puts the copy in /Applications, replacing and stopping any copy there whatever its version, asking for an administrator's name and password when the account cannot write there; it keeps every setting and starting at login as it was, removes the opened copy where it can (a copy on a disk image stays, and the disk image is ejected unless a file on it is in use), and opens the installed copy. A login start never shows it.

## Development build
A build not signed with a Developer ID, such as a Debug build run from Xcode or the performance build. It never shows the move dialog and runs where it was built; opened by hand, it stops any other running Trackpad Launcher. Outside /Applications it never changes starting at login. It never makes an update check, wherever it lies, even when started with the hand-testing argument that makes it read as a release elsewhere.

## Debug build
A development build of the Debug configuration, as Xcode runs it. Its bundle identifier is the release's with `.debug` appended, `com.domasgru.TrackpadLauncherApp.debug`, so macOS keeps its permission grants, saved settings and starting at login apart from the installed release's: System Settings lists it as its own *Trackpad Launcher*, and allowing one never allows or refuses the other. To the single-instance rule it is the same app: opened by hand it stops a running release copy, and the installed release opened by hand stops it. The performance build is a development build of the Release configuration and keeps the release's identifier, `com.domasgru.TrackpadLauncherApp`.

## Update check
The one kind of request Trackpad Launcher makes on its own: a read of the public update list on GitHub. A copy signed with a Developer ID in /Applications makes it at two moments only: at a login start, if it can write to its own bundle, and each time its settings window goes from closed to open; *Update now* reads the list once more before its download. Nothing runs on a schedule, and a *hand-over*'s start makes no check, window or not. Restoring a minimised or hidden window or bringing it to the front checks nothing; a check still running when the window closes is dropped, and every opening starts without the *update card*. A development build, a copy outside /Applications and a copy showing the move dialog never check. Every request, the download included, is the same on every Mac and every version: a fixed address with no query string of ours, fixed headers that name neither the user, the Mac nor any version, and no cookie. No system profile, setting or usage data is sent. A check that fails is silent; a login start's check that fails for lack of a connection runs again each time a connection arrives, until a check completes.

## Newer version
A published full release in the update list, neither a draft nor a pre-release, that:
- has a higher version than the running one, compared by build number, which rises with every release;
- declares a minimum macOS that this Mac meets.

When several are newer, the highest is taken. Trackpad Launcher never installs the same version or an older one.

## Login update
What a login start does when its *update check* finds a *newer version*: it downloads it and installs it the moment the download is prepared, waiting for nothing: not the trackpad, a gesture or the settings window. Gestures may stop for up to 10 seconds. Nothing shows. It installs only when it is genuine: signed with the publisher's update key, and signed with the same Developer ID and bundle identifier as the running copy, and notarised. Otherwise, or when the download fails, nothing installs, nothing shows, and nothing tries again before the next login start or the *update card*. Opening the settings window during a login update makes no check and shows no card; the update carries on, and the *hand-over* then opens the new version with its settings window. A copy that cannot write to its own bundle makes no login update: it updates from the card. The update adds nothing to trackpad use: no update code runs for a trackpad frame, in any update state.

At every moment /Applications holds either the whole old version or the whole new one. Every setting, starting at login and the permissions carry over, with no prompt and no first run.

## Update card
The first group of the settings window while the current opening's check has found a *newer version*: *Update available* above an *Update now* button, with a large tray-and-arrow picture clipped at the card's right side and a thin border. Every opening of the window starts without it, and it never shows for a failed check, with no error either. It is not dismissable and shows no version and no release notes. Its arrow lifts a point, drops 4 points quickly, springs back past its place by a fraction of a point and settles into it, then rests, about every 2 seconds, while the tray stays still; the motion stops while the window is closed, and with the system's Reduce motion setting on the arrow stands still. *Update now* greys the button out as *Updating…*, downloads the version and installs it the moment the download is prepared, with no progress bar and no cancel, then the *hand-over* opens the new version with its settings window; closing and reopening the window meanwhile shows the card the same way and checks nothing. A copy that cannot write to its own bundle asks for an administrator's name and password after the download. A download or install that fails, or a cancelled prompt, returns the card to *Update available* with no error, and the running version keeps working; an install that fails after the old version stopped brings a working copy back within 10 seconds, with its settings window. Only a genuine update installs, as for a *login update*.

## Hand-over
How a *login update* or the *update card* replaces the running copy: the moment the update is prepared, the old copy leaves a one-shot job with the system and ends, and the update installs at that end. Once the install has finished, or within a few seconds if it failed, the job opens whichever whole copy /Applications holds. After a login update whose settings window was closed, the opened copy starts silently: no window, no Dock icon, no dialog and no permission prompt, and the keyboard focus stays in the user's app. After a login update whose window was open at that moment, and always after *Update now*, it opens with its settings window, as an opening by hand would. Either way it stops any other copy, makes no update check of its own, and gestures work again within 10 seconds. Only a prepared update starts a hand-over, so a Quit, a logout or a crash never does, and nothing restarts the app after them.

## Gesture
One of the five tap gestures: the thumb anchored in the anchor corner, plus a tap with one, two, three, four or five fingers. Gestures are named by finger count: *1-finger gesture* … *5-finger gesture*. The swipe and the swap are the other ways to reach an app, and the window swipe reaches another window of the frontmost app; none of them is a gesture in this sense.

## Anchor corner
The corner of the trackpad where the thumb rests to arm a gesture, or taps to swap apps: the zone 20% of the width from the thumb corner's side edge and 25% of the height from its top or bottom edge, whichever the thumb corner is. A fixed zone; the user chooses the corner, never its size. A thumb that anchored stays anchored until it moves more than 2 mm outside the zone.

## Anchored thumb
A finger resting inside the anchor corner. While a thumb is anchored, the trackpad is in *launcher mode*: taps with the other fingers are gestures. Landing order matters: a thumb that lands under fingers already resting is not anchored while it taps (see *Thumb tap*); one that stays down past the tap window is anchored once the fingers lift.

## Thumb tap
A contact that lands inside the anchor corner, does not drag more than 3 mm, and lifts within the tap window (400 ms). Each landing is judged on its own: a thumb that lifts and lands again is a new thumb tap. Under two resting fingers it fires a swap; otherwise it is only an anchored thumb that lifted. A thumb that lands under resting fingers and stays down longer than the tap window never swaps and is an anchored thumb once the fingers lift. A press during the thumb tap, withheld or delivered, is part of it: unlike a tap, a thumb tap is never cancelled by a click.

## Edge contact
A contact that lands where the side of a palm rests beside the pad. With a top thumb corner: closer than 3 mm to the bottom edge, anywhere along its length, or closer than 3 mm to the *hand-side edge*, the side edge opposite the thumb corner, and more than 40% of the trackpad's height down from the top. With a bottom thumb corner: closer than 3 mm to the bottom edge and outside the anchor corner; no side edge is in the band, since the heel of the hand then rests below the trackpad, and a contact landing inside the anchor corner is a thumb however close to the bottom edge. The 40% line is a share of the height, like the anchor corner's size, so the band sits at the same place on every trackpad size; the 3 mm width is the same everywhere. A contact landing anywhere else near an edge, the top edge, the edge on the thumb corner's side, or the upper part of the hand-side edge, is a finger like any other. An edge contact is ignored for as long as it stays down: it neither starts nor joins a tap, a swipe or a swap, and it is not another contact for arming, click blocking or Dock swipe blocking. A finger that lands farther in and slides into the band stays a finger; a contact that lifts and lands again is judged by its new landing point.

## Tap
Fingers that touch down and lift again within a short window, without dragging. A gesture fires once per tap, when the fingers lift. The *finger count* of a tap is the number of fingers that touched during the tap, not counting the anchored thumb or any edge contact. Two fingers that slide sideways more than 3 mm under the anchored thumb are a swipe, and two that slide up or down more than 3 mm a window swipe whenever there is one (see *Window swipe*); either way they are not a tap. Two fingers that rest longer than the window fire nothing but may still become either. Under the anchored thumb a tap is the gesture alone: the click, Look up or Smart zoom macOS would make for it is a tap action and is blocked (see *Tap action*).

## Swipe
Two fingers sliding left or right, started under an anchored thumb while the swipe setting is on: the thumb anchored first, exactly two fingers landed, and one of them moved more than 3 mm, more sideways than up or down, with no time limit. A slide's direction is decided once, by that first movement past 3 mm, and holds until both fingers lift: a swipe never turns into a window swipe, nor a window swipe into a swipe, and a slide up or down that is no window swipe never becomes a swipe. The thumb only starts the swipe; afterwards it may stay, lift, leave the corner or land again, and nothing changes. A swipe ends when both fingers have lifted; a finger that briefly loses contact and lands again rejoins it. It is cancelled when a third finger lands outside the anchor corner while both are down, or a click reaches apps. Clicks and scrolling stay blocked for the whole of a swipe, whether or not a switcher shows. Nothing further happens until every non-thumb finger has lifted.

## Switcher
The on-screen row shown during a swipe: a Liquid Glass panel centred on the pointer's display, holding one row of at most 10 icons, the frontmost app at the left end followed by the 9 most recently used other running apps that no gesture is assigned to, in their order, a glass highlight that follows the fingers, and the selected icon drawn slightly larger, inside the highlight. No name is shown: the icons say which app is selected. An app with two or more windows shows its *window stack*, the frontmost app included, whether or not the window swipe setting is on; the row never waits for it. A running app that any of the five gestures is assigned to is left out, by its bundle identifier (every running copy of that bundle, and whether or not the assignment is missing), so its slot goes to the next most recently used app without a gesture; only the frontmost app is shown whatever its gesture. The assignments in place when the swipe begins decide the row; there is no setting for this. Icons are 80 pt, 20 pt apart, and the row sits 22 pt inside the panel on every side, measured to the highlight: 22 pt above and below it, 22 pt from the left edge when it is on the first icon and 22 pt from the right edge when it is on the last, so the panel is 22 pt + the highlight + 22 pt tall; when that row would not fit the display, the icons, the gaps and the highlight shrink by one factor so the whole row fits in one row, and the 22 pt stays on every side. The highlight moves one icon for every 100 points the cursor would travel for the same finger movement, with macOS's own pointer acceleration at the user's tracking speed, whatever the icons' size on screen. The selection starts on the frontmost app; sliding right moves it to apps used longer ago and sliding left back towards the frontmost app, whatever the thumb corner. The selected icon is the nearest one, so the selection changes halfway to the next icon. The ends are hard stops with a small rubber band that adds no dead zone: the moment the fingers turn back, travel past the end is forgotten and the next icon is the usual half icon away. The row is fixed when the swipe begins: an app that launches during the swipe is not in it, and one that quits stays in it. Lifting brings the selected app to the front with the gesture haptic; lifting on the frontmost app, or on an app that has quit, does nothing and is silent. It never takes focus, and shows nothing when there is nothing to switch to, as when every other running app has a gesture: the swipe then still runs its course, blocking clicks and scrolling until the fingers lift.

## Running apps
The apps macOS's ⌘-Tab shows, in its order: every running app that appears in the Dock, whether hidden, minimised, windowless, on another Space or in full screen, most recently activated first; never a menu bar app. Trackpad Launcher is one of them, in its ⌘-Tab place, exactly while its Dock icon shows: while its settings window is open, minimised or hidden included. Read from LaunchServices at the moment a swipe begins and again when it ends, and at each thumb tap that may swap, and when a launched app's window shows while the hide background apps setting waits for it; the model keeps none of it beyond the last swap of the latest swap series, which is replaced when the next series starts. Should macOS stop revealing the order, the app in front when Trackpad Launcher started and the apps activated since come first, most recent first, and the rest follow in the order they launched.

## Swipe setting
One global setting, on by default, shown as the *Switch recent* switch in the settings window's switcher section. While it is off there is no swipe: two fingers sliding sideways under an anchored thumb are not a swipe, no switcher appears, the slide scrolls once the blocking window has passed, and only the tap rules block clicks and scrolling (the blocking window); Dock swipe blocking holds as it always does, since the slide lies inside a thumb touch. Taps, swaps and the window swipe are unchanged: a slide up or down follows the window swipe setting. A change applies to the next swipe and is saved at once, so it survives a quit, a force-quit or a Mac restart.

## Swap
Bringing to front the app used most recently before the frontmost app, like a quick ⌘-Tab, with nothing on screen. Fired by a thumb tap while exactly two fingers rest outside the anchor corner (edge contacts aside), both landed before the thumb, however shortly, whether or not they are moving or have scrolled, while the swap setting is on and gestures are active. The target is the first of the running apps, in ⌘-Tab order, that is not the frontmost app, whether or not a gesture is assigned to it; with no frontmost app, the most recently used running app. It fires when the thumb lifts: the gesture haptic and bring to front, never the launch animation; an open settings window stays open. With nothing to swap to it is silent. The order is read afresh at each thumb tap; while the last swap's app is still coming to the front (the read still shows the app that swap started from, and the app it brought to front is still running), that app counts as the frontmost app, so rapid taps alternate. Thumb first, then fingers, is a gesture or a swipe, never a swap. Not a gesture in the glossary's sense.

## Swap series
The swaps made while the same two fingers stay down: from the first thumb tap that fires under them until no finger rests outside the anchor corner. A series finger that lifts rejoins if it lands again while the other is still down. The fingers may move freely. The series stops swapping, but keeps blocking, once a third finger lands outside the anchor corner; it ends when no finger rests outside the anchor corner. Clicks, scrolling and the system's trackpad swipes stay blocked for the whole series, as during a swipe. The model remembers only the last swap made, to target the next one while that swap's app is still coming to the front; that memory is replaced when the next series starts. Its fingers have rested past the tap action hold limit by the time they lift, so no lift window opens for them; macOS makes no tap action for a swap.

## Swap setting
One global setting, on by default, shown as the *Toggle recent* switch in the settings window's switcher section, below the window swipe setting's switch. While it is off there is no swap and no swap series: a thumb that lands under resting fingers is an anchored thumb that waits for them to lift, as before the swap existed, and only the thumb rules block. Independent of the swipe and window swipe settings. A change applies to the next thumb tap and is saved at once, so it survives a quit, a force-quit or a Mac restart. Upgrading from a version without the setting leaves it on and changes no other setting.

## Window swipe
Two fingers sliding up or down, started under an anchored thumb while the window swipe setting is on: the thumb anchored first, exactly two fingers landed, and one of them moved more than 3 mm, more up or down than sideways, with no time limit. It exists whenever the frontmost app's windows are known when the slide's direction is decided, whatever their number: Trackpad Launcher has the Accessibility permission, without which no window can be read, there is a frontmost app, and that app reports its windows within 0.2 s. Otherwise the slide is no window swipe: nothing shows, nothing pulses, and it behaves exactly as with the window swipe setting off, scrolling once the blocking window has passed and never becoming a swipe. A window swipe shows the window switcher: rows to move between the frontmost app's windows when it has two or more, and the *no-windows card* when it has zero or one, a full-screen front window counting as one. Everything else is as for a swipe: the direction is decided once, the thumb only starts it, it ends when both fingers have lifted, a finger that briefly loses contact and lands again rejoins it, and it is cancelled when a third finger lands outside the anchor corner while both are down, or a click reaches apps; a cancelled window swipe leaves the window in front as it is, silently. Clicks, scrolling and the system's trackpad swipes stay blocked for the whole of it. Not a gesture in the glossary's sense.

## Window switcher
The on-screen list shown on every window swipe: a Liquid Glass panel in the top-left corner of the pointer's display, just below the menu bar, holding one column of 2 to 10 rows, or the no-windows card in their place: the frontmost app's windows as the window swipe begins, in the app's *window order*. With more than ten, the ten listed are the front window, the other visible windows front to back, then the minimised windows; with more than ten the rows may therefore shift between window swipes. The panel is 360 pt wide, whatever its titles. Each row shows a preview of its window, 60 pt tall, at most 120 pt wide, as it looked when the window swipe began, and the window's title, reworded by the app's title rule when it has one and otherwise exactly as the app gives it, on one line beside the preview; a title that does not fit is cut short at the end with an ellipsis, never wrapped; a window with no title reads as the app's name followed by " — Window N", N its row, whatever the app's title rule. A row whose preview is not ready yet is empty, and the preview fades in as soon as it is; a row shows the app's icon in place of the preview when its window could not be captured, without the Screen Recording permission, and always for a minimised window, which is also dimmed and badged "Minimised". A glass highlight marks the selected row. The selection starts on the front window's row, or on the first row when every listed window is minimised, and moves one row for every 100 points the cursor would travel for the same finger movement, sliding down to the next row and up back towards the first, whatever the thumb corner, with the switcher's nearest-row choice, hard stops and rubber band. Each time it lands on a visible window, that window comes to the front with the keyboard focus, behind the window switcher; a minimised window is not restored while sliding. Lifting leaves the selected window in front with the keyboard focus, restoring it if it is minimised, and orders the windows: the selected window, then the front window, then the others as before; the gesture haptic plays when the window in front differs from the front window or a minimised window was restored, and otherwise the lift is silent. The lift orders the windows on screen, never the window order. The list is fixed when the window swipe begins: a window that opens during it is not added, and one that closes stays listed; lifting on a closed window leaves the windows as they are. A full-screen front window counts as the app's only window, so the window switcher then shows the no-windows card. When the column would not fit the display, the rows and the panel's width shrink by one factor, and titles are cut short against the narrower width. It never takes focus or receives clicks.

## Window
One of an app's normal document or app windows on the current Space, or one of its minimised windows. Panels, palettes, popovers, sheets, toolbars and other floating helpers are not windows in this sense, nor are the app's windows on other Spaces or its full-screen windows other than the front window. A hidden app's document windows count as its windows, since they show when it is shown again.

## Window order
The order in which the window switcher lists an app's windows, one per app. The first window swipe into the app sets it as the windows stood then: the window in front, the other visible windows front to back, then the minimised windows in the order the app lists them. Afterwards only three things change it: a window that opens joins it at its end, a window that closes leaves it, and the app quitting or Trackpad Launcher stopping forgets it. Bringing a window forward in any way (a lift, a click, ⌘`, the Window menu, Mission Control, the Dock), minimising, restoring and hiding change nothing. A window on another Space is not listed but keeps its place, and is listed there again once it is back on the current Space. It is never saved.

## Window stack
An app's icon in the switcher with smaller copies of it behind, peeking out above it, one copy per further window, four icons at most, for an app with two or more windows counted as the window switcher would list them. The front icon sits and sizes as a lone icon does, so the row, the highlight and the panel keep their sizes; the copies grow with the selected icon and shrink with the row. An app shows its icon alone until its count is known; each count is read when the swipe begins, holds for the whole swipe, and an app that does not report its windows within 0.2 s shows its icon alone throughout. Without the Accessibility permission every app shows its icon alone. A stack rises out from behind its icon once per swipe, as soon as its count is known, the nearer copy first, over about 0.3 s; with the system's Reduce motion setting on it shows in place.

## No-windows card
The window switcher's single card in place of its rows when the frontmost app has zero or one window: the app's icon on the left, where a row's preview sits, a bold first line and a regular message. With one window (a full-screen front window included) it reads "No other windows" and "‹App› has no other windows on this desktop."; with none, "No open windows" and "‹App› has no windows on this desktop.". It shows no preview. It follows the fingers up or down a few points, never more than 6 pt from rest, turning at once when they turn, with no haptic, and settles back as the window switcher goes; with Reduce motion on it stays still. Lifting on it, or cancelling it, changes nothing and is silent: no window moves and, with the hide background apps setting on, nothing hides.

## Front window
The frontmost app's window in front when a window swipe begins, on whichever row the window order puts it; the selection starts on its row. There is none when every window of the app is minimised: the selection then starts on the first row, and lifting on any row restores that window with the gesture haptic.

## Title rule
A built-in rewording of a window's title for the window switcher, keyed by the app's bundle identifier: every window of that app, visible or minimised, shows its title reworded, and an app without a rule shows its titles exactly as it gives them. A rule rewords only a title the app gives, never the untitled fallback. The rules are one table in the code, with no setting; adding an app is one entry. Today one rule, for VS Code (`com.microsoft.VSCode`) and VS Code Insiders (`com.microsoft.VSCodeInsiders`): the title *leads with the project*. VS Code titles the file first and the project second, `main.swift — trackpad-launcher`; the rule swaps the first two parts split by " — " (space, em dash, space), keeps every later part in its order after them, and changes no part's text, so `main.swift — trackpad-launcher — Work` reads `trackpad-launcher — main.swift — Work`, `● main.swift — trackpad-launcher` reads `trackpad-launcher — ● main.swift`, and a title with no separator is unchanged.

## Window swipe setting
One global setting, off by default, shown as the *Switch windows* switch in the settings window's switcher section, below the swipe setting's switch. While it is off there is no window swipe: two fingers sliding up or down under an anchored thumb are not a window swipe, no window switcher appears, and the slide scrolls once the blocking window has passed, exactly as before the window swipe existed. Independent of the swipe and swap settings. A change applies to the next slide and is saved at once, so it survives a quit, a force-quit or a Mac restart. Upgrading from a version without the setting leaves it off and changes no other setting; upgrading from one with it keeps the saved choice.

## Frontmost app
The active app at the moment a swipe or a window swipe begins or a thumb tap lifts. While its settings window is in front, that is Trackpad Launcher itself, like any app: first in the switcher's row and selected, a lift on it does nothing, and a swap goes to the app used before it. A slide up or down over it shows the no-windows card ("Trackpad Launcher has no other windows on this desktop."), since the settings window is its only window. Trackpad Launcher active without its Dock icon, as behind the move dialog or a developer tool, is never the frontmost app: the frontmost app is then the app that was in front before it, read as the most recently used running app. It sits at the left end of the switcher's row and the selection starts on it, so the user can stay where they are; it is there even when ⌘-Tab would not show it, such as a menu bar app with a window in front, and even when a gesture is assigned to it. When there is none, the row is the running apps without a gesture alone, the selection starts on the most recently used one, and lifting on any app, that one included, brings it to the front; a swap brings the most recently used one to the front; and a slide up or down is no window swipe. The window switcher lists the frontmost app's windows.

## Thumb corner
The corner of the trackpad the thumb anchors in: *Top left* (the default), *Top right*, *Bottom left* or *Bottom right*, chosen from the *Thumb corner* pop-up in the settings window, which lists them in that order and shows the current one. One global setting. A change applies to the next thumb that lands and is saved at once, so it survives a quit, a force-quit or a Mac restart; a thumb already down when the choice changes is judged afresh, as after any settings change: it anchors only if it rests in the new corner. Every gesture, the swipe, the window swipe and the swap work the same from every corner, with the same blocking and the same haptics, and sliding right still reaches older apps and sliding down the next window. Versions before the bottom corners offered *Left thumb* and *Right thumb*, which load as *Top left* and *Top right*; the choice is saved so that such a version, installed over this one, reads the side and keeps every other setting, anchoring the thumb in the top corner on that side.

## Hide background apps setting
One global setting, off by default, shown as the *Hide background apps* switch in the settings window's thumb corner group, directly below the thumb corner row. While it is on, every action that brings an app or a window to the front, a tap on a running app (the app already in front included), a swipe lift, a swap, and a window swipe lift that leaves a different window in front, also hides every other running app with a Dock icon, as Hide Others (⌘⌥H) does: on every display and Space, full-screen apps and Finder included (the Desktop's icons stay), the settings window included unless Trackpad Launcher is the frontmost app; menu bar apps stay as they are, and the frontmost app's own windows stay as the action left them. Nothing hides until the app brought forward is in front: active and, if it was hidden, shown again, because macOS activates a hidden app before it shows it and a hide in that gap sends the front to a third app. So the ⌘-Tab order keeps the app the user came from next, and a swap series alternates as before. A gesture that follows replaces the wait and hides everything the earlier one had not. Whatever still shows is hidden again within about half a second, while the app stays in front. An app that does not come to the front within about 3 seconds hides nothing. A silent action hides nothing. A gesture that launches its app hides the others only when the launch watch sees the app's first window, and only if the app is the frontmost app at that moment; a launch that fails, shows no window within the watch's limits, or whose user went to another app meanwhile hides nothing, and a repeated gesture for a launching app takes the switch's value then. Hiding needs no permission. Hidden apps stay in the switcher and the swap in their place, and bringing one to the front shows it. Flipping the switch hides and shows nothing: it applies to the next action and is saved at once, so it survives a quit, a force-quit or a Mac restart. Upgrading from a version without the setting leaves it off and changes no other setting; a downgrade ignores it.

## Assignment
The app chosen for a gesture, identified by its bundle identifier, not its location. A gesture is *assigned* or *unassigned*. An assignment is *missing* when no copy of the app exists outside the Trash; it recovers by itself when a copy exists again. An assigned app is left out of the switcher's row, missing or not, unless it is the frontmost app; the swap still reaches it.

## Target app
The app assigned to the gesture that just fired.

## Bring to front
What a gesture does to its target app: launch it if it is not running; otherwise unhide, restore minimised windows or open a new window as needed, and make it the active app. A hidden app is brought to front like any other: it shows again. A gesture that launches its app shows the launch bounce while the app starts up, and is followed by a launch watch, as long as the launch animation setting or the hide background apps setting is on.

## Settings window
The window that opens when the user opens Trackpad Launcher by hand: an ordinary macOS window with the close and minimise buttons, centred on the display under the pointer, in front and with the keyboard focus, every time it opens, whether the opening started the process or reached a running copy. It holds rounded groups, one under another, 20 pt apart: first, while this opening's update check has found a newer version, the update card; then, while the Accessibility permission is missing, the Accessibility hint; the five gesture rows and the launch animation switch; the switcher section (the swipe illustration, its title and the swipe setting's switch, then the window swipe illustration, its title and the window swipe setting's switch, with the screen recording hint under that switch in the same row while it applies, then the thumb tap illustration, its title and the swap setting's switch); the *Thumb corner* row, its title at the leading edge and its pop-up at the trailing edge, with the hide background apps setting's switch below it; then, while it applies, the no trackpad notice. Last, below everything and aligned right, come the *Quit Trackpad Launcher* button, red, and *Close*, which closes the window like its close button. The window resizes to fit whenever the update card, a hint or the notice appears or disappears. A gesture row's app picker is System Settings' own pop-up button, its bezel showing on hover: the app's icon, its name 6 pt after it, then the chevrons in a round badge, the content at most 128 pt wide, a long name cut short at the end. Every illustration draws the thumb in the chosen thumb corner: the bottom corners' pictures are the top corners' with their marks flipped top to bottom on the same card. A handwritten guide over the first gesture's illustration names the two marks (*Hold* for the thumb, *Tap* for the fingers), whether or not the gesture has an app; it shows for *Top left* only, where its arrows meet the thumb. It closes only by its close button, ⌘W, Escape (when no menu or chooser is open), *Close Settings* (⌘Q) in the app menu and *Quit* in the Dock icon's menu, and gestures keep working after it closes. Clicking another app, a gesture, a swipe, a window swipe, a swap, *Other…* (whose file chooser is a sheet on the window) and the System Settings buttons all leave it open; an app a gesture brings to front comes over it. With the hide background apps setting on, an action that hides hides this window too, unless Trackpad Launcher is the frontmost app: the window stays open to the app and keeps its Dock icon, as a minimised one does, and opening Trackpad Launcher again (the Dock icon, Spotlight, Finder, a swap or a lift on it) shows it where it was. Trackpad Launcher's own visuals, the switcher, the window switcher, the launch animation and the launch bounce, never hide with it.

## Gesture row
One line in the settings window: a gesture illustration and the app picker for that gesture.

## Installed apps
The apps an app picker lists: every app in /Applications and /System/Applications (with their subfolders), in ~/Applications, and Finder. One entry per bundle identifier. An app anywhere else, such as ~/Downloads, is not an installed app in this sense, even when a gesture is assigned to it through *Other…*.

## Recent apps
The up to 10 installed apps the user opened most recently, newest first, as Spotlight records it (an app's last-used date). Opening means launching; switching to an app that is already running does not count. No age limit. All five app pickers show the same recent apps; they refresh each time the settings window opens and may lag behind the very latest launches.

## App picker
The popup in a gesture row that sets the assignment: the recent apps, a divider, the other installed apps alphabetically, then *Other…* (choose any app on disk) and *None* (unassign). With no recent apps there is no recent section and no extra divider. The picker opens from a list Trackpad Launcher already holds, with the row's app over the button and checked (at the top when the row's app is not in the list); installed and removed apps show up in it within 5 seconds. Picking an app plays the pick animation on the picker's icon.

## Pick animation
The app picker's icon jumping into place from below when the user picks an app in that picker, from the menu or through *Other…*, the app it already shows included. The new icon appears at 55% of its side, 9 points below where it rests, and jumps up into place: it grows from its bottom edge to 108% in 0.16 seconds while rising, starting fast and slowing, overshooting its place by about 1.5 points, then settles back to 100% in its place by 0.26 seconds after the pick, smoothly and with no second wobble, fully opaque throughout; where it is bigger than its slot it draws past it, uncut. Only the icon moves: the app's name and the chevron show at once in their final places. Picking *None* plays nothing, and nothing else that changes an icon plays it: the settings window opening, a missing app coming back, a thumb corner change, a pick in another picker. A pick while it plays restarts it with the new icon. With the system's Reduce motion setting on the icon swaps at once. The launch animation setting does not affect it. Debug builds' animation tuner can tune it and preview it on the open settings window's pickers.

## Trackpad
A connected Apple trackpad. Its *kind* is *built-in* or *external* (a Magic Trackpad). macOS keeps trackpad settings per kind, so an external trackpad's settings can differ from the built-in one's. A Magic Mouse is not a trackpad.

## Tap-bound setting
A system trackpad setting that binds a system action to a tap rather than a press. Today: *Tap to click* and *Look up: Tap with three fingers*. The list is one table in the code; a setting is *on* when it is on for any connected trackpad. Gestures work whatever these settings are. With the Accessibility permission a gesture's tap makes no tap action (see *Tap action*); without it, a gesture under Tap to click also clicks where the pointer is, and one under Look up also looks up.

## Tap action
An action macOS performs for a tap of fingers, as opposed to a press: a left click for a tap of one finger and a right click for a tap of two (Tap to click), the Look up panel for a tap of three (Look up: Tap with three fingers) and Smart zoom for a double tap of two (Smart zoom). macOS makes it as the fingers lift, or up to about 0.3 s later for the right click while Smart zoom is on. Tap actions are blocked in the lift window; Look up and Smart zoom are blocked also under an anchored thumb with another finger down, however long the thumb has rested. So a gesture never clicks, looks up or zooms; everywhere else tap actions work as macOS makes them. Blocking them needs the Accessibility permission. A tap's click is blocked only while Tap to click is on for a connected trackpad; Look up and Smart zoom whatever the settings. A physical press is not a tap action and keeps the click blocking rules.

## Lift window
The first 0.5 seconds after a contact other than the thumb lifts inside a thumb touch, when macOS could read that contact as a tap: it was down for less than the *tap action hold limit* (the longest hold for which macOS still makes a tap action, measured on hardware) and no press was seen while it was down. A tap's fingers, a swipe's or a window swipe's fingers that lift quickly, and a finger that loses contact for a moment open it; each such lift restarts it, so it ends 0.5 s after the last one. Whether the thumb is still down changes nothing. A thumb lifting alone opens none; nor do fingers that rested or scrolled past the hold limit (a swap series' fingers, a scroll under a rested thumb), a finger that pressed the pad down, or any lift outside a thumb touch. During it every tap action is blocked: a click, a deliberate one included, and a press that starts in it is blocked whole, from press to release, so nothing is dragged and no button stays down; Look up; Smart zoom. Scrolling and the physical press rules are not changed by it. It is measured on the process's clock from the moment the lift's frame arrives; strictly less than 0.5 s is inside. The gated port stays on through it and closes on the next frame or event after it ends.

## Gestures active / inactive
Gestures are *active* when Trackpad Launcher is running and at least one trackpad is connected, whatever the trackpad settings and the Accessibility permission. Otherwise gestures are *inactive*: nothing is recognised and nothing fires, neither a gesture, a swipe, a window swipe nor a swap. Connecting or disconnecting a trackpad changes this live, with no relaunch.

## No trackpad notice
The message "No trackpad connected. Connect a trackpad to use gestures." in the settings window, shown while no trackpad is connected, with no button. The settings window never asks the user to turn a trackpad setting off.

## Feedback
The haptic pulses the trackpad gives: the *gesture haptic* when a gesture fires for an assigned, present target app, when a swipe opens an app, when a swap brings an app to front, and when a window swipe's lift leaves a window in front other than the front window or restores a minimised one; and the *light tick*, a lighter pulse, each time the switcher's or the window switcher's selection changes. A swipe or window swipe lift, or a thumb tap, that changes nothing is silent: a lift on the frontmost app, on an app that has quit, or with no switcher showing; a window swipe lift on the front window, or on a window that closed while the front window is still in front; a lift on the no-windows card; a cancelled window swipe; a slide up or down that is no window swipe; a thumb tap that is not a swap, or with nothing to swap to.

## Light tick
The lighter haptic pulse that marks each change of the switcher's or the window switcher's selection: one per icon or row the highlight crosses, none while the selection stays put.

## Launch animation
The target app's icon floating up from the pointer when a gesture fires for an assigned, present target app that is running, together with the feedback; for an app that is not running the launch bounce shows instead, and ends with the launch animation played from wherever its icon is. Only gestures play it: a swipe, a window swipe and a swap never do. It appears at once at full size, puffs up for a split second, then rises faster and faster as it shrinks, sways and tilts a little to one side, and fades out within about a third of a second, like a small balloon letting its air out. With the system's Reduce motion setting on, it fades out in place instead. It never takes focus or receives clicks, and every gesture for a running app plays its own. The *launch animation setting* turns it off.

## Launch bounce
The target app's icon bouncing just above the pointer while an app a gesture launched starts up, in place of the launch animation. It plays when a gesture fires for an assigned, present target app that is not running, while the launch animation setting is on. *Not running* means macOS reports no process for the app when the gesture fires: an app still starting up from the Dock or Finder, or a running menu bar app, has one and gets the launch animation. The icon is the launch animation's and appears with the gesture haptic, centred on the pointer's tip, its bottom edge 8 points above it. It inflates upward from there like a balloon: it appears at 24 points, swells to the launch animation's 60 × 60 points within 0.4 seconds, and keeps swelling ever more slowly, with no pause, to 84 points 5 seconds later, where it holds. Its ending's launch animation plays at the size the icon has reached, so it swells on rather than shrinking first. It follows the pointer on every move, onto any display. Near the left or right edge it slides just enough to stay on the pointer's display; the display's top edge cuts it off, and it never moves below the pointer. Several launches bounce side by side in one row above the pointer, newest on the right, 12 points apart, and when one ends the others slide to their new places.

A bounce ends with the launch animation, played from wherever the icon is, when a window of the app first shows (a splash screen counts), or 2 seconds after the app finished starting up with no window. It fades out in place within about 0.2 seconds instead when the launch fails, when the app quits, or when the app is still starting up 10 seconds after the gesture. No bounce lasts longer than 10 seconds, and a window that shows after a bounce ended plays nothing. These are the launch watch's ends: the bounce draws what the watch decides. A gesture for an app whose bounce still plays keeps that one bounce: the haptic plays and the app is brought to front, and nothing else shows. With the system's Reduce motion setting on, the icon pulses its opacity at its resting spot at 60 points instead of inflating, and every ending fades it out in place. It never takes focus or receives clicks. Only gestures play it: a swipe, a window swipe and a swap never do. Debug builds' animation tuner can tune the inflate, switch to a Dock-like jump instead, and preview either with Finder's icon.

## Launch watch
Trackpad Launcher following an app a gesture launched, from the gesture until the first of: the app's first window showing on screen (a splash screen counts; a hidden startup window does not, nor a transparent one or a sliver of a point), 2 seconds after the app finished starting up with no window, 10 seconds after the gesture, or the launch failing or the app quitting. It runs while the launch bounce shows and, with the launch animation setting off, unseen, while the hide background apps setting waits for the app's window; with both settings off nothing is watched. The bounce's endings and the hide after a launch are what it decides. A gesture for an app whose launch is watched keeps that one watch as it is, bouncing or unseen. Its time passes on the render server's clock, like the bounce's, so no watch outlasts its 10 seconds by more than a fraction of a second.

## Launch animation setting
One global setting, on by default, shown as the *Animate app launch* switch in the settings window, below the gesture rows. It covers both the launch animation and the launch bounce. While it is off, a gesture shows nothing at the pointer, whatever the system's Reduce motion setting; the feedback and bring to front are unchanged, and with the hide background apps setting on a launch is still watched, unseen, so the other apps hide once the app's window shows. A change applies to the next gesture, so a bounce already playing runs its course, and is saved at once, so it survives a quit, a force-quit or a Mac restart. Upgrading from a version without the setting leaves it on and changes no other setting.

## Sway
A launch animation's small sideways veer, to the left or to the right, never more than a third of its rise, with a slight tilt toward that side. The side is random, except that the same side never comes up three times in a row.

## Click blocking
Ignoring trackpad clicks (left-click, right-click, Force Click) for the first 3 seconds after a thumb lands in the anchor corner, while it stays there, another finger is on the trackpad, and gestures are active, and for the whole of a swipe, a window swipe or a swap series. Besides presses, it blocks the tap actions: under an anchored thumb with another finger down, however long the thumb has rested, and in the lift window after the fingers lift (see *Tap action*, *Lift window*). A thumb that lands under resting fingers opens that window like any other, so before a series starts the thumb rules alone apply. A press is blocked or passed whole. It needs the Accessibility permission; without it, clicks are never blocked. Under the same rule, trackpad and Magic Mouse scrolling is suppressed: a scroll suppressed at any point stays suppressed, momentum included, until its fingers lift, and a scroll that began unsuppressed coasts to a stop as usual. Pointer movement and a mouse's scroll wheel are never blocked; a mouse click is blocked only while another finger rests on the trackpad inside the blocking window or a swipe, a window swipe or a swap series is on, when it cannot be told from a trackpad press. The system's own trackpad swipes are blocked too, for longer: see *Dock swipe blocking*. With the swipe setting off there is no swipe, with the window swipe setting off no window swipe, and with the swap setting off no swap series, so only the thumb rules apply.

## Blocking window
The first 3 seconds after a thumb lands in the anchor corner, during which click blocking applies; held open for the whole of a swipe, a window swipe or a swap series, however long after the thumb landed and whether or not it stays. A thumb that was already resting when recognition restarted (after a trackpad change, wake, or a settings change) opens no window: its landing time is unknown, so clicks pass. The *lift window* is the other, shorter window, counted from the fingers' lift rather than the thumb's landing, and it blocks tap actions rather than presses.

## Thumb touch
The stretch of frames from one with a thumb in the anchor corner, whether it anchored or landed under resting fingers, until the first frame with no contact on the trackpad, edge contacts aside. Every gesture, swipe, window swipe and swap series lies inside one. What the thumb does inside it changes nothing about its length: it may roll out of the corner, lift, or land again anywhere, even as a plain finger, and the thumb touch lasts until the pad is empty. A touch no thumb landed in the corner during, such as three fingers landing outside the corner and swiping, is not one. Recognition restarting mid-touch (after a trackpad change, wake, or a settings change) starts a thumb touch only if a thumb is in the corner on its first frame.

## Dock swipe blocking
Ignoring the system's own trackpad swipes to another desktop, a full-screen app, Mission Control or App Exposé on every frame of a thumb touch with two or more contacts down, and for the whole of a swipe, a window swipe or a swap series, with no time limit. macOS counts every contact, the thumb included, so a thumb plus two sliding fingers reads as its three-finger swipe, and a thumb that has drifted out of the corner, or lifted and landed again as a plain finger, is a contact it still counts; that is why the blocking lasts the thumb touch rather than the thumb's anchoring. Outside a thumb touch nothing is blocked, so three fingers that land and swipe with no thumb in the corner reach the system as usual. A system swipe is blocked or passed whole, decided on the event that begins it. If the system sends an early warning of a swipe as the fingers land, before anything moves, it is judged on its own: a warning that passed commits nothing, so a swipe whose warning passed while the thumb was still alone is still blocked from its beginning once the fingers are down, and a warning that was blocked blocks the whole swipe. A swipe first seen under way is never cut short. Like click blocking, it needs the Accessibility permission; without it, nothing is blocked.

## Accessibility hint
The card at the top of the settings window, below the update card when there is one and above the gesture rows, shown while Trackpad Launcher lacks the Accessibility permission, whatever the trackpad settings: a rounded group with a light border, the message "Allow Accessibility access to make trackpad gestures work reliably." at most 216 pt wide, and under it a filled *Open Settings…* button in the system's accent colour (blue unless the user chose another, as the switches are) that opens the Accessibility page of System Settings, with no prompt first. A gear 91 pt across sits in the card's top-right corner, partly outside it and cut by its edges, and turns counter-clockwise around its own centre, one full turn every 30 seconds, smoothly across turns, for as long as the card shows; with the system's Reduce motion setting on it stands still in the design's pose, and it follows that setting live. The gear takes no clicks. The card goes the moment the permission is granted.

## Screen recording hint
The message in the settings window's *Switch windows* row, directly under its switch and lined up with the row's title, shown while Trackpad Launcher lacks the Screen Recording permission and the window swipe setting is on: a yellow warning triangle, then "Allow Screen Recording access to show previews in the window switcher.", then under the message an *Open Settings…* button in the ordinary grey style. The button asks macOS for the permission the first time it is ever pressed, which is remembered across relaunches, and opens the Screen Recording page of System Settings on any later press while the permission is still missing. The hint disappears, and the row returns to its usual height, once the permission is granted or the setting is turned off. A window swipe never asks for the permission.
