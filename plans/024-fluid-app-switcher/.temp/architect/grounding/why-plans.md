## Direct Evidence Found

### A. Idle-CPU rule (the root of the timer/display-link bans)

1. **Product requirement, zero idle cost.**
   - "A launcher only earns a place in the menu bar if it costs nothing to keep. One that asks for Accessibility, phones home, logs, or burns CPU while idle gets uninstalled." — `plans/001-trackpad-launcher-app/plan.md` Problem statement (l.9).
   - "### R22. Zero cost when idle — While no finger is touching any trackpad, Trackpad Launcher MUST show 0% CPU in Activity Monitor, with at most one momentary blip per minute." Scenario: "its CPU reads 0.0% throughout, with at most one momentary blip" — 001 plan.md l.419-425.
   - Design: "the whole app must cost nothing while idle … Hard constraints: no permissions, no network, no logging, no timers or polling (R20–R22)" — 001 plan.md l.457.
   - Requirement. Relevance: idle CPU is the original forcing function; animation rules descend from it.

2. **Timers banned by the source scan from 001.** Sketch: `("Timer", "R22 timer"), ("asyncAfter", "R22 timer"), ("Task.sleep", "R22 polling"), ("makeTimerSource", "R22 timer")` — 001 plan.md l.1325. Alternatives rejected: "**An injected `Clock` and a tap-timeout timer.** Conventional, but every lift is observed as a frame, so the frame timestamp is a sufficient clock, and a timer would be the app's only timer (R22)." — 001 plan.md l.1389. Implementation decision.

3. **Plan 003 R6 "No work while idle"**: "While nobody uses the picker, Trackpad Launcher MUST do no periodic work to keep it current." — `plans/003-dropdown-recents-performance/plan.md` l.115-116. Dev log: "Background freshness vs. the overview's minimal-resources rule → added R6" (003 dev log l.8). Requirement.

4. **Measured idle baseline** (Release audit): "Idle, nothing touching (shipped) | 0.77 ms per 60 s, 0 idle wakeups | 0.001%" — `plans/014-gate-event-tap/plan.md` Problem table (l.12). "the app is free while idle but costs 2.2–2.7% of one CPU core for the whole time any finger touches the trackpad" (l.5). Measured fact.

### B. The animation rule and the display-link ban (plan 004)

5. **Origin of "display links are banned".**
   - "`SourcePolicyTests.banned` gains `displayLink` and `DisplayLink`, under the rule "timer". A per-frame callback is the tempting alternative to keyframes, and it would run code of ours on every frame." — `plans/004-launch-icon-animation/plan.md` "Source policy" (l.346-347).
   - "`docs/architecture.md`: Concurrency gains the animation rule: Core Animation keyframes, cleaned up from the completion callback, no display links." — 004 plan.md "Docs" (l.351-352).
   - Implementation decision. Relevance: this is the only stated rejection of a per-frame callback, and the reason given is "run code of ours on every frame" (tied to the "timer" rule, i.e. R22).

6. **"No code of ours runs" after the animation.** "The panel is closed from Core Animation's completion callback, never from a timer: `Timer`, `asyncAfter` and `Task.sleep` are banned from shipped sources." … "Core Animation renders the frames in the render server. Once the last panel has closed, no code of ours runs." — 004 plan.md "Lifetime" (l.336-339). Implementation decision.

7. **Measured facts from 004's planning probe** (004 plan.md "Further Notes", l.531-537):
   - "First panel created with `defer: false`: 26–29 ms. First icon fetch: ~6 ms. Each overlay after that: 1–2 ms."
   - "First render ever of an app's icon at this size: 45–120 ms … After that, 1–2 ms".
   - "Core Animation's completion fired 9–19 ms after a 300 ms animation ended, for a window on screen and one off screen."
   - "A closed panel stays in `NSApplication.shared.windows`."
   - Also the idle verification: "Activity Monitor then shows 0.0 % CPU for Trackpad Launcher while idle, as in plan 001's idle check." (l.499).

8. **Pure flight builds exactly the `CAKeyframeAnimation`s the overlay adds, so the copy into Core Animation is under test.** "Copying poses into Core Animation (the lean's sign, conversion to window coordinates) was checked only by eye → the flight now builds the exact `CAKeyframeAnimation`s the overlay adds, and the T9–T21 rows read their values, keyTimes and duration." — 004 dev log, Plan bullet (l.21). Also 004 plan.md l.237-242: "They build `CAKeyframeAnimation` objects but never add them to a layer … Tests then read what Core Animation will play". Dev-log entry + decision. Relevance: the testing pattern for motion (pure keyframe builders, assert requirement bounds not formulas).

### C. How the launch animation's tuning was set up and why

9. **Tuning by feel in a Debug-only tuner.**
   - "The user polished the animation by feel in a Debug-only tuner window and picked their "Preset 2" → it is the shipped animation: 60 pt, 0.34 s, a 20 % pop over 75 ms, rise 70 pt, and new rise, shrink, fade and sway curves." — 004 dev log "Tuning" (l.51).
   - "Every animation number moved into `LaunchTuning`, whose defaults are the shipped animation. The tuner (`AnimationTuner`, `#if DEBUG`) stays in the codebase for future polishing; Release builds contain none of it." — 004 dev log l.52.
   - "The icon bitmap is rendered at the pop's peak size, and keyframes are sampled at 240 per second so the short pop stays smooth." — 004 dev log l.53 (measured/feel-driven choice).
   - 004 plan.md "Tuning (Debug builds only)" (l.291-295): "Release builds read its defaults as constants. Debug builds read them through a `Mutex` the tuner writes." "a slider per number, live preview at the pointer, reset to shipped, and named presets saved in user defaults." "To ship a new tuning, copy its values into `LaunchTuning`'s defaults and adjust the requirement bounds and tests if they move."
   - 004 plan.md "Curves" (l.278): "Retuned by feel with the Debug-only tuner …; the tests check the requirement bounds, not these formulas." Further Notes: "The curve constants are feel choices. The tests check requirement bounds, so tuning within those bounds keeps the suite green." (l.539).

10. **Tuning drift between Debug and Release (an incident).** "During M2 the human saw the launch icon much smaller than in Debug builds. … Release always plays `LaunchTuning.shipped` (40 pt, 47 pt rise), while Debug builds open the animation tuner at launch, which applies its saved "current" tuning, equal to "Preset 2" (60 pt, 70 pt rise) → at the human's request the shipped tuning now equals Preset 2 (R6)" — `plans/014-gate-event-tap/development-logs.md` l.40; requirement 014 R6 (plan.md l.44-45). Background: 005 had shrunk it ("The icon starts at 60 × 60 points. That is too big for a quick confirmation and draws more attention than it should." — 005 plan.md l.5; "`LaunchTuning`'s shipped values change … 60 → 40, and the rise 70 → 47" l.146). 017 F25 restates: "Debug builds play the last saved tuner state, not shipped (the plan 014 incident)."

11. **Tuner extended for the switcher's swipe speed.** "The four numbers are knobs in the Debug animation tuner, read live on every frame." (006 dev log l.46, swipe acceleration), later replaced: "The tuner's four gain knobs became a follow-the-cursor toggle, points per icon and a tracking-speed override." (006 dev log l.47). 017 how-tuner: `LaunchTuning` doc comment "Every number that shapes a launch flight, plus the switcher's swipe acceleration, which the same tuner tweaks."

### D. The switcher's visual shape (plan 006)

14. **Requirement wording for the look.** 006 R10: "The switcher MUST be a Liquid Glass panel centred on the screen the pointer is on, holding one row of 80 pt app icons with 20 pt between neighbours, a glass selection highlight slightly larger than an icon that slides under the icons, the selected icon drawn slightly larger than the others, and the selected app's name below the row. It MUST appear as the swipe begins with no perceptible delay, MUST be gone within 200 ms of the swipe ending or cancelling, MUST never take focus or activate Trackpad Launcher, and MUST look correct in light and dark appearance. With Reduce motion on, the highlight MUST still follow the fingers and the selected icon is still drawn larger, but nothing springs, fades or animates its size." — `plans/006-five-finger-tap-and-corner-swipe/plan.md` l.241. Solution: "A glass highlight follows the fingers across the icons. The icon under it grows a little, its name shows below" (l.15). Requirement. Relevance: Liquid Glass panel, glass highlight, enlarged selected icon, ≤200 ms disappearance and Reduce motion are product requirements, not implementation choices.

15. **Highlight follows continuously.** 006 R6: "The highlight MUST move continuously with the fingers: between two icons it sits between them in proportion to the travel. … travel beyond an end moves the highlight only slightly past it, and it springs back to the end icon." (l.135). Requirement.

16. **Design decision 8 (the rendering shape).** 006 plan.md l.646: "*The switcher is model state rendered by `LauncherUI`, with AppKit and Core Animation (O5; F24, F26, F27, F32).* … `SwitcherPresenter`, owned by `MenuBarShell`, iterates `Observations({ launcher.switcher })`, which coalesces to the latest value per main-actor turn, a natural back-pressure at ~100 Hz. Its `SwitcherPanel` uses the launch overlay's configuration (F26: borderless, `.nonactivatingPanel`, `ignoresMouseEvents`, `.screenSaver` level, …) around an `NSGlassEffectView` in a rounded clip as `LauncherPanel` does, holding a layer-backed host for the 80 pt icon layers, a glass highlight view 92 pt square, and a name label. It is created once at shell init (F32's 27 ms). … *Per update, with actions disabled:* highlight x = `position × 100 pt`, so it follows the fingers one to one; the selected icon layer at 1.12× with the name below. *When `stretch` changes and is not zero:* add an additive `CASpringAnimation` on the highlight layer's `position.x`, keyed so each one replaces the last, from `stretch × 100 pt` to 0. … "moved only slightly past, and springs back" with no code of ours per display frame. *On close:* opacity to 0 over 150 ms, `orderOut` from the completion unless a new switcher opened meanwhile. *Reduce motion:* no spring (the highlight rests on the end icon), no scale animation, no fade." Implementation decision. Relevance: origin of overlay panel config, separate glass highlight, 1.12×, per-update actions-disabled positioning, additive keyed spring, 150 ms fade.

But its springs and scale animations are not Core Animation keyframes, the architecture's animation rule, and the overlay precedent is Core Animation. Kept for the window, not used for the switcher."
   - 006 candidate-1 (`.temp/architect/candidate-1.md` l.940-941) gave a sharper reason: "Declarative, with `glassEffect` and environment Reduce motion. But its springs and fades are interpolated in-process per display frame, which the architecture's animation rule avoids."
   - 006 Tradeoffs (l.1338): "We accept that rendering the switcher in AppKit and Core Animation is more imperative than SwiftUI, in exchange for springs and fades played by the render server with no code of ours per display frame, as in the launch overlay."
   - 006 dev log Plan (l.30): "Rejected from candidate 2 with reasons: SwiftUI content for the switcher (its springs are not Core Animation keyframes, the architecture's rule)".
   - Rejected alternative.

18. **Per-input-event carve-out: first articulated in 006 grounding F27.** "F27 **sourced** (`docs/architecture.md` Concurrency): "No timers, no polling, no background loops: every input is a push"; "Animation is Core Animation keyframes … No code of ours runs per frame, and display links are banned." ### E. The row scaling on narrow displays (plans 008, 013)

25. **Requirement.** 008 R6: "Icons MUST be 80 pt when the whole row fits on the pointer's display. When it does not, the icons and the gaps between them MUST scale by the same factor, so the row keeps its proportions and the whole row fits on that display, in one row. The finger travel per icon MUST NOT change with the icon size." — `plans/008-recent-apps-switcher/plan.md` l.119-120. Solution: "When many apps run, the row shrinks its icons to fit the display, like ⌘-Tab. The finger distance per icon stays the same." (l.17). Dev log Specify: ""Shrink evenly" was ambiguous, and long rows may exceed trackpad travel → R6 now scales icons and gaps by one factor" (008 dev log l.9). This replaced 006's non-goal "A switcher row wider than the screen. … The row is laid out as if it fits; nothing slides, shrinks or wraps." (006 plan.md l.473), which itself came from user review removing a sliding-row rule (006 dev log l.23).

26. **Decision 10 (pure layout in core).** "**A pure row layout scales the panel to the display.** `SwitcherRowLayout`, a value in the core beside `Switcher`, … one function, `centreX(at:)`, … which the panel uses for both the icon layers (integer positions) and the highlight (any position), so the two cannot drift apart. … The core's travel … never sees the layout, so the finger travel per icon is unchanged by construction. The 80 pt bitmaps are shown smaller by the layer's trilinear minification. There is no lower bound on the icon size, as in ⌘-Tab." — 008 plan.md l.288. Dev log Plan: "T16 could not fail … and the real risk, icons and highlight drifting apart, was untested → `SwitcherRowLayout.centreX(at:)` positions both" (l.25).

27. **Plan 013 re-based padding on the highlight.** 013 R3: "The icon row MUST sit 22 pt from the panel's top, bottom, left and right edges at full size, measured to the highlight's edge" (l.33). Decision: "`SwitcherRowLayout.padding` becomes 22 and means the gap between the panel's edge and the highlight's edge on all four sides. … The padding does not shrink with the row" (l.99); fitting rule uses "the highlights' span" (l.101); `selectedIconScale` (1.12) moved into the layout "so every size that must agree with another, the icon, the highlight and the enlarged icon, is one tested value" (l.103). 013 R2: "The selected icon MUST be drawn larger than the others, unchanged from today, and it MUST stay inside the highlight." (l.26). Problem: name label removed because it made "the panel taller below the icons than above them, so the panel looks unbalanced" (l.5).
   - 013 non-goals: "Changing icon size, the highlight's size, its motion, the haptics, or where either panel appears." (l.91); decision l.105: "The panel's corner radius (34) and the highlight's (24), the transform's 0.12 s animation and the spring are untouched: the look and motion are non-goals."

### G. Plan 017 wrote the per-input-event rule into the architecture, with human sign-off

30. **D1 reading.** "**D1 reading.** No code of ours runs per *display* frame. Code may run per *input event* while the effect it serves is on screen. This is the switcher's per-trackpad-frame precedent (plan 006 F27, `docs/performance.md`). The bounce itself is keyframes on the render server." — `plans/017-launch-wait-bounce/plan.md` l.478.
   - Docs change: "The animation bullet is reworded to say what it allows: never per display frame, per input event while the effect shows." (l.1087). Slice S4 wording of the target doc: "Code may run per input event while the effect it serves is on screen: the switchers' highlight on trackpad frames, the launch bounce's row on pointer moves." (`.temp/slices/S4.md` l.70).
   - Open question D1 (l.1196): "is "never per display frame; per input event while the effect shows" the rule you want written into `docs/architecture.md` for later features too?" Answer recorded: "D1 accepted as the rule for later features too." (017 plan.md "Open questions" preface; dev log l.51: "Human review of the design: … D1 accepted for later features").
   - Decision + human sign-off. Relevance: this is the exact provenance of the quoted architecture sentence in the question.

31. **Measured costs behind the per-input-event allowance (017 grounding, probed).**
   - F20: NSEvent global monitor delivers without Input Monitoring; "median 3.5 ms (p90 4.2 ms) from the event's timestamp to the handler."
   - F21: "moving an 84×120 click-through panel with `setFrameOrigin` costs 0.057 ms per move; moving a layer in a display-sized panel with commit + flush 0.038 ms. **Conclusion:** following at ~120 events/s costs well under 1% of a core while a bounce shows. How far the icon visibly trails the hardware cursor cannot be measured by a probe."
   - Tradeoff: "**Code on every pointer event while a bounce shows** (about 0.04 ms per move, up to about 120 per second). In exchange, the icon is glued to the pointer, no code is driven by the display, and nothing runs once the last bounce ends." (017 plan.md l.1153).
   - R7 open question: "the icon trails the hardware cursor by the monitor's delivery delay (median 3.5 ms) plus up to one display frame. Is that "no lag the user can see"? Only drawing the cursor itself would beat it." (l.1200).
   - Open question: "The hand-off frame: … Is a manual check for a blink or a doubled icon at 120 Hz enough?" (l.1203).

32. **Core Animation as the only clock; measured lateness.**
   - "**Time (R10, R12, R18): Core Animation is the clock, and every deadline belongs to a bounce.** … A deadline is a 1→1 `opacity` `CABasicAnimation` on that layer, and its delegate's `animationDidStop` is the deadline passing. That is about 1 ms late while the panel is composited, and up to about 60 ms late when the row is cut off entirely at the top edge (F24, P5)." … "No banned token is lifted, and the model holds no clock. The idle-CPU rationale behind the ban holds by construction: a deadline cannot outlive the bounce that carries it." — 017 plan.md l.456-463.
   - F24 (probed P3): "a Core Animation animation's delegate fires 1.1–1.3 ms late for a 2 s animation on a layer in a visible panel or in an alpha-0 panel; … on a layer in no window the animation stops at once with `finished == false`; removing an animation fires its delegate with `finished == false` at the next commit. **Conclusion:** a CA animation is a precise deadline only on a layer inside an ordered-in window."
   - Check P5: committed animations complete "15–57 ms late" when the panel is off-screen/empty/moved off/ordered out.
   - Check P6: "in our process a display-sized panel whose root layer draws nothing costs about 0.8 MB more than a closed one … What the WindowServer spends compositing it is not attributable from here (unmeasured)."
   - Rejected alternative: "**A deadline port backed by a dispatch source.** It is honest about time. It needs `asyncAfter` or `makeTimerSource` unbanned and the architecture rewritten. … Lost." (l.1175-1178).
   - Bounce motion: "`BounceMotion` is pure. It builds one cycle as 240-per-second `transform` keyframes" (l.486).

33. **Rejected: moving a small panel per event.** "**One small panel per row, moved with `setFrame` per event.** It is as cheap per move (F21). The top-edge clip would change the frame and the layer offset in two systems that may not land in the same frame. `trailing` would need an unbounded reach. Lost to the display-sized panel once P6 showed that panel is cheap in our process." — 017 plan.md Alternatives. Relevance: a recorded reason to prefer layer moves inside one panel over window-frame moves per input event (two systems not landing in the same frame).

### H. Performance facts about the switcher itself

34. **Switcher redraw cost noted, deliberately not optimised.** 014 Non-goals: "Fewer redraws in `SwitcherPanel.show` during app switcher swipes: it saves a few milliseconds per swipe and would likely change the icon-grow animation that plan 013 keeps unchanged." — `plans/014-gate-event-tap/plan.md` l.49. 014 task.md: "the non-goals stand (no redraw work …)". Relevance: an audit found per-update work in `SwitcherPanel.show`; the only quantified figure in plans is "a few milliseconds per swipe".

35. **Swipe travel and input rate.** 006 dev log l.47: travel reproduces macOS pointer acceleration from IOHIDFamily with "the trackpad driver's `HIDAccelCurves`, 400 counts per inch, a 120 Hz report rate, the 67 Hz standardisation and 96/67 cursor scale … Travel is cursor points, 100 per icon (the icon pitch)." 006 plan/candidates repeatedly state the frame stream as "~100 Hz" (e.g. 006 plan.md l.646, l.671). 001 l.457: frames "at ~100 Hz while touching".

36. **Icons pre-drawn so the first swipe never stalls (measured).** 008 Implementation Decisions intro: "A running app's first icon load plus 80 pt draw costs about 25 ms per app (0.1 ms once drawn), so a cold row of 14 would stall 350 ms if drawn at the swipe." (l.274-ish, "Three numbers from a probe"). Decision 9 pre-draws on pushes (launch/terminate/appearance), never polls. 008 Further Notes: "Cost on the swipe path after this plan: one LaunchServices read (1.4 ms warm, under 4 ms cold, for 14 apps) and cache hits for icons".

## Contradictions

1. **What "no code of ours runs per frame" forbids** (recorded as disputed before 017 settled it).

   - Input-driven reading: 006 grounding F27 "A switcher highlight driven by finger frames is input-driven work … not a per-display-frame loop."
