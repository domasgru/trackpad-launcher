# Design: Switcher hides apps that have a gesture

## Implementation Decisions

Two facts about the code shape the decisions. First, the switcher's row is composed in exactly one place: the `Switcher` value's failable initializer, which takes the frontmost app and the ⌘-Tab apps the model just read, drops the copy at the frontmost app's location, prepends the frontmost app, keeps at most 10, and returns nil when nothing besides the frontmost app is left. Every requirement here is a change to what that row holds, so the feature is one more rule in that initializer and one more argument from the model; the selection, the travel, the lift, the swap, the window and the icon passes stay as they are. Second, an assignment is identified by its bundle identifier, not its location, and the stored assignment carries that identifier whether or not the app can still be found on disk. Hiding by that identifier needs no disk lookup, so a missing assignment hides its app exactly as a present one does, and a swipe's beginning gets no slower.

### Identity: an assignment hides by bundle identifier

The apps the row leaves out are identified by bundle identifier: the set of bundle identifiers of every stored assignment, over all five gestures, missing ones included. A running app is left out when its bundle identifier is in that set. Nothing is located on disk for this: the catalog is not consulted and the row never depends on where the app lives now, so an assignment whose app was moved to the Trash still hides the running copy (R1), and an assigned app that no gesture can bring to front is still not offered a slot. Two running copies of one bundle (identity by location in the row, as today) are both left out when that bundle is assigned, since the assignment names the bundle, not a copy. The frontmost app is never left out, whatever its bundle identifier (R2): it is passed separately and the set is applied to the ⌘-Tab list only.

### Switcher: the row leaves out the assigned apps

`Switcher`'s initializer gains one argument: the set of bundle identifiers to leave out. The others are the ⌘-Tab apps without the copy at the frontmost app's location and without any app whose bundle identifier is in the set, in their order; the row is the frontmost app, if any, then the others, at most `switcherMaxApps` in all. The existing rules deliver the rest without further code: the `prefix` refills the freed slots with the next most recently used others, so the row holds 10 whenever enough unassigned apps run (R3); the nil result when the others are empty covers both the frontmost app with only assigned apps behind it and no frontmost app with every running app assigned (R4, R5), and the model already treats nil as a swipe with nothing to show; with no frontmost app the row is the others alone and the selection starts on the first (R5). The argument has no default: the one production caller decides it, and the tests pass an empty set where they want today's row. The documentation on the row describes the leaving out, and the doc comment on the initializer says identity for the frontmost's copy stays the location while leaving out goes by bundle identifier.

### Launcher: the set is read when the swipe begins

In the model's swipe path, on `.began`, after the running apps are read, the model derives the set from its settings' assignments at that moment and passes it to the switcher. Nothing is stored: there is no cached set and no new field on the model, so the row always reflects the assignments in place when the swipe begins (R6), including an assignment set or cleared through the launcher window since the previous swipe. `.moved`, `.ended` and `.cancelled` are untouched: a hidden app can never be the selection because it is not in the row, and the lift's rules (the frontmost app is silent, an app that quit is silent, otherwise the gesture haptic and bring to front) apply to the row as composed. Whether the derivation is a one-line expression in the swipe path or a small read-only derivation on `Settings` is the implementer's call; either way it is read, not kept.

### Swap, window, presenter and settings: untouched

The swap path and `SwapSeries` never see the set: a swap still targets the first running app, in ⌘-Tab order, that is not the frontmost app, assigned or not (R7). The launcher window and its switcher section gain nothing (R8): there is no setting, no key in `Settings`, no change to its decoding, and no new control; the section keeps its two switches. The presenter's icon passes are untouched: they draw every running Dock app's icon before any swipe, and an assigned app's icon that no row uses costs nothing at swipe time; it is also needed again the moment the user clears that assignment. The reconcile, the recognizers, click blocking and scroll suppression are untouched: a swipe with nothing to show already runs its course with the fingers blocked until they lift, which is what R4 asks for.

### Existing tests

The `Switcher` value's own tests construct it directly; each construction, including the suite's helper, passes an empty set, so every existing row keeps its assertions and proves that an empty set changes nothing. One model-level switcher test changes: the one that proves a tap fires after a reconcile mid-swipe assigns Mail, a running app, to the 1-finger gesture before the swipe and then expects a 12 mm slide to select Mail, which this feature leaves out of the row. It keeps its purpose and its assertions' shape but assigns an app that is not running (install one, assign it, expect the final tap to bring that app to the front), so it stays about the reconcile and independent of this feature. No other model-level switcher or swap test assigns an app that is also running. The World needs no new helper: assignments are set through the model's picker path, running apps and the frontmost app through the existing fakes.

### Documentation

`docs/domain-model.md`: the *Switcher* entry says the row leaves out the apps a gesture is assigned to, by bundle identifier, missing assignments included, with the frontmost app always shown, and that "nothing to switch to" includes every other running app having a gesture; the *Frontmost app* entry adds that it is there even when a gesture is assigned to it, and says that with no frontmost app the row is the running apps without a gesture alone; the *Swap* entry says the target may be an app a gesture is assigned to; the *Assignment* entry points to the switcher. `docs/product-overview.md`: the switcher's description says the row leaves out the apps that have a gesture. `docs/architecture.md`: no change; nothing here is a decision that holds across the codebase.

## Further Notes

- **Why the Switcher and not the model filters.** The model could filter the ⌘-Tab list before constructing the switcher, one line either way. Composing the row in the Switcher keeps the whole answer to "what is in the row" in one initializer with its own tests, and keeps the model's swipe path a read of the system plus a construction, as it is today.
- **Why by stored bundle identifier and not by locating.** Locating each assignment through the catalog would read Info.plist files on the main actor at the start of every swipe, and would stop hiding an app the moment its bundle moved to the Trash, the opposite of R1. The stored identifier is the assignment's identity by the domain model's own definition.
- **A menu bar app in front with a gesture.** A frontmost app absent from the ⌘-Tab list is shown at the left end today; an assignment on it changes nothing, since the set applies to the list only.
- **A switch to turn this off** is a non-goal. Should one come later, it is one more Boolean setting beside the swipe and swap settings and an empty set passed when it is off; nothing here needs reshaping for it.
