# Task: design the launch bounce

## The artifact
One design package for plan 017 (`plans/017-launch-wait-bounce/plan.md`, requirements R1–R19), shaped exactly per the Design package template in the shared design reference: Problem, Usage (caller's view), Shape (with the Swift type sketch: types, signatures, class shapes, module boundaries, `fatalError("not implemented")` bodies, `// TODO` pseudocode for the tricky logic), Synthesis decision (leave empty), Tradeoffs accepted, Alternatives considered, Open questions and risks, Next implementation step. Swift 6, strict concurrency, the project's module split (`LauncherCore`, `LauncherPlatform`, `LauncherUI`, app target). Name modules and types, not file paths, except where a source-scan confinement rule ties code to a file name.

## What the human asked for (verbatim)
"I want you to implement the icon bounce animation while app is being loaded for the first time, until the app window is showed. The icon size should be the same. And that bouncing icon, should follow the cursor, so you are sure that anytime the app will be launched. The bounce should have a similar feel of the native macos bounce in dock. I will tweak it later if needed. You can straight away add some animatino settings in our animation tweaking UI, so that I could test different variations if needed"

## What the design must address
Start from `plans/017-launch-wait-bounce/.temp/architect/grounding/index.md`: it states each fact with its standing (probed on this Mac, sourced, or disputed) and the open questions. Facts F7–F24 come from probes run on this Mac today and override any recollection of how macOS behaves.

1. **The decision.** Where and how a fired gesture chooses between the launch bounce, the launch animation and nothing (R1–R3), how "not running" is read (R1, R2), and how a repeated gesture for an app still bouncing keeps one bounce (R14), without breaking today's fire-path guarantees (haptic and first visible icon in the same main-actor turn; bring to front before any animation work).
2. **The lifecycle.** How the bounce learns, for its own launch only, that a window showed (R9), that the app finished launching and no window followed within 2 s (R10), that the launch failed or the app quit (R11), and the 10 s cap with its two outcomes (R12); and what happens to signals that arrive after a bounce ended. The probes show which macOS signals exist, when they arrive, and for which kinds of app (regular, menu bar, crashing, failing, Electron); the design must work with those facts, including without the Accessibility permission (open question O1).
3. **Time.** Where the 2 s grace, the 10 s cap and the tuner's 3 s preview come from, given the architecture's timer ban and its idle-CPU rationale (F23, F24, D4), and how a test controls that time without waiting.
4. **The pointer.** How the icon follows the pointer on every move, across displays (R7), rests and clips per R5/R6, lays out several icons in a row that re-flows over about 0.2 s (R13), and never takes focus or clicks (R16); with zero cost once the last bounce has ended. State which reading of "no code of ours runs per frame" (D1) and of the pointer-privacy question (D2) the design relies on.
5. **The motion.** The Dock-like bounce (R8) at the launch animation's icon size, sharp at every height (R4); ending mid-jump into the launch animation from wherever the icon is (R9); the quiet fade (R11); the Reduce motion pulse (R15).
6. **The tuner.** The launch bounce section with each knob R17 lists, applying to the next bounce, the preview (R18), presets that carry the knobs and load old presets with shipped bounce values (R19), Release builds unchanged.
7. **Seams and docs.** The seam the requirement scenarios run at, and a test's handle on everything a test cannot wait for or provoke (time, lifecycle signals, Accessibility answers). Which contracts in `docs/architecture.md`, `docs/domain-model.md`, the `SystemActions` port docs and `SourcePolicyTests` change, and why.

Satisfy the requirements as written; where a requirement cannot be met as written on this platform, say so in Open questions and risks rather than silently weakening it.
