# S3: Sliding brings each window forward and lifting keeps it

## Goal

During a window swipe, each time the selection lands on a visible window, that window comes to the front at once with the keyboard focus (a minimised row is never restored while sliding). When both fingers lift, the model reads the windows again and carries out a pure lift plan: the selected window in front with the keyboard focus, then the front window, then the rest; a minimised selection restored; the gesture haptic, and the launcher window closing, only when the window in front changed. Message rows read nothing and stay silent; a cancel leaves the windows as they are. `docs/product-overview.md` gains the window swipe.

## Requirements

Quoted from the plan, cut to what this slice delivers.

- **R3 (the full-screen lift).** "When the front window is full screen, the switcher MUST show that window as its single row … and lifting MUST change nothing."
- **R5 (focus stays put).** Scenario: "GIVEN a text field in the front window has the keyboard focus, WHEN the user starts a window swipe and lifts without moving the selection, THEN the text field still has the keyboard focus."
- **R10.** "Each time the selection moves to a visible window, that window MUST come to the front at once, above the app's other windows, and get the keyboard focus, while the switcher stays on top. Selecting a minimised window MUST NOT restore it while sliding. Selecting a window that has closed MUST change nothing on screen. Moving the selection back to the first row MUST bring the front window back to the front. When there is no front window, sliding back to the first row MUST change nothing on screen."
- **R11.** "When both fingers lift, the selected window MUST be in front and have the keyboard focus. A selected minimised window MUST be restored and brought to the front. The windows MUST then be ordered: the selected window, then the front window, then the others in their order from before the window swipe. When every listed window is minimised there is no front window: the selection MUST start on the first row, and lifting on any row MUST restore that window and bring it to the front with the gesture haptic. Lifting on the front window MUST change nothing and be silent. Lifting on a window that has closed MUST leave the windows as they are at that moment, with no reordering, and follows R12 for the haptic." Scenario "Selected window closes": "GIVEN Safari's front window was "Docs" and the user has slid onto "Mail", WHEN "Mail" closes, then the user lifts, THEN the windows stay as they are at that moment, with no reordering, and the gesture haptic plays only if the window now in front is not "Docs"."
- **R12 (the haptic).** "A lift MUST give the gesture haptic if, and only if, the window in front after the lift differs from the front window at the start of the window swipe, or a minimised window was restored. Otherwise the lift MUST be silent. The window swipe MUST never play the launch animation."
- **R13, R14 (silent lifts).** "In each of these cases [one window, no windows, no frontmost app] lifting MUST change nothing and be silent." "[Without Accessibility] Lifting MUST change nothing and be silent."
- **R15 (a cancel keeps the window in front).** "a cancelled window swipe MUST keep the window in front as it is at that moment, without the lift's reordering, and be silent."

Design answers to open questions, to follow as defaults (the human will confirm later):
- One minimised window and nothing else: lifting restores it, with the haptic (R11's "every window minimised" wins over R13's one-window rule).
- When the front window closes mid-swipe and the user lifts on its row, the haptic plays because another window is now in front. When every listed window has closed, the lift is silent. When the app opens a window in front mid-swipe, the lift brings the selected window back above it and leaves the new window just behind, above the other listed windows. When another app is in front at the lift, nothing is raised and it is silent.
- "Lifting on the front window MUST change nothing" reads as "leaves the windows as they were before the window swipe": after sliding away and back, the lift raises windows to restore that order, silently.

## Design

Background: `plans/012-window-switcher-gesture/.temp/architect/grounding/index.md` facts F14, F19 to F24 (AX raise behaviour, probed), and `.../grounding/probes/probe-2-ax-windows.swift` for working `AXRaise` code. `.../architect/checks/check-2-lift-rules.swift` is a worked, runnable model of `WindowStack.raises` checked against R10 to R13; use it as a reference.

### Port (LauncherCore `Ports.swift`)

```swift
@MainActor public protocol SystemActions: AnyObject {
    // existing members, and frontmostWindows() from S2 (its doc gains: "The windows it lists are the only ones a later
    // `raiseWindows` may name, until the next read.")

    /// Raises these windows of the latest `frontmostWindows()` read, the last first, so the first ends in front of its
    /// app with the keyboard focus and the rest behind it in this order; beside `bringToFront`, which is app-level. A
    /// raised minimised window is restored. A window that has closed is skipped; an id the latest read did not list is
    /// skipped, so nothing on another Space is ever raised. About 2 ms per raise; once the app has timed out, no
    /// further calls go to it for that read. [] does nothing.
    func raiseWindows(_ frontToBack: [WindowID])
}
```

### Core values (LauncherCore)

```swift
/// How raising windows one at a time, each to the front of its app, reaches an order.
public enum WindowStack {
    /// The shortest front part of `target` (front to back) that, raised back to front, leaves the target windows on
    /// screen in `target` order among themselves, with the first in front of every window of the app. `current`: the
    /// app's visible windows now, front to back, including any that opened since the begin. The first target window is
    /// part of it unless it already leads `current`, so a minimised first window is restored and one opened mid-swipe
    /// is passed; target windows not in `current` other than the first (minimised) are left out, so a later minimised
    /// window is never restored. A window not in `target` keeps its place among the windows not raised, so one opened
    /// mid-swipe in front ends just behind the raised ones. Empty when the order already holds. Total: the whole target
    /// always qualifies.
    public static func raises(current: [WindowID], target: [WindowID]) -> [WindowID]
}

/// What the lift does: `raises` front to back (the first ends in front with the keyboard focus), and R12's pulse.
public struct WindowLift: Equatable, Sendable {
    public let raises: [WindowID]
    public let playsHaptic: Bool
    public static let nothing = WindowLift(raises: [], playsHaptic: false)
}

extension WindowSwitcher {
    /// The window that comes to the front while its row is selected. nil on a minimised row or a message (R10).
    public var selectedVisibleWindow: WindowID? { … }

    /// The lift (R11, R12), from the rows fixed at begin and a second read of the frontmost app's windows. Pure.
    /// - `now` is no app or another app, or nothing is listed → `.nothing`: no raises, silent.
    /// - The selected window has closed → no raises (no reordering); the haptic plays iff a window is in front now and
    ///   it is not `frontWindow`. Every listed window closed is therefore silent.
    /// - Otherwise the target is the selected window, then the visible windows in their begin order (the front window
    ///   first) without it, minus any that closed; `raises` is `WindowStack.raises(current: now's visible, target:)`;
    ///   the haptic plays iff the selected window is not `frontWindow`, which covers restoring a minimised one and every
    ///   row when every window is minimised. Lifting on the front window therefore restores the order, silently.
    public func lift(now: FrontmostWindows) -> WindowLift { … }
}
```
"Closed" = in neither `now`'s visible nor minimised lists. "Another app" = `now.app` differs from the switcher's `app` (compare however `AppEntry` identity is compared elsewhere, e.g. bundle identifier/equality).

### The model (`Launcher.windowSwipe(_:)`)

The final handler (S2 built begin/moved/clearing; this slice adds the raise on move and the lift). Keep whatever S2 named things; the logic is:

```swift
case .moved(let travel):
    guard case .windows(var open)? = shown, open.trackpad == event.trackpad else { return }
    let crossed = open.selection.follow(travel)
    shown = .windows(open)
    for _ in 0..<crossed { hardware.playFeedback(.lightTick, on: event.trackpad) }
    // Only a visible window comes forward while sliding: raising a minimised one would restore it (R10).
    if crossed > 0, let window = open.selectedVisibleWindow { system.raiseWindows([window]) }
case .ended:
    guard case .windows(let open)? = shown, open.trackpad == event.trackpad else { return }
    shown = nil
    // A message row has nothing to switch: silent, and nothing is read (R13, R14).
    guard open.listsWindows else { return }
    // The second read: the plan follows the windows as they are now, whatever the raises while sliding did.
    let lift = open.lift(now: system.frontmostWindows())
    if lift.playsHaptic {
        hardware.playFeedback(.gesture, on: event.trackpad)
        window = .closed        // the launcher window closes, as the swipe's lift does (whatever the model calls it)
    }
    system.raiseWindows(lift.raises)    // always called on a listing lift, [] included (tests count calls)
case .cancelled:
    // The windows stay as they are: no reordering, silent (R15).
    if case .windows(let open)? = shown, open.trackpad == event.trackpad { shown = nil }
```
Never call `playLaunchAnimation` from this handler.

### The platform adapter (`LauncherPlatform/FrontmostAppWindows.swift`, from S2)

```swift
func raise(_ frontToBack: [WindowID]) {
    // Unanswering listing (a read or an earlier raise hit cannot-complete) → nothing. For each id, last first:
    // unlisted by the latest read → skip; kAXRaiseAction on its element (it restores a minimised window);
    // kAXErrorInvalidUIElement (closed) → skip; kAXErrorCannotComplete → mark the listing unanswering and stop.
}
```
`read()` keeps `[WindowID: element]` for the listed windows (replacing the previous read's map) and whether the listing is unanswering. `WorkspaceActions.raiseWindows(_:)` → `windows.raise(_:)`.

### The fake (`RecordingSystemActions.windows: FakeWindows`, LauncherCoreTests)

Add raises: it does what `AXRaise` does and nothing more. `raiseWindows` logs each call in `raised: [[WindowID]]` (every call, empty ones included), then, unless `answers == false` or `dropsRaises == true`, raises its ids last first, each to the front of the visible stack, restoring a minimised one (moving it from minimised to the front of visible), skipping closed ids and ids the latest read did not list. Add `dropsRaises` (raises are logged and change nothing: an app that ignores them). `frontmostWindows()` keeps answering from the stack, so a second window swipe sees the first one's order.

## Rules that apply

- `docs/architecture.md` Shape: "Policy lives in pure functions and value types; the shell stays thin." "Every port has exactly two adapters." "`LauncherCore` … imports Foundation and Observation only."
- `docs/architecture.md` Concurrency: "A window swipe reads the frontmost app's windows and raises them through the Accessibility API on the main actor: synchronous calls into another app, about a millisecond each, each bounded by a short messaging timeout, after which that app gets no further raises until it is read again."
- `docs/architecture.md` Privacy: Accessibility "is used only to … list, raise and restore the frontmost app's windows during a window swipe." "The … Accessibility element API with the window list … [is] confined to one file by the source-scan test." Core comments must not spell `AXUIElement` or `CGWindowList` (the scan reads comments).
- `docs/domain-model.md` Window switcher: "Each time it lands on a visible window, that window comes to the front with the keyboard focus, behind the window switcher; a minimised window is not restored while sliding. Lifting leaves the selected window in front with the keyboard focus, restoring it if it is minimised, and orders the windows: the selected window, then the front window, then the others as before; the gesture haptic plays when the window in front differs from the front window or a minimised window was restored, and otherwise the lift is silent. … lifting on a closed window leaves the windows as they are."
- `docs/domain-model.md` Feedback: "A swipe or window swipe lift … that changes nothing is silent: … a window swipe lift on the front window, on a "No open windows" or Accessibility row, or on a window that closed while the front window is still in front; a cancelled window swipe." Launch animation: "a swipe, a window swipe and a swap never do."
- Source scan hazards: identifiers or comments containing `Timer`, `print(`, `dump(`, `KeyDown`, `keyDown`, `scrollWheel`, `asyncAfter`, `Task.sleep` fail the build.
