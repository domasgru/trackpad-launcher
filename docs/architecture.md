# Architecture

The decisions that hold across the whole codebase. Feature-level decisions live in their plan under `plans/` and then in the code.

## Language, platform, toolchain
- Swift 6 language mode with complete strict concurrency, on the Xcode 26 toolchain (macOS 26 SDK). Deployment target macOS 26, universal binary (arm64 + x86_64).
- Build: a local SwiftPM package holds every library and test target; an xcodegen-generated Xcode project builds only the app bundle (Info.plist, resources, hardened runtime, signing, archiving). `swift test` runs the whole behavioural suite; `xcodebuild` is used only for the bundle.
- Tests use Swift Testing.

## Shape
- One `@MainActor @Observable` model owns every decision. Platform adapters sense and act behind small ports; the AppKit/SwiftUI shell renders the model's state and forwards user intents. Policy lives in pure functions and value types; the shell stays thin.
- Modules by ownership, not by execution order: `LauncherCore` (domain types, pure policy, ports, the model; imports Foundation and Observation only), `LauncherPlatform` (the real adapters over AppKit, Core Animation, IOKit, CoreGraphics (the window list), CoreServices (FSEvents, MDItem), ServiceManagement, the Accessibility element API, two private LaunchServices functions, one private Accessibility function and the private MultitouchSupport framework), `LauncherUI` (menu bar shell and SwiftUI views, plus the window previews it captures with ScreenCaptureKit, a rendered asset like the icons it draws), and the app target (composition root only).
- Framework and wire types never cross a port: `MTTouch`, `CFTypeRef`, `CGEvent`, `CFMachPort`, `UserDefaults` keys, `NSRunningApplication`, `NSImage` stay inside adapters and views. External data is parsed into domain types at the adapter.
- Every port has exactly two adapters: the real one in `LauncherPlatform` and an in-memory one in the tests. Concrete types that can be pointed at a temp directory or a throwaway `UserDefaults` suite are not put behind a port, unless they deliver asynchronously: those sit behind a port so the model's tests stay synchronous.

## Concurrency
- `LauncherCore` and `LauncherPlatform` are nonisolated by default; the model, the ports and the public surface of every real adapter are `@MainActor`. `LauncherUI` and the app target use main-actor default isolation.
- Multitouch frames are recognised on the framework's own thread; only recognised events hop to the main actor: a fired tap, a swap, and the begin, moves and end of a swipe or of a slide up or down that may be a window swipe, in frame order on the main queue and never from a session a later `run` replaced. One thing hops back: the model's answer to a window swipe's start, whether the slide is a window swipe, which only the main actor can tell because it reads the frontmost app's windows. The model gives it while it handles the start; the adapter replies once that call returns, and the frame thread hands the reply to that trackpad's recognizer before its next frame. The recognizer ignores an answer to any other start. Until the answer arrives the slide blocks only by the thumb rules, and the frame thread never waits for it. State shared with that thread lives behind a `Mutex` with one writer.
- Work that would delay a click (folder scans, Spotlight reads, icon drawing) runs off the main actor in explicitly concurrent functions, including inside `LauncherUI`; only its results hop back. The first scan and the first icon pass are the exception: they run, and are waited for, before the run loop starts, so no click can arrive before their results exist. The other exception is `AppIcons.iconDrawingIfMissing(for:)`, which draws a missing icon on the main actor, but only for the closed button showing a row app outside the list that was just picked through Other…. The launch overlay likewise draws an icon at gesture time only when its off-main pass has not drawn one yet (the app moved, or a sharper display was connected since). The switcher's icons are drawn before any swipe: every running Dock app's in the first icon pass at start, and each newly launched app's off the main actor on the workspace's launch notification, again on an appearance change; a swipe begins by reading the running apps from LaunchServices, a few milliseconds at most, and draws an icon on the main actor only for an app whose pass has not finished yet or that no pass covers (a frontmost menu bar app, from the running app's already-loaded icon). With the swipe setting off nothing is drawn or observed for the switcher. Every slide up or down reads the frontmost app's windows when it starts, and a window swipe raises them, through the Accessibility API on the main actor: synchronous calls into another app, about a millisecond each, each bounded by a short messaging timeout, after which that app gets no further raises until it is read again; the window list's first call in the process (about 50 ms) is paid off the main actor at launch. Window previews are captured off the main actor inside `LauncherUI`, and only the pictures hop back.
- No timers, no polling, no background loops: every input is a push (frames, cfprefs KVO, IOKit notifications, workspace notifications, the TCC Darwin notification, FSEvents for the app folders, user events). This is what keeps idle CPU at zero. The one extra thread is the click tap's run loop, which exists only while click blocking is armed and sleeps until an event arrives (a press, its drags and pressure, a scroll event, or a system gesture event).
- Animation is Core Animation keyframes, which the render server plays. Whatever an animation leaves behind is cleaned up from its completion callback. No code of ours runs per frame, and display links are banned along with timers.
- Developer tools live in `#if DEBUG` and never ship. Today that is the launch animation tuner in `LauncherPlatform`: a SwiftUI window over `LaunchTuning`, whose defaults are the shipped animation.

## Privacy and permissions
- The app may ask for two permissions, both optional. Accessibility, asked for on first launch, is used only to block trackpad clicks, suppress trackpad scrolling and block the system's desktop and Mission Control swipes during gestures, to list the frontmost app's windows when two fingers start sliding up or down under the thumb, and to raise and restore them during a window swipe. Screen Recording, asked for only from the screen recording hint's button and never by a gesture, is used only to take one picture of each listed visible window when a window swipe begins; the pictures are kept in memory and dropped when the window swipe ends, never streamed, recorded, encoded or written to a file. The app never asks for Input Monitoring or any other permission and never reads keyboard events. Without Accessibility everything works except click blocking, scroll suppression, Dock swipe blocking and switching windows; without Screen Recording the window switcher shows app icons instead of previews. The permission checks and their TCC push, the Accessibility element API with the window list, screen capture, the event tap and the scroll-event API are each confined to one file by the source-scan test.
- Trackpad touches come from `MultitouchSupport.framework` via `dlopen` (no link flags, no entitlements, no permission); it is Apple-signed, so the hardened runtime needs no library-validation exception. The ⌘-Tab order comes from two private LaunchServices functions resolved with `dlsym` from the LaunchServices already loaded (no link flag, no permission), confined to one adapter file by the source-scan test; when either is missing, the order falls back to the app in front at launch and the activations observed since, then launch order. A window's number comes from the private `_AXUIElementGetWindow`, resolved the same way and confined to the window adapter's file; when it is missing, windows are matched to the window list by their frames, and a window that matches none is not listed.
- No network code of any kind, no logging of any kind (`print`, `NSLog`, `os_log`, `Logger`), no files written other than settings in `UserDefaults`. A source-scan test in `LauncherCoreTests` fails the build on any banned API; add to its list rather than adding prose.

## Distribution
- Direct download only, signed with Developer ID, hardened runtime, notarized with `notarytool` and stapled. Never sign with `--deep`; the main executable is signed last.
