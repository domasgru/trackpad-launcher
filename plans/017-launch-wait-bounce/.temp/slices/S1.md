# S1: Prefactor: shared flight staging, set-valued confinement, launch probes

## Goal

Nothing the user sees changes. This slice prepares the ground for the launch bounce (a later slice): the launch animation can start from any point among a given set of displays; the overlay's icon cache and panel recipe become reachable from other files in `LauncherPlatform`; the rule for "which display holds the pointer" is shared; the source scan can confine a token to several files; and the platform tests gain scripted throwaway `.app` bundles they can launch and clean up.

Context for why (the feature this prepares): when a gesture fires for an app that is not running, its icon will bounce above the pointer until the app's window shows, then play the existing launch animation *from wherever the bouncing icon is*. That needs `LaunchOverlay.play(for:from:among:)`. The later platform tests launch real throwaway apps whose startup is scripted (slow start, window at finish, late window, splash, menu bar app, crash, missing executable), which needs the probe executable and the bundle helper built here.

## Requirements

None (prefactor). The existing behaviour of the launch animation must be unchanged.

## Design

### `ScreenRead` (new, `LauncherPlatform`, e.g. in `LaunchOverlay.swift` or its own file)

```swift
/// Where the pointer is and which displays exist, read now: what a bounce reads when it starts and on every move.
struct ScreenRead {
    let pointer: CGPoint
    let displays: [LaunchDisplay]
    /// `NSEvent.mouseLocation` and `NSScreen.screens`.
    @MainActor static func now() -> ScreenRead
}
```

`now()` maps `NSScreen.screens` to `LaunchDisplay(frame: $0.frame, scale: $0.backingScaleFactor)`, exactly as `LaunchOverlay.play(for:)` does today.

### `LaunchDisplay.containing` (moved from `LaunchFlight`)

```swift
extension LaunchDisplay {
    /// AppKit's rule for the pointer's display, else the nearest; moved here from `LaunchFlight.display(for:among:)`.
    static func containing(_ point: CGPoint, among displays: [LaunchDisplay]) -> LaunchDisplay?
}
```

Same body as today's private `LaunchFlight.display(for:among:)` (plus its `distance` helper). `LaunchFlight.staged(at:among:)` calls it. Both the flight and, later, the bounce row use it.

### `LaunchOverlay` changes

```swift
extension LaunchOverlay {
    /// As `play(for:)`, staged at `start` among `displays` instead of at the pointer among `NSScreen.screens`: a
    /// bounce's ending, from wherever its icon is, among the displays the bounce read, so one `ScreenRead` places
    /// both. `play(for:)` becomes `play(for: app, from: read.pointer, among: read.displays)` with `ScreenRead.now()`.
    func play(for app: AppEntry, from start: CGPoint, among displays: [LaunchDisplay])
    // bitmap(for:scale:) and static makePanel(frame:) become internal: one icon cache and one panel recipe.
}
```

- `play(for:)` keeps its signature and its behaviour; it becomes a one-liner over `ScreenRead.now()` and `play(for:from:among:)`.
- `play(for:from:among:)` holds today's body (Reduce motion read, `flights.next`, `staged(at: start, among: displays)`, panel, transaction).
- `bitmap(for:scale:)` and `makePanel(frame:)` lose `private` (become internal). Nothing else about them changes.

### `SourcePolicyTests` (`LauncherKit/Tests/LauncherCoreTests/SourcePolicyTests.swift`)

- `Confined.onlyIn` becomes `Set<String>`; every existing entry keeps its meaning (one-element sets). `testDescription` and the failure message still name the file(s) readably.
- `scan(_:for:outside:)` skips every file whose name is in the set.
- The existing self-test `confinedScanFindsAUseOutsideItsFile` still passes (adapt it to the set). It is good to also show that a token allowed in two files is found in a third and not in either of the two.
- Do not add the new launch-bounce confinements yet (later slices add `LaunchWatch.swift`, `BounceOverlay.swift` entries when those files exist).

### Launch probe executable (test-only)

A tiny AppKit app whose startup is scripted, used by later platform tests as the "app being launched". Its model is the architect's probe at `plans/017-launch-wait-bounce/.temp/architect/grounding/probes/p1-probe-app.swift` (read it), which took its script from launch arguments. Differences required here:

- The script is read from a key in the bundle's `Info.plist` (for example `ProbeScript`, a dictionary or string array), because the code under test opens apps with `NSWorkspace.openApplication` and passes no launch arguments.
- P1's scripts: pre-sleep S seconds before `NSApplication` runs (slow start); crash (exit) after S seconds before finishing launching; window in `applicationWillFinishLaunching`; window in `applicationDidFinishLaunching`; window S seconds after did-finish; borderless splash at did-finish (with a later main window); no window at all. A menu bar app is the same executable with `LSUIElement` true in its Info.plist.
- Three new scripts:
  1. block the main thread inside will-finish (for S seconds);
  2. on the first main-run-loop turn after finishing, write a marker file (path given in the script), then block the main thread for S seconds, then open a window;
  3. open its only window at the status-window level (`NSWindow.Level.statusBar`).
- Where it lives: outside the scanned roots (`LauncherKit/Sources` and `TrackpadLauncher/` are scanned for banned APIs like `asyncAfter`, `Timer`, `Task.sleep`; the probe may use them, so it must not live there). For example an `.executableTarget(name: "LaunchProbe", path: "Tests/LaunchProbe")` in `LauncherKit/Package.swift`, with `LauncherPlatformTests` depending on it so `swift test` builds it. The test helper finds the built binary next to the test bundle in the build products directory. Choose the mechanism that works with plain `swift test` (that is the repo's gate, `Scripts/test.sh`); verify it.
- It must not be part of any product the app ships (no `.library` product, not referenced by `project.yml`).

### Probe bundle helper (test-only, in `LauncherPlatformTests`)

- Builds one throwaway `.app` bundle per script, in a fresh temp directory: `Contents/MacOS/<exe>` (a copy of the built probe binary), `Contents/Info.plist` with a **fresh bundle ID** each time (e.g. `com.trackpadlauncher.test.probe.<uuid>`), `CFBundleExecutable`, `CFBundlePackageType APPL`, optional `LSUIElement`, and the script key. Also can build a bundle **without its executable** (for the "macOS refuses to open it" case).
- Cleanup when its test ends, even if an expectation failed: quit (terminate, then force-terminate if needed) every running instance of each bundle ID it built, unregister each bundle from LaunchServices (`/System/Library/Frameworks/CoreServices.framework/Frameworks/LaunchServices.framework/Support/lsregister -u <path>`), and delete the temp directory. Look at how `World` (`Tests/LauncherCoreTests/World.swift`) removes its temp folder and how existing platform tests (`SystemAppScannerTests.swift`, `SystemTrackpadPreferencesTests.swift`) handle cleanup for the idiom; a scoped helper (`withProbes { ... }`) or a class with `deinit`/explicit `cleanUp()` in `defer` are both fine.
- Ad-hoc signing (`codesign -s - --force`) of the copied bundle may be needed for `openApplication` to launch it on this Mac; verify by launching one.
- Add one small smoke test that proves the helper works end to end: build a bundle with a window-at-did-finish script, launch it with `NSWorkspace.shared.openApplication(at:configuration:)`, await its `NSRunningApplication` reaching `isFinishedLaunching` (await a push, e.g. KVO or the completion, bounded by a few seconds; never poll in a loop with sleeps if avoidable), then let cleanup run and assert the process is gone and the bundle directory deleted. Mark any suite that launches apps `.serialized`.

## Rules that apply

- `docs/architecture.md`, Shape: "`LauncherCore` (domain types, pure policy, ports, the model; imports Foundation and Observation only)". Nothing in this slice touches `LauncherCore` sources.
- `docs/architecture.md`, Privacy: "No network code of any kind, no logging of any kind (`print`, `NSLog`, `os_log`, `Logger`), no files written other than settings in `UserDefaults`. A source-scan test in `LauncherCoreTests` fails the build on any banned API." This applies to the scanned roots (`LauncherKit/Sources`, `TrackpadLauncher/`). The probe and test helpers are outside them, which is why the probe must not live under `Sources`.
- `docs/architecture.md`, Concurrency: "No timers, no polling, no background loops" applies to shipped code. Tests await pushes with a bound rather than polling, as `SystemTrackpadPreferencesTests.swift` and `SystemAppScannerTests.swift` do.
- `docs/architecture.md`, Language: "Swift 6 language mode with complete strict concurrency … Tests use Swift Testing."
- Keep the launch overlay's comments' and doc comments' style: plain sentences saying what holds, as in the existing file.
