# Grounding index: plan 017, launch bounce

Start here. Every fact a design decision rests on, with its standing. `probed` = what a probe printed on this Mac (macOS 26.6.2, M3 Pro, one display) on 2026-10-19, naming the probe; `sourced` = the file and heading that state it; `disputed` = both sides. A conclusion drawn from a probe is labelled **Conclusion**.

Skill runs: `how` ran (four explorers + explainer: `how.md`, `how-fire-path.md`, `how-overlay.md`, `how-tuner.md`, `how-lifecycle.md`). `why` ran (`why.md`, ending in a Preserve / Change / Avoid / Risk constraint set; raw evidence in `why-plans.md`, `why-source-control.md`). Not greenfield.

Probes live in `probes/` (Swift sources; build with `swiftc -O`). They were run from a scratch directory outside the repo; the throwaway `.app` bundles they launched were unregistered from LaunchServices and deleted, and every app they launched was quit.
- `p0-environment.swift`: displays, permission preflights, Reduce motion.
- `p1-probe-app.swift` + `p1-lifecycle.swift`: a tiny app whose startup is scripted by launch arguments, and an observer that launches an app exactly as `WorkspaceActions.bringToFront` does (`openApplication`, `activates = true`) and timestamps every push signal against the first on-screen window (the observer polls the window list every 2 ms for measurement only). Runs: (1) 1 s slow start, window at did-finish; (2) window 1.5 s after did-finish; (3) LSUIElement menu bar app, no window; (4) exits 0.5 s in, before check-in; (5) bundle with no executable; (6) second `openApplication` 150 ms into a slow launch; (7) window in will-finish (like state restoration); (8) borderless splash at did-finish, main window 1 s later; (9) Obsidian (Electron), real cold launch.
- `p2-pointer-follow.swift`: global and local NSEvent monitors for moves and drags; 60 zero-motion synthetic moves; cost of moving a panel or a layer.
- `p3-ca-clock.swift`: Core Animation completions as a clock.
- `p4-running-check-cost.swift`: cost of the "is it running" read.

## Facts

### The fire path today
- **F1** `sourced` (`how.md` §1; `how-fire-path.md` B): `Launcher.fire` runs, in one synchronous main-actor turn: guards (active, assigned, `catalog.locate` reads Info.plist) → `hardware.playFeedback(.gesture)` → `system.bringToFront(app)` → `if settings.isLaunchAnimationOn { system.playLaunchAnimation(for: app) }` → `window = .closed`. Plan 004 reads R1's "no later than the haptic" as "issued in the same main-actor turn as the pulse, with nothing slow in the way" (`why.md` (4)). The animation comes after bring-to-front so its cost never delays the app (004 R13, comment at `Launcher.swift:241`, test T1 via the `onPlayLaunchAnimation` hook).
- **F2** `sourced` (`how-lifecycle.md` A.4): `WorkspaceActions.bringToFront` calls `NSWorkspace.openApplication(at:configuration:)` with `activates = true` and no completion handler, for running and non-running apps alike. The pid and any launch error are never learned.
- **F3** `sourced` (`how-fire-path.md` "How the model knows"): `fire` never asks whether the app runs. `SystemActions.runningApps()` is the ⌘-Tab list (`ApplicationType == "Foreground"` / `.regular`), so a running menu bar app reads as not running. Assigned-vs-running identity precedent is the bundle ID (`Switcher.init`, `assignedBundleIDs`); URL equality between a catalog `AppEntry` and a running one is not guaranteed.
- **F4** `sourced` (`how.md` "Contracts" 1; `why.md` (2)): `playLaunchAnimation` is fire-and-forget: returns at once, reads pointer/displays/Reduce motion itself, ~0.34 s, removes itself, "every call plays its own and never cancels, restarts or reuses one already playing" (004 R14, `docs/domain-model.md` Launch animation, test `repeatedTapsWhileTheThumbStaysAnchoredFireEachTime`). The launch animation setting is enforced in the model only (plan 005).
- **F5** `sourced` (`how-overlay.md` A–D): one click-through `NSPanel` per play (`.borderless, .nonactivatingPanel`, `.screenSaver`, `ignoresMouseEvents`, `[.canJoinAllSpaces, .fullScreenAuxiliary, .stationary, .ignoresCycle]`), sized to the flight's reach ∩ the pointer's display (clipped, never slid), icon centred on the tip, closed from the `CATransaction` completion; `playingPanels` keeps panels alive. Icons are prepared off-main at the pop peak (72 pt) × highest backing scale into `[URL: CGImage]`; a miss renders synchronously on the main actor. Pure staging (`LaunchFlights`, `LaunchFlight.staged(at:among:)` which already takes a start point, `LaunchDisplay`) is tested in `LaunchFlightTests` by decoding keyframes back into samples and asserting requirement bounds, not formulas. `LauncherCore` may import only Foundation and Observation, so animation geometry lives in `LauncherPlatform`.
- **F6** `sourced` (`how-overlay.md` "Existing idioms"; `how.md` §4): `LauncherUI/OverlayPanel.dismiss` fades from `layer.presentation()?.opacity` with a generation counter guarding stale completions: the existing "continue from the in-flight value" precedent.

### Is the app running (R1, R2, R14)
- **F7** `probed` (P1 runs 2, 4, 6, 7, 9; P4): `NSRunningApplication.runningApplications(withBundleIdentifier:)` lists a launching process 60–440 ms after `openApplication`, before the app checks in, with `isFinishedLaunching == false`. Cost: 1.65 ms on the first call in a process, under 0.1 ms afterwards. **Conclusion:** it answers R1/R2 "macOS reports a process" for an app launching from the Dock; but for the first 60–440 ms after our own `openApplication` it still says "not running", so R14 (same app fired again) cannot rest on it and needs the model's own record of live bounces.
- **F8** `probed` (P1 run 6): a second `openApplication` 150 ms into a launch starts no second instance; its completion arrives when the app finishes launching, with the same pid. **Conclusion:** R14's "asks macOS to open the app again, which changes nothing visible" holds.

### Launch lifecycle signals (R9–R12)
- **F9** `probed` (P1 all runs): `openApplication`'s completion runs off the main thread, when the app checks in (NSApplication start), not at spawn: 118–1838 ms after the call, with `isFinishedLaunching == false`. The `willLaunch` notification and the `NSWorkspace.runningApplications` KVO insert arrive at the same moment. Before it, the adapter holds no `NSRunningApplication` to observe.
- **F10** `probed` (P1 run 5): a bundle that cannot launch → completion with `error` (NSCocoaErrorDomain 259, "could not be launched because it is corrupt") after 236 ms, no app.
- **F11** `probed` (P1 run 4): a process that exits before checking in → completion with a terminated `NSRunningApplication` (pid -1) and no error; `didTerminate` (regular apps) and `isTerminated` KVO also fire. **Conclusion:** the completion must be read as "failed" when it carries an error or a terminated app.
- **F12** `probed` (P1 runs 1, 2, 3, 7, 8, 9): finishing launching is pushed for every app by KVO on `NSRunningApplication.isFinishedLaunching`; quitting by KVO on `isTerminated`. The `didLaunch`/`didTerminate` notifications fire for regular apps only.
- **F13** `probed` (P1 run 3): an LSUIElement menu bar app gets **no** `willLaunch`, `didLaunch`, `didActivate` or `didTerminate` notification; only the completion, the `runningApplications` KVO, and `isFinishedLaunching` / `isTerminated` KVO.
- **F14** `probed` (P1 runs 2, 6, 7, 8, 9): `didActivate` / `isActive` arrives early (118–355 ms), before finishing launching and long before a late window. **Conclusion:** activation is not a window signal.
- **F15** `probed` (P1 runs 1, 7, 8): windows an app makes before or at finishing launching come on screen at the finish moment, within ~1 ms of `didLaunch` / the `isFinishedLaunching` KVO (in run 7 the window reached the window list 0.6 ms after `didLaunch`).
- **F16** `probed` (P1 all runs, Accessibility trusted in the probe's context): `AXObserverAddNotification` on the launching pid fails with `kAXErrorCannotComplete` (-25204), quickly, until about the moment the app finishes launching; in every run it first succeeded within ~0–10 ms of the `isFinishedLaunching` KVO (before it in runs 2, 3, 6, 7, 9). Right after registering, a one-shot `kAXWindowsAttribute` read returned 1 whenever a window had been made during launch (runs 1, 6, 7, 8: splash included), ~1–7 ms before that window was on screen, and 0 otherwise.
- **F17** `probed` (P1 runs 2, 8, 9): for a window made after finishing launching, `kAXWindowCreatedNotification` arrives 1–9 ms before the window is on screen (Obsidian, Electron: 1.3 ms before); `kAXFocusedWindowChanged` / `kAXMainWindowChanged` a little earlier. Every created window reported role `AXWindow`, subrole `AXStandardWindow`.
- **F18** `sourced` (`how-lifecycle.md` "Source-scan confinement"; `how.md` Contracts 7; `docs/architecture.md` Privacy): `AXUIElement` and `CGWindowList` are confined to `FrontmostAppWindows.swift` by `SourcePolicyTests` (substring match by file name); the process-wide AX messaging timeout is 0.2 s (`FrontmostAppWindows.init`), so a call into a hung app can block the main actor that long; the Privacy section lists the only uses of Accessibility, and watching a launching app's windows is not among them.
- **F19** `sourced` (`how-lifecycle.md` "What exists"; Apple: `CGWindowListCopyWindowInfo` is a snapshot): there is no public push for "a window showed" except an `AXObserver`, which needs Accessibility (optional in this app). **Conclusion:** without Accessibility, only windows present at the finishing-launching push can be seen (by a one-shot read, racy per F15), and a later window can only end the bounce through R10's 2 s rule.

### Pointer following (R5–R7, R13, R16)
- **F20** `probed` (P2): an NSEvent global monitor for `.mouseMoved` and the drags installs and delivers in a process without Input Monitoring (`CGPreflightListenEventAccess` false): 37 of 60 zero-motion synthetic moves arrived (identical positions coalesce), median 3.5 ms (p90 4.2 ms) from the event's timestamp to the handler. A global monitor does not see events sent to our own windows (the launcher window, the Debug tuner): a local monitor covers those. (`docs/performance.md` Known limits: a listen-only *event tap* recorded nothing without Input Monitoring; the NSEvent monitor is a different route.) `MenuBarShell` already uses a global NSEvent monitor for mouse downs, installed only while the window shows.
- **F21** `probed` (P2): moving an 84×120 click-through panel with `setFrameOrigin` costs 0.057 ms per move; moving a layer in a display-sized panel with commit + flush 0.038 ms. **Conclusion:** following at ~120 events/s costs well under 1% of a core while a bounce shows. How far the icon visibly trails the hardware cursor cannot be measured by a probe.
- **F22** `probed` (P0): this Mac has one display (1512×982 @2x), `screensHaveSeparateSpaces` false. Moving onto a second display (R7) cannot be probed here.

### Time without timers (R10, R12, R18)
- **F23** `sourced` (`why.md` (1); `SourcePolicyTests.swift:30-35`): `Timer`, `asyncAfter`, `Task.sleep`, `makeTimerSource`, `displayLink`, `DisplayLink` are banned by case-sensitive substring over `LauncherKit/Sources` and `TrackpadLauncher/`, comments and `#if DEBUG` included. The origin is plan 001 R22, zero idle CPU; the display-link ban is plan 004's ("a per-frame callback … would run code of ours on every frame"). Plan 001 rejected an injected `Clock`; no plan ever had a deadline longer than the AX messaging timeout. The model has no clock; tests never wait in real time.
- **F24** `probed` (P3): a Core Animation animation's delegate fires 1.1–1.3 ms late for a 2 s animation on a layer in a visible panel or in an alpha-0 panel; a repeating keyframe with `repeatDuration` 2 s ends 0.7 ms late; on a layer in no window the animation stops at once with `finished == false`; removing an animation fires its delegate with `finished == false` at the next commit. **Conclusion:** a CA animation is a precise deadline only on a layer inside an ordered-in window.

### Tuner and presets (R17–R19)
- **F25** `sourced` (`how-tuner.md`): `LaunchTuning` is one flat struct of `Double`/`Bool` knobs whose defaults are shipped; `current` reads `tunerOverride` (a `Mutex`) in Debug, `shipped` in Release. Debug-only `Codable` with a hand-written `init(from:)` using `decodeIfPresent ?? shipped` per key; a missing decode line is not a compile error. A wrong-typed key drops the whole preset list; a renamed key silently drops its saved value. The saved presets on this Mac hold only the 15 flight keys (no `swipe*`), proof old presets are loaded today. The `knob` helper takes `WritableKeyPath<LaunchTuning, Double>` (nested paths work). The tuner's one preview closure plays Finder through the overlay, bypassing `Launcher`. `TunerModel.preview(_:play:)` swaps the override, plays, and restores at once, so anything that reads `LaunchTuning.current` after `play` returns sees the live tuning: a seconds-long bounce must snapshot its tuning when it starts. Debug builds play the last saved tuner state, not shipped (the plan 014 incident).

### Testing
- **F26** `sourced` (`how.md` "How tests drive this"; `how-fire-path.md` tests): model tests build `World` (real `Launcher`, in-memory adapters, temp bundles, throwaway defaults), call `world.tap(n)` which runs synthetic frames through the real recognizer inline. Push ports are `var on…: (@MainActor (…) -> Void)?` set in `Launcher.start()`; fakes call them inline. `RecordingSystemActions` records `broughtToFront`, `launchAnimations`; ordering is asserted with an in-call hook. Every port has exactly two adapters (real + in-memory); asynchronously delivering things sit behind a port so model tests stay synchronous.

## Disputed
- **D1 What "no code of ours runs per frame" forbids.** For "input-driven updates are fine": plan 006 grounding F27 and plan 006:1338, and the switcher's per-trackpad-frame `SwitcherPanel.show` accepted in `docs/performance.md`. For "nothing of ours runs while an animation shows": the literal `docs/architecture.md` Concurrency text and plan 004 "Once the last panel has closed, no code of ours runs." (`why.md` Competing Hypotheses.) The design must say which reading it uses and Phase D writes it into `docs/architecture.md`.
- **D2 Reading pointer movement.** Against: plan 002 R9 ("MUST NOT read, record or change keyboard input, scrolling, pointer movement or any other event"); plan 006 T76 pins `.mouseMoved` parsing to nil in the click tap. For: the human asked that the bouncing icon follow the cursor; today's `docs/architecture.md` Privacy text forbids reading keyboard events, not pointer position, and scrolling is already read (later plans superseded 002 R9's scroll clause). Needs an explicit Privacy line and the human's sign-off.
- **D3 AX observers for Electron/Chromium.** Plan 012 rejected AX window observers ("Chromium and Electron trees are unreliable observers") for a pushed window *count* on the frontmost app. P1 run 9: Obsidian (Electron) delivered `kAXWindowCreated` 1.3 ms before its window was on screen. One sample; Chrome/Figma/Slack not tried (running, or not to be disturbed).
- **D4 How to keep time.** Core Animation as the clock (house style for time, `why.md` Preserve/Avoid; F24 shows it precise, but only on a layer in an ordered-in window) versus a deadline behind a port with a real adapter on a dispatch deadline (contradicts F23's letter and scan, but not R22's idle-CPU rationale if it exists only while a bounce lives). Either way the model's tests need a handle on time.

## What a test can produce for real, and what needs a fake or a manual check
- **Real, in `swift test`, synchronous**: every model decision through `World` (bounce vs launch animation vs nothing; R1–R3, R14; row order R13; which ending R9–R12 picks), with an in-memory adapter that pushes lifecycle events inline and a test-controlled clock or deadline push (tests never wait in real time, F23, F26). Pure geometry and keyframes in `LauncherPlatformTests` in the `LaunchFlightTests` style: rest spot (R5), top clip and side slide (R6), row layout and slide (R13), bounce height/period/shape and squash (R8), Reduce motion pulse (R15), hand-off from a mid-jump point (R9), knob effects (R17). Tolerant decoding against a real old preset JSON (R19). The source-scan test for any new confinement or ban.
- **Real on this Mac, heavier**: the real lifecycle adapter against throwaway `.app` bundles with scripted startup (the P1 technique: window at finish, late window, splash, menu bar app, crash before check-in, missing executable), launched with `openApplication`; AX parts need the test process to be trusted (true in this terminal context, F16). Bundles must be unregistered (`lsregister -u`) and deleted afterwards.
- **Fake only**: the 10 s cap, the 2 s grace and the 3 s preview in model tests (no waiting); a missing or late AX answer; Accessibility off.
- **Manual**: visible lag behind the hardware cursor (R7); feel against the Dock (R8); sharpness at every height (R4); a second display (R7; this Mac has one, F22); clicks through the icon (R16); Reduce motion's look (R15); the Gatekeeper first-launch dialog (R11); real Figma/Slack/Xcode cold launches; a window opening on another Space (R10).

## Open questions
- **O1** Without Accessibility (optional in this app), R9 cannot be met for windows that show after finishing launching (F19). Degrade to R10's 2 s rule, plus a one-shot window read at the finishing push? Needs the human's acceptance.
- **O2** Where time comes from for the 2 s grace, the 10 s cap and the 3 s preview (D4).
- **O3** The pointer-movement privacy line (D2) and the per-frame reading (D1): design decision plus Phase D doc change.
- **O4** Does `kAXWindowCreatedNotification` fire for a window that opens on another Space? Not probed (one Space, one display). If it does, such an app would float away rather than wait out R10's 2 s.
- **O5** What the completion reports while the Gatekeeper "are you sure" dialog is pending or after it is declined (R11 scenario accepts running to the 10 s cap either way). Not probed: it needs a quarantined download.
- **O6** Second display behaviour (R7), not probed here (F22).
- **O7** AX registration is first possible only at about finishing launching (F16); a non-Cocoa app (Java, Qt) may answer later. Should the adapter retry registration on later pushes it already receives (activation, the completion), and what happens if every try fails (R10's 2 s rule)?
- **O8** A call into a hung launching app can block the main actor up to the 0.2 s AX messaging timeout (F18): acceptable on the bounce path, which is not on the gesture's critical path?
