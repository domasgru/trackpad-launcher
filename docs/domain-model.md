# Domain model

The glossary for Trackpad App. Use these words, with these meanings, everywhere: docs, plans, code, UI.

## Trackpad App
The product. A macOS background app that brings apps to the front with trackpad gestures. It has no menu bar icon; it shows in the Dock and in ⌘-Tab only while its settings window is open, minimised or hidden included. At most one Trackpad App recognises gestures at any moment.

## Login start
Trackpad App started by macOS at login, while starting at login is on. A login start is silent wherever the copy lies: no window, no Dock icon, no dialog and no permission prompt, and the app in front stays in front; gestures work from that moment. It never does the first run's work. A window that was open at logout does not come back. A login start of a copy that can replace its own bundle makes an *update check* and, finding a *newer version*, a *login update*. For the hand tests, a release copy started with `--at-login` reads as a login start.

## Opened by hand
Any other start or opening of Trackpad App: from Spotlight, Finder, Launchpad, the Dock or Xcode, by a move finishing, or by an older version's update card opening the new version. A *hand-over* is not an opening by hand, though one that brings the settings window opens it the same way and makes no update check. Opened by hand from inside /Applications, at any depth, or as a development build, it stops every other running Trackpad App (another build, Debug or release, a copy from another place, the menu bar version) and then runs with its settings window open; opening the running copy again brings that same window to the front, restored if minimised. A release build opened by hand anywhere else shows only the move dialog.

## First run
The first opening by hand on a Mac that holds no saved Trackpad App settings. It turns starting at login on when the copy is inside /Applications, asks for the Accessibility permission when it is missing, and opens the settings window. Later runs never ask for the permission; the Accessibility hint shows instead. The *mixed trackpads* record alone is not saved settings: a Mac that holds only it, recorded by a login start or a start before the first opening by hand, still has its first run.

## Starting at login
Whether macOS starts Trackpad App at login, as *System Settings → General → Login Items* shows it. The first run from /Applications turns it on. *Quit Trackpad App* turns it off when it is on, and the next opening by hand turns it back on only when that Quit turned it off. Trackpad App never turns back on what the user turned off in Login Items, whatever happens. A development build outside /Applications never changes it. Trackpad App never relaunches itself after a crash or a force quit; only a *hand-over* opens it, once, after an update.

## Quit Trackpad App
The red button at the end of the settings window, the only control of the app's own that stops it: at once, with no confirmation, the window and the Dock icon go and no gesture is recognised until it is opened again. It turns starting at login off. Every other way to quit, *Close Settings* (⌘Q) in the app menu and *Quit* in the Dock icon's menu, only closes the settings window. It works at once in any update state: a download dies with the app, nothing restarts it, and the app stays stopped until it is opened. Logging out, restarting and shutting down end Trackpad App without asking and with no delay from an update; they dismiss any *update alert* unanswered. While the update alert asks *Restart Trackpad App to update?*, the Dock's *Quit* does nothing until it is answered.

## Move dialog
The dialog a release build opened by hand outside /Applications shows before anything else: Trackpad App needs to be in the Applications folder, with *Move to Applications* (the default) and *Quit*. It shows in front of the app that was in front, with the keyboard focus. ~/Applications counts as outside. Until it is answered, the copy recognises no gesture, asks for no permission, does not register for login and opens no settings window; a copy already running elsewhere keeps its gestures. *Quit*, or cancelling the administrator prompt, stops it with nothing changed. *Move to Applications* puts the copy in /Applications, replacing and stopping any copy there whatever its version, asking for an administrator's name and password when the account cannot write there; it keeps every setting and starting at login as it was, removes the opened copy where it can (a copy on a disk image stays, and the disk image is ejected unless a file on it is in use), and opens the installed copy. A login start never shows it.

## Development build
A build not signed with a Developer ID, such as a Debug build run from Xcode or the performance build. It never shows the move dialog and runs where it was built; opened by hand, it stops any other running Trackpad App. Outside /Applications it never changes starting at login. It never makes an update check, wherever it lies, even when started with the hand-testing argument that makes it read as a release elsewhere.

## Debug build
A development build of the Debug configuration, as Xcode runs it. Its bundle identifier is the release's with `.debug` appended, `com.domasgru.TrackpadLauncherApp.debug`, so macOS keeps its permission grants, saved settings and starting at login apart from the installed release's: System Settings lists it as its own *Trackpad App*, and allowing one never allows or refuses the other. To the single-instance rule it is the same app: opened by hand it stops a running release copy, and the installed release opened by hand stops it. The performance build is a development build of the Release configuration and keeps the release's identifier, `com.domasgru.TrackpadLauncherApp`.

## Update check
The one kind of request Trackpad App makes on its own: a read of the public update list on GitHub. Only an *update-capable copy* makes it, only while the *automatic updates setting* is on, and at two moments only: at a login start, if it can write to its own bundle, and each time its settings window goes from closed to open. *Update now* and the update alert's *Update* read the list once more before their download, and a *manual check* reads it whatever the setting says. With the setting off, Trackpad App makes no request of its own: the only requests are a manual check, the update alert's *Update*, and a download already under way when the setting was turned off. Nothing runs on a schedule, and a *hand-over*'s start makes no check, window or not. Restoring a minimised or hidden window or bringing it to the front checks nothing; a check still running when the window closes is dropped, and every opening starts without the *update card*. A development build, a copy outside /Applications and a copy showing the move dialog never check. Every request, the download included, is the same on every Mac and every version: a fixed address with no query string of ours, fixed headers that name neither the user, the Mac nor any version, and no cookie. No system profile, setting or usage data is sent. A check that fails is silent; a login start's check that fails for lack of a connection runs again each time a connection arrives, until a check completes or the setting is turned off.

## Newer version
A published full release in the update list, neither a draft nor a pre-release, that:
- has a higher version than the running one, compared by build number, which rises with every release;
- declares a minimum macOS that this Mac meets.

When several are newer, the highest is taken. Trackpad App never installs the same version or an older one.

## Login update
What a login start does, while the *automatic updates setting* is on, when its *update check* finds a *newer version*: it downloads it and installs it the moment the download is prepared, waiting for nothing: not the trackpad, a gesture or the settings window. Gestures may stop for up to 10 seconds. Nothing shows. It installs only when it is genuine: signed with the publisher's update key, and signed with the same Developer ID and bundle identifier as the running copy, and notarised. Otherwise, or when the download fails, nothing installs, nothing shows, and nothing tries again before the next login start, the *update card* or a *manual check*. Turning the setting off while the login start's check still reads the list drops it before anything downloads; a login update already downloading carries on and installs. Opening the settings window during a login update makes no check and shows no card, and the *Check for updates…* button reads *Updating…*; the update carries on, and the *hand-over* then opens the new version with its settings window. The update alert's *Update* clicked during a login update starts nothing new: the running download becomes its download, and the hand-over then opens the new version with its settings window. A copy that cannot write to its own bundle makes no login update: it updates from the card. The update adds nothing to trackpad use: no update code runs for a trackpad frame, in any update state.

At every moment /Applications holds either the whole old version or the whole new one. Every setting, starting at login and the permissions carry over, with no prompt and no first run.

## Update card
The first group of the settings window while the current opening's check has found a *newer version* and the *automatic updates setting* is on: *Update available* above an *Update now* button, with a large tray-and-arrow picture clipped at the card's right side and a thin border. Every opening of the window starts without it, and it never shows for a failed check, with no error either. It is not dismissable and shows no version and no release notes. Its arrow lifts a point, drops 4 points quickly, springs back past its place by a fraction of a point and settles into it, then rests, about every 2 seconds, while the tray stays still; the motion stops while the window is closed, and with the system's Reduce motion setting on the arrow stands still. *Update now* greys the button out as *Updating…*, a *progress label*, downloads the version and installs it the moment the download is prepared, with no progress bar and no cancel, then the *hand-over* opens the new version with its settings window; closing and reopening the window meanwhile shows the card the same way and checks nothing. The card reads *Updating…* the same way through a download the update alert's *Update* started while the card showed; one started while no card showed brings none. A copy that cannot write to its own bundle asks for an administrator's name and password after the download. A download or install that fails, or a cancelled prompt, returns the card to *Update available* with no error while the setting is on, and the running version keeps working; turning the setting off removes a card that offers *Update available* at once, the window resizing to fit, and the card does not return while the setting is off. A *manual check* never adds the card, though one that finds nothing new removes it; an install that fails after the old version stopped brings a working copy back within 10 seconds, with its settings window. Only a genuine update installs, as for a *login update*.

## Update-capable copy
A copy signed with a Developer ID that lies in /Applications, whether or not it can write to its own bundle: the only kind that makes *update checks*. A development build and any copy elsewhere are not update-capable.

## Automatic updates setting
One global setting, on by default, shown as the *Automatic updates* switch in the last row of the settings window's thumb corner group, above the line "Current version: <version>" (the running copy's version, without the build number) and the *Check for updates…* button. While it is on, an *update-capable copy* makes its *update checks* and *login updates* and shows the *update card*. While it is off, Trackpad App makes no network request of its own: the only requests are a *manual check*, the *update alert*'s *Update*, and a download already under way when it was turned off. Turning it off drops a window's check still running, removes an update card that offers *Update available*, ends a failed login check's wait for a connection, and drops a login check still reading the list before it downloads anything; a manual check and a running download carry on, and an *Update now* download that then fails leaves no card. Turning it on checks nothing by itself: checks resume at the next login start or the next opening of the settings window, and a card it removed stays gone until then. A change is saved at once, beside the settings record, so it survives a quit, a force-quit, a Mac restart and an update; a new install and an upgrade from a version without it start with it on, and a version without it, installed over this one, neither reads nor drops it. In a copy that is not update-capable the switch only saves its value.

## Manual check
The *update check* a *Check for updates…* click starts, in every copy, whatever the *automatic updates setting* says and whether or not the update card shows. It is answered by one read of the update list, a read already running included, never by a second read beside it. While it runs, the button greys out as *Checking…*, a *progress label*, and a second click does nothing; an answer that has not come within 30 seconds counts as a failed check. It answers with an *update alert*: the update is ready to install, Trackpad App is up to date, or the check failed. It never adds the *update card* and never retries by itself. Closing the window drops it silently: no alert shows then or at the next opening. In a copy that is not update-capable a click makes no request and answers "Updates aren't available for this copy". *Update now* clicked while it runs takes its place: the button reads *Updating…* and no alert follows.

## Update alert
A standard macOS alert, free-standing (not a sheet), app-modal and with the app's icon, that answers a *manual check* or the download its *Update* started. It shows only while the settings window is open, one at a time:
- "Restart Trackpad App to update?", with "Update Trackpad App from <running version> to <new version>." and, after a blank line, "Trackpad App will quit to install the update and open again.", and *Not now* and *Update*, the default;
- "Trackpad App is up to date", with "You're running the latest version, <running version>.";
- "Couldn't check for updates", with "Check your internet connection and try again.";
- "Couldn't install the update", with "Trackpad App <running version> keeps running. Try again later.", when a download *Update* started fails or is not genuine; a cancelled administrator prompt shows none, and *Update* that finds nothing newer any more shows "Trackpad App is up to date";
- "Updates aren't available for this copy", with "This copy of Trackpad App can't update itself.".

All but the first have a single *OK*. *Not now* remembers nothing: the next check offers the same version again. *Update* downloads and installs exactly as *Update now* does, whatever the setting says: it reads the list once more and installs the newest *newer version* it then finds, and the *hand-over* then opens the new version with its settings window. While a download already runs, *Update* starts nothing new. While an alert shows, the settings window takes no clicks; gestures, the swipe, the window swipe and the swap keep working. Closing the window or a hand-over dismisses it unanswered, and so does a logout, restart or shutdown, which it never holds up. A result that comes while the window is closed shows nothing, then or later.

## Progress label
A button title that names work under way: *Checking…* and *Updating…*, on the *Check for updates…* button and on the *update card*'s button. Its three dots step through none, one, two and three, 250 ms each, in a one-second loop, each step switching at once with no fade, while the word stays still; VoiceOver reads the whole label once and announces no change of the dots. With the system's Reduce motion setting on, the dots stand still as "…". The dots step only while the window is on screen. A title whose ellipsis means "opens something" (*Check for updates…*, *Open Settings…*, *Other…*) is not a progress label and never animates.

## Hand-over
How a *login update*, the *update card* or the *update alert* replaces the running copy: the moment the update is prepared, the old copy leaves a one-shot job with the system and ends, and the update installs at that end. Once the install has finished, or within a few seconds if it failed, the job opens whichever whole copy /Applications holds. After a login update whose settings window was closed, the opened copy starts silently: no window, no Dock icon, no dialog and no permission prompt, and the keyboard focus stays in the user's app. After a login update whose window was open at that moment, and always after *Update now* or the update alert's *Update*, it opens with its settings window, as an opening by hand would. Either way it stops any other copy, makes no update check of its own, and gestures work again within 10 seconds. Only a prepared update starts a hand-over, so a Quit, a logout or a crash never does, and nothing restarts the app after them.

## Gesture
One of the five tap gestures: a tap with one, two, three, four or five fingers, made under the thumb anchored in the anchor corner or, while the hold thumb setting is off, also as a *thumbless tap*. Gestures are named by finger count: *1-finger gesture* … *5-finger gesture*. The swipe and the swap are the other ways to reach an app, and the window swipe reaches another window of the frontmost app; none of them is a gesture in this sense.

## Anchor corner
The corner of the trackpad where the thumb rests to arm a gesture, or taps to swap apps: the zone 20% of the width from the thumb corner's side edge and 25% of the height from its top or bottom edge, whichever the thumb corner of that trackpad is. A fixed zone; the user chooses the corner, never its size. A thumb that anchored stays anchored until it moves more than 2 mm outside the zone.

## Anchored thumb
A finger resting inside the anchor corner. While a thumb is anchored, the trackpad is in *launcher mode*: taps with the other fingers are gestures. Landing order matters: a thumb that lands under fingers already resting is not anchored while it taps (see *Thumb tap*); one that stays down past the tap window is anchored once the fingers lift.

## Thumb tap
A contact that lands inside the anchor corner, does not drag more than 3 mm, and lifts within the tap window (400 ms). Each landing is judged on its own: a thumb that lifts and lands again is a new thumb tap. Under two resting fingers it fires a swap; otherwise it is only an anchored thumb that lifted. A thumb that lands under resting fingers and stays down longer than the tap window never swaps and is an anchored thumb once the fingers lift. A press during the thumb tap, withheld or delivered, is part of it: unlike a tap, a thumb tap is never cancelled by a click.

## Edge contact
A contact that lands where the side of a palm rests beside the pad. The thumb corner meant here is that of the trackpad the contact lands on. With a top thumb corner: closer than 3 mm to the bottom edge, anywhere along its length, or closer than 3 mm to the *hand-side edge*, the side edge opposite the thumb corner, and more than 40% of the trackpad's height down from the top. With a bottom thumb corner: closer than 3 mm to the bottom edge and outside the anchor corner; no side edge is in the band, since the heel of the hand then rests below the trackpad, and a contact landing inside the anchor corner is a thumb however close to the bottom edge. The 40% line is a share of the height, like the anchor corner's size, so the band sits at the same place on every trackpad size; the 3 mm width is the same everywhere. A contact landing anywhere else near an edge, the top edge, the edge on the thumb corner's side, or the upper part of the hand-side edge, is a finger like any other. An edge contact is ignored for as long as it stays down: it neither starts nor joins a tap, a swipe or a swap, and it is not another contact for arming, click blocking or Dock swipe blocking. A finger that lands farther in and slides into the band stays a finger; a contact that lifts and lands again is judged by its new landing point.

## Tap
Fingers that touch down and lift again within a short window, without dragging. A gesture fires once per tap, when the fingers lift. The *finger count* of a tap is the number of fingers that touched during the tap, not counting the anchored thumb or any edge contact. Two fingers that slide sideways more than 3 mm under the anchored thumb are a swipe, and two that slide up or down more than 3 mm a window swipe whenever there is one (see *Window swipe*); either way they are not a tap. Two fingers that rest longer than the window fire nothing but may still become either. Under the anchored thumb a tap is the gesture alone: the click, Look up or Smart zoom macOS would make for it is a tap action and is blocked (see *Tap action*). A tap with no thumb is a gesture only as a *thumbless tap*.

## Thumbless tap
A tap with no thumb that fires its finger count's gesture while the hold thumb setting is off. It is a touch that meets all of these:
- one to five fingers touch one trackpad;
- the first finger lands while no other contact is on that trackpad, edge contacts aside, after the trackpad has been silent (no contact but edge contacts) for at least 100 ms; after recognition restarts, a finger landing on an empty trackpad counts as quiet, while one already resting starts no tap;
- every finger lifts within the thumbless tap window, counted from the first landing, without dragging past the thumbless drag limit: 70 ms and 3 mm for 1 or 2 fingers, 90 ms and 5 mm for 3, 4 or 5 (against the 400 ms and 3 mm a thumb-held tap allows). Recorded deliberate taps: 1–2 fingers at most 64 ms; 3–5 fingers at most 80 ms with up to 4.3 mm of roll;
- no contact lands inside the anchor corner;
- the trackpad is not pressed to a click, a press that click blocking withholds included.

The finger count is the number of fingers that touched. The gesture fires once, when the last finger lifts, and brings its app to the front exactly as a tap under the thumb does: the same gesture haptic, launch animation, launch bounce and hide. A finger landing after the trackpad is empty again starts a new tap once it has been silent for 100 ms, so a double tap fires twice only when its taps are at least 100 ms apart. A contact landing in the anchor corner is a thumb, never a tap finger, and a touch with one follows the thumb rules alone: a single finger tapping in the corner fires nothing. A finger already resting when recognition restarted (after a trackpad change, wake, or a settings change) is in no thumbless tap, since its landing time is unknown. A thumbless tap lies outside any thumb touch and blocks nothing, during or after it: no press, tap action, scroll or system swipe. So the click, right-click or Look up macOS makes for the same tap happens too, wherever macOS sends it. It needs no permission. Any touch that meets the definition fires, such as a tap that stops a scroll's momentum, a pointer nudge under 3 mm, or the first tap of tap-and-drag.

## Hold thumb setting
One global setting for every trackpad, on by default, shown as the *Hold thumb* switch in the settings window, the last row of the gesture rows' group, directly below the launch animation setting's switch. While it is on, a gesture needs the anchored thumb: a tap with no thumb fires nothing. While it is off, a *thumbless tap* fires its gesture too; taps under the anchored thumb work as before, with the same blocking. The swipe, the window swipe and the swap need the thumb either way. While it is off, the five gestures' illustrations show no thumb and the hand guide shows only its tapping hand; the swipe, window swipe and thumb tap illustrations keep the thumb, since those need it either way. A change applies to the next tap and is saved at once, so it survives a quit, a force-quit or a Mac restart. Upgrading from a version without the setting leaves it on and changes no other setting; a downgrade ignores it. A version without the setting that saves any setting drops the choice, so installing this version again starts with it on.

## Swipe
Two fingers sliding left or right, started under an anchored thumb while the swipe setting is on: the thumb anchored first, exactly two fingers landed, and one of them moved more than 3 mm, more sideways than up or down, with no time limit. A slide's direction is decided once, by that first movement past 3 mm, and holds until both fingers lift: a swipe never turns into a window swipe, nor a window swipe into a swipe, and a slide up or down that is no window swipe never becomes a swipe. The thumb only starts the swipe; afterwards it may stay, lift, leave the corner or land again, and nothing changes. A swipe ends when both fingers have lifted; a finger that briefly loses contact and lands again rejoins it, and a jump in the other finger's reported position while it is away is not movement (see *Travel*). It is cancelled when a third finger lands outside the anchor corner while both are down, or a click reaches apps. Clicks and scrolling stay blocked for the whole of a swipe, whether or not a switcher shows. Nothing further happens until every non-thumb finger has lifted.

## Switcher
The on-screen row shown during a swipe: a Liquid Glass panel centred on the pointer's display, holding one row of at most 10 icons, the frontmost app at the left end followed by the 9 most recently used other running apps that no gesture holds alone, in their order, a glass highlight that follows the fingers, and the selected icon drawn slightly larger, inside the highlight. No name is shown: the icons say which app is selected. An app with two or more windows shows its *window stack*, the frontmost app included, whether or not the window swipe setting is on; the row never waits for it. A running app that one of the five gestures holds alone is left out, by its bundle identifier (every running copy of that bundle, and whether or not the assignment is missing), so its slot goes to the next most recently used app without such a gesture; only the frontmost app is shown whatever its gesture. A split gesture's apps are not left out on that account: its gesture brings two apps, so the switcher stays the way to reach one of them alone. The assignments in place when the swipe begins decide the row; there is no setting for this. Icons are 80 pt, 20 pt apart, and the row sits 22 pt inside the panel on every side, measured to the highlight: 22 pt above and below it, 22 pt from the left edge when it is on the first icon and 22 pt from the right edge when it is on the last, so the panel is 22 pt + the highlight + 22 pt tall; when that row would not fit the display, the icons, the gaps and the highlight shrink by one factor so the whole row fits in one row, and the 22 pt stays on every side. The highlight moves one icon for every 100 points the cursor would travel for the same finger movement, with macOS's own pointer acceleration at the user's tracking speed, whatever the icons' size on screen; it follows the swipe's *travel*, which evens out the trackpad's uneven reports. The selection starts on the frontmost app; sliding right moves it to apps used longer ago and sliding left back towards the frontmost app, whatever the thumb corner. The selected icon is the nearest one, so the selection changes halfway to the next icon. The ends are hard stops with a small rubber band that adds no dead zone: the moment the fingers turn back, travel past the end is forgotten and the next icon is the usual half icon away. The row is fixed when the swipe begins: an app that launches during the swipe is not in it, and one that quits stays in it. Lifting brings the selected app to the front with the gesture haptic; lifting on the frontmost app, or on an app that has quit, does nothing and is silent. It never takes focus, and shows nothing when there is nothing to switch to, as when every other running app has a gesture: the swipe then still runs its course, blocking clicks and scrolling until the fingers lift.

## Travel
How far a swipe's or a window swipe's fingers have taken the highlight since the slide began, in *step millimetres*, 12 to an item: positive to the right along a swipe and downwards along a window swipe, whatever the thumb corner, and 0 on the frame the slide begins, since the 3 mm that began it do not count. It advances only on trackpad frames. Each frame adds what the cursor would travel (its points ÷ 100 × 12) for the fingers' movement averaged over the last 4 frames, that frame's and the 3 before it, frames before the slide began counting as none. So the pointer acceleration sees the fingers' averaged speed, a frame the trackpad reports unevenly is spread over four instead of jolting the highlight, and the highlight has caught up with the fingers 3 frames after they stop. The fingers' movement on a frame is what the swipe fingers present on that frame and the one before did, their mean when both were. While only one of the two swipe fingers is down, a jump in its reported position is not movement: a movement longer than 2 mm in one frame and longer than 3 times that finger's last counted movement plus 1 mm is a snap and is discarded, though the finger is followed from where it is reported. A snap is remembered for the next 4 frames, until the finger lifts or both fingers are down again, and a movement that undoes it meanwhile, the two summing to at most half the snap's length, is discarded with it: a position that jumps away and back leaves the highlight where the fingers are. A finger's first movement in a slide always counts, and so does its movement on the frame after a discarded one unless it undoes the snap, and it becomes what the next is measured against: a finger moving on its own loses one frame at most. A lift takes travel as it is: the selection is what the highlight shows, and movement the highlight had not caught up with is dropped.

## Running apps
The apps macOS's ⌘-Tab shows, in its order: every running app that appears in the Dock, whether hidden, minimised, windowless, on another Space or in full screen, most recently activated first; never a menu bar app. Trackpad App is one of them, in its ⌘-Tab place, exactly while its Dock icon shows: while its settings window is open, minimised or hidden included. Read from LaunchServices at the moment a swipe begins and again when it ends, and at each thumb tap that may swap, and when a launched app's window shows while the hide background apps setting waits for it; the model keeps none of it beyond the last swap of the latest swap series, which is replaced when the next series starts. Should macOS stop revealing the order, the app in front when Trackpad App started and the apps activated since come first, most recent first, and the rest follow in the order they launched.

## Swipe setting
One global setting, on by default, shown as the *Switch recent* switch in the settings window's switcher section. While it is off there is no swipe: two fingers sliding sideways under an anchored thumb are not a swipe, no switcher appears, the slide scrolls once the blocking window has passed, and only the tap rules block clicks and scrolling (the blocking window); Dock swipe blocking holds as it always does, since the slide lies inside a thumb touch. Taps, swaps and the window swipe are unchanged: a slide up or down follows the window swipe setting. A change applies to the next swipe and is saved at once, so it survives a quit, a force-quit or a Mac restart.

## Swap
Bringing to front the app used most recently before the frontmost app, like a quick ⌘-Tab, with nothing on screen. Fired by a thumb tap while exactly two fingers rest outside the anchor corner (edge contacts aside), both landed before the thumb, however shortly, whether or not they are moving or have scrolled, while the swap setting is on and gestures are active. The target is the first of the running apps, in ⌘-Tab order, that is not the frontmost app, whether or not a gesture is assigned to it; with no frontmost app, the most recently used running app. It fires when the thumb lifts: the gesture haptic and bring to front, never the launch animation; an open settings window stays open. With nothing to swap to it is silent. The order is read afresh at each thumb tap; while the last swap's app is still coming to the front (the read still shows the app that swap started from, and the app it brought to front is still running), that app counts as the frontmost app, so rapid taps alternate. Thumb first, then fingers, is a gesture or a swipe, never a swap. Not a gesture in the glossary's sense.

## Swap series
The swaps made while the same two fingers stay down: from the first thumb tap that fires under them until no finger rests outside the anchor corner. A series finger that lifts rejoins if it lands again while the other is still down. The fingers may move freely. The series stops swapping, but keeps blocking, once a third finger lands outside the anchor corner; it ends when no finger rests outside the anchor corner. Clicks, scrolling and the system's trackpad swipes stay blocked for the whole series, as during a swipe. The model remembers only the last swap made, to target the next one while that swap's app is still coming to the front; that memory is replaced when the next series starts. Its fingers have rested past the tap action hold limit by the time they lift, so no lift window opens for them; macOS makes no tap action for a swap.

## Swap setting
One global setting, on by default, shown as the *Toggle recent* switch in the settings window's switcher section, below the window swipe setting's switch. While it is off there is no swap and no swap series: a thumb that lands under resting fingers is an anchored thumb that waits for them to lift, as before the swap existed, and only the thumb rules block. Independent of the swipe and window swipe settings. A change applies to the next thumb tap and is saved at once, so it survives a quit, a force-quit or a Mac restart. Upgrading from a version without the setting leaves it on and changes no other setting.

## Window swipe
Two fingers sliding up or down, started under an anchored thumb while the window swipe setting is on: the thumb anchored first, exactly two fingers landed, and one of them moved more than 3 mm, more up or down than sideways, with no time limit. It exists whenever the frontmost app's windows are known when the slide's direction is decided, whatever their number: Trackpad App has the Accessibility permission, without which no window can be read, there is a frontmost app, and that app reports its windows within 0.2 s. Otherwise the slide is no window swipe: nothing shows, nothing pulses, and it behaves exactly as with the window swipe setting off, scrolling once the blocking window has passed and never becoming a swipe. A window swipe shows the window switcher: rows to move between the frontmost app's windows when it has two or more, and the *no-windows card* when it has zero or one, a full-screen front window counting as one. Everything else is as for a swipe: the direction is decided once, the thumb only starts it, it ends when both fingers have lifted, a finger that briefly loses contact and lands again rejoins it, and it is cancelled when a third finger lands outside the anchor corner while both are down, or a click reaches apps; a cancelled window swipe leaves the window in front as it is, silently. Clicks, scrolling and the system's trackpad swipes stay blocked for the whole of it. Not a gesture in the glossary's sense.

## Window switcher
The on-screen list shown on every window swipe: a Liquid Glass panel in the top-left corner of the pointer's display, just below the menu bar, holding one column of 2 to 10 rows, or the no-windows card in their place: the frontmost app's windows as the window swipe begins, in the app's *window order*. With more than ten, the ten listed are the front window, the other visible windows front to back, then the minimised windows; with more than ten the rows may therefore shift between window swipes. The panel is 360 pt wide, whatever its titles. Each row shows a preview of its window, 60 pt tall, at most 120 pt wide, as it looked when the window swipe began, and the window's title, reworded by the app's title rule when it has one and otherwise exactly as the app gives it, on one line beside the preview; a title that does not fit is cut short at the end with an ellipsis, never wrapped; a window with no title reads as the app's name followed by " — Window N", N its row, whatever the app's title rule. A row whose preview is not ready yet is empty, and the preview fades in as soon as it is; a row shows the app's icon in place of the preview when its window could not be captured, without the Screen Recording permission, and always for a minimised window, which is also dimmed and badged "Minimised". A glass highlight marks the selected row. The selection starts on the front window's row, or on the first row when every listed window is minimised, and moves one row for every 100 points the cursor would travel for the same finger movement, following the window swipe's *travel*, sliding down to the next row and up back towards the first, whatever the thumb corner, with the switcher's nearest-row choice, hard stops and rubber band. Each time it lands on a visible window, that window comes to the front with the keyboard focus, behind the window switcher; a minimised window is not restored while sliding. Lifting leaves the selected window in front with the keyboard focus, restoring it if it is minimised, and orders the windows: the selected window, then the front window, then the others as before; the gesture haptic plays when the window in front differs from the front window or a minimised window was restored, and otherwise the lift is silent. The lift orders the windows on screen, never the window order. The list is fixed when the window swipe begins: a window that opens during it is not added, and one that closes stays listed; lifting on a closed window leaves the windows as they are. A full-screen front window counts as the app's only window, so the window switcher then shows the no-windows card. When the column would not fit the display, the rows and the panel's width shrink by one factor, and titles are cut short against the narrower width. It never takes focus or receives clicks.

## Window
One of an app's normal document or app windows on the current Space, or one of its minimised windows. Panels, palettes, popovers, sheets, toolbars and other floating helpers are not windows in this sense, nor are the app's windows on other Spaces or its full-screen windows other than the front window. A hidden app's document windows count as its windows, since they show when it is shown again.

## Window order
The order in which the window switcher lists an app's windows, one per app. The first window swipe into the app sets it as the windows stood then: the window in front, the other visible windows front to back, then the minimised windows in the order the app lists them. Afterwards only three things change it: a window that opens joins it at its end, a window that closes leaves it, and the app quitting or Trackpad App stopping forgets it. Bringing a window forward in any way (a lift, a click, ⌘`, the Window menu, Mission Control, the Dock), minimising, restoring and hiding change nothing. A window on another Space is not listed but keeps its place, and is listed there again once it is back on the current Space. It is never saved.

## Window stack
An app's icon in the switcher with smaller copies of it behind, peeking out above it, one copy per further window, four icons at most, for an app with two or more windows counted as the window switcher would list them. The front icon sits and sizes as a lone icon does, so the row, the highlight and the panel keep their sizes; the copies grow with the selected icon and shrink with the row. An app shows its icon alone until its count is known; each count is read when the swipe begins, holds for the whole swipe, and an app that does not report its windows within 0.2 s shows its icon alone throughout. Without the Accessibility permission every app shows its icon alone. A stack rises out from behind its icon once per swipe, as soon as its count is known, the nearer copy first, over about 0.3 s; with the system's Reduce motion setting on it shows in place.

## No-windows card
The window switcher's single card in place of its rows when the frontmost app has zero or one window: the app's icon on the left, where a row's preview sits, a bold first line and a regular message. With one window (a full-screen front window included) it reads "No other windows" and "‹App› has no other windows on this desktop."; with none, "No open windows" and "‹App› has no windows on this desktop.". It shows no preview. It follows the fingers up or down a few points, never more than 6 pt from rest, turning at once when they turn, with no haptic, and settles back as the window switcher goes; with Reduce motion on it stays still. Lifting on it, or cancelling it, changes nothing and is silent: no window moves and, with the hide background apps setting on, nothing hides.

## Front window
The window an app shows in front of its other windows. When that is a sheet or a panel, it is the window the sheet or panel belongs to; a minimised window is restored first. A split gesture places each app's front window. For a window swipe it is the frontmost app's front window when the window swipe begins, on whichever row the window order puts it; the selection starts on its row. There is none when every window of the app is minimised: the selection then starts on the first row, and lifting on any row restores that window with the gesture haptic.

## Title rule
A built-in rewording of a window's title for the window switcher, keyed by the app's bundle identifier: every window of that app, visible or minimised, shows its title reworded, and an app without a rule shows its titles exactly as it gives them. A rule rewords only a title the app gives, never the untitled fallback. The rules are one table in the code, with no setting; adding an app is one entry. Today one rule, for VS Code (`com.microsoft.VSCode`) and VS Code Insiders (`com.microsoft.VSCodeInsiders`): the title *leads with the project*. VS Code titles the file first and the project second, `main.swift — trackpad-launcher`; the rule swaps the first two parts split by " — " (space, em dash, space), keeps every later part in its order after them, and changes no part's text, so `main.swift — trackpad-launcher — Work` reads `trackpad-launcher — main.swift — Work`, `● main.swift — trackpad-launcher` reads `trackpad-launcher — ● main.swift`, and a title with no separator is unchanged.

## Window swipe setting
One global setting, off by default, shown as the *Switch windows* switch in the settings window's switcher section, below the swipe setting's switch. While it is off there is no window swipe: two fingers sliding up or down under an anchored thumb are not a window swipe, no window switcher appears, and the slide scrolls once the blocking window has passed, exactly as before the window swipe existed. Independent of the swipe and swap settings. A change applies to the next slide and is saved at once, so it survives a quit, a force-quit or a Mac restart. Upgrading from a version without the setting leaves it off and changes no other setting; upgrading from one with it keeps the saved choice.

## Frontmost app
The active app at the moment a swipe or a window swipe begins or a thumb tap lifts. While its settings window is in front, that is Trackpad App itself, like any app: first in the switcher's row and selected, a lift on it does nothing, and a swap goes to the app used before it. A slide up or down over it shows the no-windows card ("Trackpad App has no other windows on this desktop."), since the settings window is its only window. Trackpad App active without its Dock icon, as behind the move dialog or a developer tool, is never the frontmost app: the frontmost app is then the app that was in front before it, read as the most recently used running app. It sits at the left end of the switcher's row and the selection starts on it, so the user can stay where they are; it is there even when ⌘-Tab would not show it, such as a menu bar app with a window in front, and even when a gesture is assigned to it. When there is none, the row is the running apps without a gesture alone, the selection starts on the most recently used one, and lifting on any app, that one included, brings it to the front; a swap brings the most recently used one to the front; and a slide up or down is no window swipe. The window switcher lists the frontmost app's windows.

## Thumb corner
The corner of the trackpad the thumb anchors in: *Top left*, *Top right*, *Bottom left* or *Bottom right*, chosen from a pop-up in the settings window, which lists them in that order and shows the current one. Until the Mac has *mixed trackpads* it is one setting for every trackpad of either kind, *Top left* by default, chosen from the *Thumb corner* pop-up; a Mac with no built-in trackpad, such as a Mac mini, only ever has this one. Once the Mac has mixed trackpads there are two. The *MacBook trackpad* corner is the built-in trackpad's: the same setting as the one corner, keeping its value. The *External trackpad* corner is every external trackpad's: *Bottom left* the moment the Mac comes to have mixed trackpads, upgraders included, and from then on whatever the user chooses. Each has its own pop-up, and changing one leaves the other alone. Every rule that depends on the thumb corner (the anchor corner, the thumb tap, edge contacts) follows the corner of the trackpad the touch is on, both trackpads work at the same time, and touches on different trackpads never combine: a thumb on one never arms taps on the other. A change applies to the next thumb that lands on a trackpad of that kind and is saved at once, so it survives a quit, a force-quit or a Mac restart; a thumb already down when a choice changes is judged afresh, as after any settings change: it anchors only if it rests in its trackpad's corner. Every gesture, the swipe, the window swipe and the swap work the same from every corner, with the same blocking and the same haptics, and sliding right still reaches older apps and sliding down the next window. Versions before the bottom corners offered *Left thumb* and *Right thumb*, which load as *Top left* and *Top right*; the choice is saved so that such a version, installed over this one, reads the side and keeps every other setting, anchoring the thumb in the top corner on that side. A version without the External trackpad corner, installed over this one, uses the MacBook trackpad corner for every trackpad and keeps every other setting; installing this version again brings back the External trackpad corner and the mixed-trackpads record, whatever was changed in between.

## Hide background apps setting
One global setting, off by default, shown as the *Hide background apps* switch in the settings window's thumb corner group, directly below the thumb corner row, or below the two rows once the Mac has mixed trackpads. While it is on, every action that brings an app or a window to the front, a tap on a running app (the app already in front included), a swipe lift, a swap, and a window swipe lift that leaves a different window in front, also hides every other running app with a Dock icon, as Hide Others (⌘⌥H) does: on every display and Space, full-screen apps and Finder included (the Desktop's icons stay), the settings window included unless Trackpad App is the frontmost app; menu bar apps stay as they are, and the frontmost app's own windows stay as the action left them. Nothing hides until the app brought forward is in front: active and, if it was hidden, shown again, because macOS activates a hidden app before it shows it and a hide in that gap sends the front to a third app. So the ⌘-Tab order keeps the app the user came from next, and a swap series alternates as before. A gesture that follows replaces the wait and hides everything the earlier one had not. Whatever still shows is hidden again within about half a second, while the app stays in front. An app that does not come to the front within about 3 seconds hides nothing. A silent action hides nothing. A gesture that launches its app hides the others only when the launch watch sees the app's first window, and only if the app is the frontmost app at that moment; a launch that fails, shows no window within the watch's limits, or whose user went to another app meanwhile hides nothing, and a repeated gesture for a launching app takes the switch's value then. A split gesture keeps both its apps, and nothing hides until its first app is in front: with both apps running the others hide then; otherwise they hide when a launching app's first window shows, only if the first app is the frontmost app at that moment and is not itself still waiting for its first window (its own window then hides them), and never hiding the other app of the gesture. Hiding needs no permission. Hidden apps stay in the switcher and the swap in their place, and bringing one to the front shows it. Flipping the switch hides and shows nothing: it applies to the next action and is saved at once, so it survives a quit, a force-quit or a Mac restart. Upgrading from a version without the setting leaves it off and changes no other setting; a downgrade ignores it.

## Assignment
What a gesture holds: its *first app* and, optionally, a *second app*, each identified by its bundle identifier, not its location. A gesture is *assigned* (it has a first app) or *unassigned*. An assignment never holds one app twice, and only an assignment with a first app holds a second app. Both apps are saved at once in the one settings record; a version without second apps keeps every first app and drops the second apps the first time it saves. An app of an assignment is *missing* when no copy of it exists outside the Trash; it recovers by itself when a copy exists again. An app that a gesture holds alone is left out of the switcher's row, missing or not, unless it is the frontmost app; a split gesture's apps are not left out on that account. The swap still reaches every app.

## First app
The app an assignment has always held, chosen in the gesture row's first picker. *None* on the first picker unassigns the gesture, second app included. Picking another app keeps the second app; picking the second app makes it the first app and removes the second app.

## Second app
An optional extra app in an assignment, chosen through the plus button or the second picker. Only an assignment with a first app can hold one, and it is never the first app: the first app shows disabled in its menu, and choosing it through *Other…* changes nothing. *None* in its menu changes nothing; the minus button removes it.

## Split gesture
A gesture whose assignment holds a first app and a second app. Firing it, with both apps present, does *split to front*; with one app missing it brings the present app to front exactly as a one-app gesture would, moving no window; with both missing it is silent, as a gesture with a missing app is.

## Split to front
What a split gesture does. Both apps are brought to front with one gesture haptic, the app on the half the pointer is over ending active (the first app when no window is placed), the *focused* one: the other app is brought to front first and the focused app last; an app that has to launch is launched without being made active unless it is the focused one, so the other never takes the focus when it finishes launching, and a focused app that launches becomes active when it finishes launching. A running other app is made active for a moment before the focused one, its menu bar showing briefly, except while the hide background apps setting is on: then it is never made active, so only the focused app's menu bar shows; it is unhidden, or, when it has no window on screen, restored or given a window without the focus, while the other apps hide. For a second after the gesture, the other app taking the focus by itself, as some apps do when brought to front, makes the focused app active again; any third app becoming active ends that. With the Accessibility permission, the first app's front window is then placed in the left half and the second app's in the right half of the usable area (menu bar and Dock excluded) of the display under the pointer, the halves meeting exactly, the left one taking the odd point. A full-screen window leaves full screen first; a window that cannot take its half's size keeps the closest size it allows, anchored at its half's top-left corner for the first app and top-right corner for the second, so an oversize window overlaps the other half. Each fire places both windows again. An app with no window on screen at the gesture (launching, windowless, hidden or minimised) has its first window placed when it shows, within its launch watch's limits, on the display chosen at the gesture; a later gesture that brings an app to front cancels this. Placement is best effort and never shows an error. Without the permission both apps come to front and no window moves or resizes.

## Target app
The app the gesture that just fired holds, or a split gesture's two apps.

## Bring to front
What a gesture does to its target app: launch it if it is not running; otherwise unhide, restore minimised windows or open a new window as needed, and make it the active app. A hidden app is brought to front like any other: it shows again. A gesture that launches its app shows the launch bounce while the app starts up, and is followed by a launch watch, as long as the launch animation setting or the hide background apps setting is on. A split gesture brings both its apps to front this way, the first app ending active (see *Split to front*).

## Settings window
The window that opens when the user opens Trackpad App by hand: an ordinary macOS window with the close and minimise buttons, centred on the display under the pointer, in front and with the keyboard focus, every time it opens, whether the opening started the process or reached a running copy. It holds rounded groups, one under another: first, while this opening's update check has found a newer version, the update card; then, while the Accessibility permission is missing, the Accessibility hint; the five gesture rows, the launch animation switch and the hold thumb setting's switch; the switcher section (the swipe illustration, its title and the swipe setting's switch, then the window swipe illustration, its title and the window swipe setting's switch, with the screen recording hint under that switch in the same row while it applies, then the thumb tap illustration, its title and the swap setting's switch); the thumb corner group: the *Thumb corner* row, its title at the leading edge and its pop-up at the trailing edge, or, once the Mac has mixed trackpads, the title "Thumb corner:" and under it two indented rows, *MacBook trackpad* and *External trackpad*, each with its own pop-up at the trailing edge, whether or not an external trackpad is connected; then the hide background apps setting's switch; then the *Automatic updates* row: the *automatic updates setting*'s switch, the line "Current version: <version>" and the *Check for updates…* button; then, while it applies, the no trackpad notice. Last, below everything and aligned right, come the *Quit Trackpad App* button, red, and *Close*, which closes the window like its close button. The update card and the Accessibility hint sit 10 pt apart, and the last of them 16 pt above the gesture rows' group; the groups that follow, the no trackpad notice included, sit 10 pt apart; the buttons start 20 pt below the last of them. Every one-line row is 48 pt tall, except the 1-finger gesture's (see *Gesture row*). The window resizes to fit whenever the update card, a hint or the notice appears or disappears, when the thumb corner row becomes two, and when a gesture row gains or loses its second line. It is never taller than 95% of the visible area of its display (the display less the menu bar and the Dock): taller content scrolls inside it with the system's scroller, the hand guide scrolling with the first gesture row, and the limit holds on every resize to fit and when the window moves to another display. A gesture row's app picker is System Settings' own pop-up button, its bezel showing on hover: the app's icon, its name 6 pt after it, then the chevrons in a round badge, the content at most 128 pt wide, a long name cut short at the end. Every illustration that draws a thumb draws it in one corner, the *corner drawn*: the External trackpad corner while the Mac has mixed trackpads and an external trackpad is connected, otherwise the MacBook trackpad corner, which is the one corner of a Mac without mixed trackpads. It switches at once as a trackpad connects or disconnects and as the corner in view changes. While the hold thumb setting is off, the five gestures' illustrations draw no thumb (see *Illustration*). The *hand guide* shows over the 1-finger gesture's illustration while it applies, whether or not the gesture has an app. It closes only by its close button, ⌘W, Escape (when no menu or chooser is open), *Close Settings* (⌘Q) in the app menu and *Quit* in the Dock icon's menu, and gestures keep working after it closes. Clicking another app, a gesture, a swipe, a window swipe, a swap, *Other…* (whose file chooser is a sheet on the window) and the System Settings buttons all leave it open; an app a gesture brings to front comes over it. With the hide background apps setting on, an action that hides hides this window too, unless Trackpad App is the frontmost app: the window stays open to the app and keeps its Dock icon, as a minimised one does, and opening Trackpad App again (the Dock icon, Spotlight, Finder, a swap or a lift on it) shows it where it was. Trackpad App's own visuals, the switcher, the window switcher, the launch animation and the launch bounce, never hide with it.

## Gesture row
One row in the settings window: a gesture illustration at the leading edge and, at the trailing edge, the gesture's app pickers. An unassigned gesture shows its first picker alone. A gesture with a first app and no second app shows the picker and, 12 pt after it, the plus button (`plus.circle.fill`, 16 pt, grey; "Add a second app"), a missing first app included. A split gesture's row has two lines, right-aligned with the two pickers' trailing edges lined up: the first app's picker, and under it the minus button (`minus.circle.fill`, 16 pt, grey; "Remove the second app") followed by the second app's picker. A one-line row is 48 pt tall and a two-line row 86 pt: its two lines take 56 pt, with 15 pt above and below. The illustration stays vertically centred. The 1-finger gesture's row differs: it is 70 pt tall, or 86 pt with two lines, and its illustration is the large picture fixed to the top-leading corner of the gesture rows' group, which keeps its place when the row grows; its pickers stay at the trailing edge, centred vertically.

## Illustration
The picture in a settings row that shows how its gesture or action is made: the thumb and the fingers as dots on a trackpad, ringed where they tap. The 2- to 5-finger gestures, the swipe, the window swipe and the thumb tap each have a small trackpad card, 45 × 28 pt. The 1-finger gesture has a large picture of a MacBook's keyboard and trackpad, 137 pt wide, fixed to the top-leading corner of the gesture rows' group, its top-left corner 1 pt above the row's top and 12 pt left of the group's leading edge, and cut by the group's rounded corner and edges; it never reaches into the 2-finger row. Each illustration comes in a version for each thumb corner and shows the one for the *corner drawn*. A card's other versions are its top-left version with the marks mirrored on the same card, lit as drawn: left to right for *Top right*, top to bottom for *Bottom left*, both ways for *Bottom right*. The 1-finger gesture's four versions are drawn one by one. While the hold thumb setting is off, the five gestures' illustrations show no thumb: the fingers alone, where the top-left version has them, whatever the thumb corner. The swipe, window swipe and thumb tap illustrations always show the thumb.

## Hand guide
Two hands and two small labels over the 1-finger gesture's illustration that show how a gesture is made: a left hand resting on the trackpad's top-left corner with the label *Hold*, marked by a filled dot, below it, and a right hand tapping the trackpad's centre with the label *Tap*, marked by a ringed dot, below it. It shows only while the corner drawn is *Top left*, the one corner it is drawn for. While the hold thumb setting is off it shows the right hand and *Tap* alone, since no thumb is held. Each part appears and disappears at once with the corner and the setting. The hands are slightly see-through and the labels lie over them. It sits at the same place over the gesture rows' group whatever else the window shows, may reach past its row and its group, and takes no clicks: the controls under it work.

## Installed apps
The apps an app picker lists: every app in /Applications and /System/Applications (with their subfolders), in ~/Applications, and Finder. One entry per bundle identifier. An app anywhere else, such as ~/Downloads, is not an installed app in this sense, even when a gesture is assigned to it through *Other…*.

## Recent apps
The up to 10 installed apps the user opened most recently, newest first, as Spotlight records it (an app's last-used date). Opening means launching; switching to an app that is already running does not count. No age limit. All five app pickers show the same recent apps; they refresh each time the settings window opens and may lag behind the very latest launches.

## App picker
The popup in a gesture row that sets the assignment: the recent apps, a divider, the other installed apps alphabetically, then *Other…* (choose any app on disk) and *None*. With no recent apps there is no recent section and no extra divider. The picker opens from a list Trackpad App already holds, with the row's app over the button and checked (at the top when the row's app is not in the list); installed and removed apps show up in it within 5 seconds. Picking an app plays the pick animation on the picker's icon. The first picker sets the first app, and its *None* unassigns the gesture. The second picker, and the menu the plus button opens, list the same items with the first app disabled; picking an app there sets the second app, and *None* there changes nothing, like closing the menu. A missing app shows in either picker by its name, greyed.

## Pick animation
The app picker's icon jumping into place from below when the user picks an app in that picker, from the menu or through *Other…*, the app it already shows included; an app picked through the plus button plays it on the new second picker's icon. The new icon appears at 55% of its side, 9 points below where it rests, and jumps up into place: it grows from its bottom edge to 108% in 0.16 seconds while rising, starting fast and slowing, overshooting its place by about 1.5 points, then settles back to 100% in its place by 0.26 seconds after the pick, smoothly and with no second wobble, fully opaque throughout; where it is bigger than its slot it draws past it, uncut. Only the icon moves: the app's name and the chevron show at once in their final places. Picking *None* plays nothing, and nothing else that changes an icon plays it: the settings window opening, a missing app coming back, a thumb corner change, a pick in another picker. A pick while it plays restarts it with the new icon. With the system's Reduce motion setting on the icon swaps at once. The launch animation setting does not affect it. Debug builds' animation tuner can tune it and preview it on the open settings window's pickers.

## Trackpad
A connected Apple trackpad. Its *kind* is *built-in* or *external* (a Magic Trackpad). macOS keeps trackpad settings per kind, so an external trackpad's settings can differ from the built-in one's. Once the Mac has mixed trackpads, each kind also has its own thumb corner; two Magic Trackpads share the External trackpad corner. A Magic Mouse is not a trackpad.

## Mixed trackpads
What a Mac has from the first time Trackpad App sees a built-in trackpad and an external trackpad connected at the same time, whether at a start, a login start, a hand-over, a hot-plug or a wake; from then on it has two thumb corners (see *Thumb corner*). It is the Mac having an External trackpad corner: the two are one fact. It is recorded at once, whatever started the app, and lasts through a quit, a force-quit, a disconnect, a Mac restart, an update, and a downgrade followed by a re-upgrade; nothing clears it and no control resets it. Recording it is the one thing a login start may save, and it does not end the first run (see *First run*). A Mac with no built-in trackpad never has mixed trackpads, and connecting a Magic Mouse never gives a Mac mixed trackpads.

## Tap-bound setting
A system trackpad setting that binds a system action to a tap rather than a press. Today: *Tap to click* and *Look up: Tap with three fingers*. The list is one table in the code; a setting is *on* when it is on for any connected trackpad. Gestures work whatever these settings are. With the Accessibility permission a gesture's tap makes no tap action (see *Tap action*); without it, a gesture under Tap to click also clicks where the pointer is, and one under Look up also looks up. A thumbless tap is never blocked, with or without the permission: macOS makes its tap action as well.

## Tap action
An action macOS performs for a tap of fingers, as opposed to a press: a left click for a tap of one finger and a right click for a tap of two (Tap to click), the Look up panel for a tap of three (Look up: Tap with three fingers) and Smart zoom for a double tap of two (Smart zoom). macOS makes it as the fingers lift, or up to about 0.3 s later for the right click while Smart zoom is on. Tap actions are blocked in the lift window; Look up and Smart zoom are blocked also under an anchored thumb with another finger down, however long the thumb has rested. So a gesture under the thumb never clicks, looks up or zooms; everywhere else, a thumbless tap included, tap actions work as macOS makes them. Blocking them needs the Accessibility permission. A tap's click is blocked only while Tap to click is on for a connected trackpad; Look up and Smart zoom whatever the settings. A physical press is not a tap action and keeps the click blocking rules.

## Lift window
The first 0.5 seconds after a contact other than the thumb lifts inside a thumb touch, when macOS could read that contact as a tap: it was down for less than the *tap action hold limit* (the longest hold for which macOS still makes a tap action, measured on hardware) and no press was seen while it was down. A tap's fingers, a swipe's or a window swipe's fingers that lift quickly, and a finger that loses contact for a moment open it; each such lift restarts it, so it ends 0.5 s after the last one. Whether the thumb is still down changes nothing. A thumb lifting alone opens none; nor do fingers that rested or scrolled past the hold limit (a swap series' fingers, a scroll under a rested thumb), a finger that pressed the pad down, or any lift outside a thumb touch. During it every tap action is blocked: a click, a deliberate one included, and a press that starts in it is blocked whole, from press to release, so nothing is dragged and no button stays down; Look up; Smart zoom. Scrolling and the physical press rules are not changed by it. It is measured on the process's clock from the moment the lift's frame arrives; strictly less than 0.5 s is inside. The gated port stays on through it and closes on the next frame or event after it ends.

## Gestures active / inactive
Gestures are *active* when Trackpad App is running and at least one trackpad is connected, whatever the trackpad settings and the Accessibility permission. Otherwise gestures are *inactive*: nothing is recognised and nothing fires, neither a gesture, a swipe, a window swipe nor a swap. Connecting or disconnecting a trackpad changes this live, with no relaunch.

## No trackpad notice
The message "No trackpad connected. Connect a trackpad to use gestures." in the settings window, shown while no trackpad is connected, with no button. The settings window never asks the user to turn a trackpad setting off.

## Feedback
The haptic pulses the trackpad gives: the *gesture haptic* when a gesture fires for an assigned, present target app, when a swipe opens an app, when a swap brings an app to front, and when a window swipe's lift leaves a window in front other than the front window or restores a minimised one; and the *light tick*, a lighter pulse, each time the switcher's or the window switcher's selection changes. A swipe or window swipe lift, or a thumb tap, that changes nothing is silent: a lift on the frontmost app, on an app that has quit, or with no switcher showing; a window swipe lift on the front window, or on a window that closed while the front window is still in front; a lift on the no-windows card; a cancelled window swipe; a slide up or down that is no window swipe; a thumb tap that is not a swap, or with nothing to swap to.

## Light tick
The lighter haptic pulse that marks each change of the switcher's or the window switcher's selection: one per icon or row the highlight crosses, none while the selection stays put.

## Launch animation
The target app's icon floating up from the pointer when a gesture fires for an assigned, present target app that is running, together with the feedback; for an app that is not running the launch bounce shows instead, and ends with the launch animation played from wherever its icon is. Only gestures play it: a swipe, a window swipe and a swap never do. It appears at once at full size, puffs up for a split second, then rises faster and faster as it shrinks, sways and tilts a little to one side, and fades out within about a third of a second, like a small balloon letting its air out. With the system's Reduce motion setting on, it fades out in place instead. It never takes focus or receives clicks, and every gesture for a running app plays its own. A split gesture plays one for each of its apps that is running, the first app's swaying left and the second app's right; the two icons start side by side about the pointer, 8 points apart, the other app's 0.02 seconds after the focused app's, so the icon that moves first marks the window that ends active, their shapes never touching, and slide inward together just enough to start whole on the pointer's display. The *launch animation setting* turns it off.

## Launch bounce
The target app's icon bouncing just above the pointer while an app a gesture launched starts up, in place of the launch animation. It plays when a gesture fires for an assigned, present target app that is not running, while the launch animation setting is on. *Not running* means macOS reports no process for the app when the gesture fires: an app still starting up from the Dock or Finder, or a running menu bar app, has one and gets the launch animation. The icon is the launch animation's and appears with the gesture haptic, centred on the pointer's tip, its bottom edge 8 points above it. It inflates upward from there like a balloon: it appears at 24 points, swells to the launch animation's 60 × 60 points within 0.4 seconds, and keeps swelling ever more slowly, with no pause, to 84 points 5 seconds later, where it holds. Its ending's launch animation plays at the size the icon has reached, so it swells on rather than shrinking first. It follows the pointer on every move, onto any display. Near the left or right edge it slides just enough to stay on the pointer's display; the display's top edge cuts it off, and it never moves below the pointer. Several launches bounce side by side in one row above the pointer, newest on the right, 12 points apart, and when one ends the others slide to their new places. A split gesture starts its bounces first app first, so the first app's sits on the left of the second's, and each ends with the launch animation swaying toward its app's side.

A bounce ends with the launch animation, played from wherever the icon is, when a window of the app first shows (a splash screen counts), or 2 seconds after the app finished starting up with no window. It fades out in place within about 0.2 seconds instead when the launch fails, when the app quits, or when the app is still starting up 10 seconds after the gesture. No bounce lasts longer than 10 seconds, and a window that shows after a bounce ended plays nothing. These are the launch watch's ends: the bounce draws what the watch decides. A gesture for an app whose bounce still plays keeps that one bounce: the haptic plays and the app is brought to front, and nothing else shows. With the system's Reduce motion setting on, the icon pulses its opacity at its resting spot at 60 points instead of inflating, and every ending fades it out in place. It never takes focus or receives clicks. Only gestures play it: a swipe, a window swipe and a swap never do. Debug builds' animation tuner can tune the inflate, switch to a Dock-like jump instead, and preview either with Finder's icon.

## Launch watch
Trackpad App following an app a gesture launched, from the gesture until the first of: the app's first window showing on screen (a splash screen counts; a hidden startup window does not, nor a transparent one or a sliver of a point), 2 seconds after the app finished starting up with no window, 10 seconds after the gesture, or the launch failing or the app quitting. It runs while the launch bounce shows and, with the launch animation setting off, unseen, while the hide background apps setting waits for the app's window. With the Accessibility permission, a split gesture also watches its launching apps, so their first windows can be placed, and follows each of its running apps, unseen, from the gesture until a window of it shows on screen, 2 seconds pass, or the next gesture that brings an app to front, to place that window. Otherwise, with both settings off nothing is watched. The bounce's endings and the hide after a launch are what it decides. A gesture for an app whose launch is watched keeps that one watch as it is, bouncing or unseen. Its time passes on the render server's clock, like the bounce's, so no watch outlasts its 10 seconds by more than a fraction of a second.

## Launch animation setting
One global setting, on by default, shown as the *Animate app launch* switch in the settings window, below the gesture rows. It covers both the launch animation and the launch bounce. While it is off, a gesture shows nothing at the pointer, whatever the system's Reduce motion setting; the feedback and bring to front are unchanged, and with the hide background apps setting on a launch is still watched, unseen, so the other apps hide once the app's window shows. A change applies to the next gesture, so a bounce already playing runs its course, and is saved at once, so it survives a quit, a force-quit or a Mac restart. Upgrading from a version without the setting leaves it on and changes no other setting.

## Sway
A launch animation's small sideways veer, to the left or to the right, never more than a third of its rise, with a slight tilt toward that side. For a one-app gesture the side is random, except that the same side never comes up three times in a row. A split gesture's first app always sways left and its second app right, a bounce's ending included; those sways do not count toward the streak.

## Click blocking
Ignoring trackpad clicks (left-click, right-click, Force Click) for the first 3 seconds after a thumb lands in the anchor corner, while it stays there, another finger is on the trackpad, and gestures are active, and for the whole of a swipe, a window swipe or a swap series. Besides presses, it blocks the tap actions: under an anchored thumb with another finger down, however long the thumb has rested, and in the lift window after the fingers lift (see *Tap action*, *Lift window*). A thumb that lands under resting fingers opens that window like any other, so before a series starts the thumb rules alone apply. A press is blocked or passed whole. It needs the Accessibility permission; without it, clicks are never blocked. Under the same rule, trackpad and Magic Mouse scrolling is suppressed: a scroll suppressed at any point stays suppressed, momentum included, until its fingers lift, and a scroll that began unsuppressed coasts to a stop as usual. Pointer movement and a mouse's scroll wheel are never blocked; a mouse click is blocked only while another finger rests on the trackpad inside the blocking window or a swipe, a window swipe or a swap series is on, when it cannot be told from a trackpad press. The system's own trackpad swipes are blocked too, for longer: see *Dock swipe blocking*. With the swipe setting off there is no swipe, with the window swipe setting off no window swipe, and with the swap setting off no swap series, so only the thumb rules apply. A thumbless tap has no thumb in the corner, so nothing is blocked for it.

## Blocking window
The first 3 seconds after a thumb lands in the anchor corner, during which click blocking applies; held open for the whole of a swipe, a window swipe or a swap series, however long after the thumb landed and whether or not it stays. A thumb that was already resting when recognition restarted (after a trackpad change, wake, or a settings change) opens no window: its landing time is unknown, so clicks pass. The *lift window* is the other, shorter window, counted from the fingers' lift rather than the thumb's landing, and it blocks tap actions rather than presses.

## Thumb touch
The stretch of frames from one with a thumb in the anchor corner, whether it anchored or landed under resting fingers, until the first frame with no contact on the trackpad, edge contacts aside. Every gesture made under the thumb, every swipe, window swipe and swap series lies inside one; a thumbless tap lies outside any. What the thumb does inside it changes nothing about its length: it may roll out of the corner, lift, or land again anywhere, even as a plain finger, and the thumb touch lasts until the pad is empty. A touch no thumb landed in the corner during, such as three fingers landing outside the corner and swiping, is not one. Recognition restarting mid-touch (after a trackpad change, wake, or a settings change) starts a thumb touch only if a thumb is in the corner on its first frame.

## Dock swipe blocking
Ignoring the system's own trackpad swipes to another desktop, a full-screen app, Mission Control or App Exposé on every frame of a thumb touch with two or more contacts down, and for the whole of a swipe, a window swipe or a swap series, with no time limit. macOS counts every contact, the thumb included, so a thumb plus two sliding fingers reads as its three-finger swipe, and a thumb that has drifted out of the corner, or lifted and landed again as a plain finger, is a contact it still counts; that is why the blocking lasts the thumb touch rather than the thumb's anchoring. Outside a thumb touch nothing is blocked, so three fingers that land and swipe with no thumb in the corner reach the system as usual. A system swipe is blocked or passed whole, decided on the event that begins it. If the system sends an early warning of a swipe as the fingers land, before anything moves, it is judged on its own: a warning that passed commits nothing, so a swipe whose warning passed while the thumb was still alone is still blocked from its beginning once the fingers are down, and a warning that was blocked blocks the whole swipe. A swipe first seen under way is never cut short. Like click blocking, it needs the Accessibility permission; without it, nothing is blocked.

## Accessibility hint
The card at the top of the settings window, below the update card when there is one and above the gesture rows, shown while Trackpad App lacks the Accessibility permission, whatever the trackpad settings: a rounded group with a light border, the message "Allow Accessibility access to make trackpad gestures work reliably." at most 216 pt wide, and under it a filled *Open Settings…* button in the system's accent colour (blue unless the user chose another, as the switches are) that opens the Accessibility page of System Settings, with no prompt first. A gear 91 pt across sits in the card's top-right corner, partly outside it and cut by its edges, and turns counter-clockwise around its own centre, one full turn every 30 seconds, smoothly across turns, for as long as the card shows; with the system's Reduce motion setting on it stands still in the design's pose, and it follows that setting live. The gear takes no clicks. The card goes the moment the permission is granted.

## Screen recording hint
The message in the settings window's *Switch windows* row, directly under its switch and lined up with the row's title, shown while Trackpad App lacks the Screen Recording permission and the window swipe setting is on: a yellow warning triangle, then "Allow Screen Recording access to show previews in the window switcher.", then under the message an *Open Settings…* button in the ordinary grey style. The button asks macOS for the permission the first time it is ever pressed, which is remembered across relaunches, and opens the Screen Recording page of System Settings on any later press while the permission is still missing. The hint disappears, and the row returns to its usual height, once the permission is granted or the setting is turned off. A window swipe never asks for the permission.
