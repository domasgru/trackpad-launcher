## Goal

A gesture, swipe, window swipe or swap leaves the settings window open; the app it brings to front comes over the window. With the settings window in front (Trackpad Launcher active), the switcher's row and the swap start from the app that was in front before it, and Trackpad Launcher never counts as a running or frontmost app.

## Requirements

- **R15.** A gesture, a swipe, a window swipe or a swap that fires while the settings window is open MUST leave the window open. The app it brings to front comes over the window. Its feedback and launch animation are unchanged. Trackpad Launcher MUST never count as a running app or as the frontmost app for the switcher or the swap. With the settings window in front, the switcher's row and the swap MUST work from the app that was in front before it, as the glossary's *Frontmost app* says.
  - Scenario: the settings window is open and the user just assigned Notes to the 2-finger gesture; they make the 2-finger gesture → Notes comes to the front over the settings window, with the gesture haptic and the launch animation, and the settings window and the Dock icon stay.
  - Scenario: Safari was in front, and the user opened the settings window over it; the user swipes to open the switcher → the switcher's row does not hold Trackpad Launcher, and it is the row the user would get with Safari in front.
- **R16** and **R17** were delivered in S1 (the *Other…* sheet, and System Settings buttons that only open the pane); this slice only checks they still hold.

## Design

1. **Delete the four effect closes** in `Launcher` (`LauncherKit/Sources/LauncherCore/Launcher.swift`): the `window = .closed` writes in `fire`, `swipe`, `windowSwipe` and `swap`. No effect closes the window any more. Update the `Launcher` header doc ("`fire` is the only path that pulses, launches, plays … or closes the window from a gesture") so it no longer claims a gesture closes the window.

2. **The frontmost app while Trackpad Launcher is active** stays below the port, where self-exclusion lives. While this process is the active app, `RunningAppsReader` reports as frontmost the first ⌘-Tab app. That order already drops this process by pid, so it holds the app that was in front before it, and Spotlight, which is not a ⌘-Tab app, never counts. One pure function, no new state:

   ```swift
   // RunningAppsReader.swift (LauncherPlatform): read() = RunningApps(frontmost: Self.frontmost(...), apps: apps),
   // with `apps` read first (the order, or the fallback list) and passed in.
   /// Never this process. While it is active (its settings window in front), the app that was in front before it: the
   /// first ⌘-Tab app, an order this process never enters (LaunchServices drops its pid; the tracker never notes it). Pure.
   static func frontmost(activePID: pid_t?, activeEntry: AppEntry?, ownPID: pid_t, apps: [AppEntry]) -> AppEntry? {
       guard let activePID else { return nil }
       return activePID == ownPID ? apps.first : activeEntry
   }
   ```
   `activePID`/`activeEntry` come from `NSWorkspace.shared.frontmostApplication` (its pid, and `RunningApp.entry(for:)`). `FrontmostAppWindows` is unchanged: while Trackpad Launcher is active a slide up or down is no window swipe, because raising windows needs their app frontmost. The swap, switcher and window-swipe paths in `Launcher` change only by losing their window closes.

3. **The own-pid filter in the switcher presenter's Dock-app read**: `SwitcherPresenter.dockLocation(_:)` (LauncherUI) also returns nil for this process (`app.processIdentifier == ProcessInfo.processInfo.processIdentifier`), now that the app is `.regular` while its window is open, so its icon is never drawn into the switcher's cache as a running Dock app.

4. **Stale "never active" comments** corrected, and the no-frontmost tests reworded as "no active app":
   - `Apps.swift` `RunningApps.frontmost` doc ("…or it is Trackpad Launcher itself, which never activates except around the Other… chooser") → never Trackpad Launcher; while it is active, the app that was in front before it (the most recently used ⌘-Tab app).
   - `RunningAppsReader.swift` (same claim), `WindowSwitcher.swift` `FrontmostWindows.noApp` ("or it is Trackpad Launcher itself" — still true: the windows reader reports no app while Trackpad Launcher is active; keep it accurate), `Switcher.swift:4-5` ("as while Trackpad Launcher itself is active" → no active app), `LaunchOverlay.swift` ("The app is never active, so it never deactivates either." → the overlay must not hide when the app deactivates, which it now does), `AnimationTuner.swift` ("a menu bar app that is otherwise never active"), `InMemoryAdapters.swift` and `World.swift` ("nil models no active app, or Trackpad Launcher itself" → no active app).
   - Tests in `SwitcherOnScreenTests.swift` under `// MARK: Trackpad Launcher in front` (the `withNoReadableFrontmostApp…` tests), `SwitcherAssignedAppsTests.swift` (~134-161), `SwapTests.swift` (`aMenuBarAppInFrontIsSkippedAndNoFrontmostAppSwapsToTheFirstRunningApp`), `WindowSwipeNeedsTwoWindowsTests.swift` (`.noFrontmostApp`), the `frontmost: nil` row in `WindowTitleRuleTests.swift`: keep their assertions, reword names/comments/MARKs to "no active app" rather than "Trackpad Launcher in front".

## Rules that apply

- Domain model, *Frontmost app*: "The active app at the moment a swipe or a window swipe begins or a thumb tap lifts; never Trackpad Launcher. While Trackpad Launcher itself is active, as while its settings window is in front, the frontmost app is the app that was in front before it, read as the most recently used running app, so the switcher's row and the swap are the ones the user would get with that app in front; a slide up or down is then no window swipe. … When there is none, the row is the running apps without a gesture alone, the selection starts on the most recently used one, …; a swap brings the most recently used one to the front; and a slide up or down is no window swipe."
- Domain model, *Running apps*: "… never a menu bar app, and never Trackpad Launcher."
- Domain model, *Swap*: "… the gesture haptic and bring to front, never the launch animation; an open settings window stays open."
- Domain model, *Launch animation setting*: "the feedback and bring to front are unchanged" (no window close).
- Domain model, *Settings window*: "Clicking another app, a gesture, a swipe, a window swipe, a swap, *Other…* … and the System Settings buttons all leave it open; an app a gesture brings to front comes over it."
- `docs/architecture.md` § Shape: "Framework and wire types never cross a port: … `NSRunningApplication` … stay inside adapters and views." The frontmost rule stays inside `RunningAppsReader`; the model sees only `RunningApps`.
- § Shape: "Policy lives in pure functions and value types" — the frontmost rule is a pure static function, no new state, no new observer.
- § Concurrency: no timers, no polling (source-scanned).
