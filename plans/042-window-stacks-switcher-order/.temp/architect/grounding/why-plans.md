### Direct Evidence Found

#### Q1. Synchronous main-actor read, 0.2 s messaging timeout, "no further raises after a timeout", one-file confinement, async/off-main alternatives, only the frontmost app

1. **Tradeoff stated: synchronous AX on main, bounded by the timeout, in exchange for a synchronous model and tests.**
   - "We accept AX calls synchronously on the main actor (about a millisecond to read, about 2 ms per raise), bounded by a 0.2 s process-wide messaging timeout with no further raises to an app after its first timeout, in exchange for a synchronous model and model tests with no held reads. An app that hangs mid-swipe can stall the main actor for up to 0.2 s at the raise that meets it and again at the lift's read; one that hangs before the begin costs 0.2 s once, and the slide is then no window swipe."
   - `plans/012-window-switcher-gesture/plan.md` Tradeoffs accepted, :1431–1435. Implementation decision. Direct.

2. **Async / background-queue alternative considered and rejected (final plan).**
   - "**Raises on a serial background queue, or an async window read.** The main actor would never wait on another app, but the model would gain a loading state and a lift that can arrive before the read lands. For a read of about a millisecond, bounded timeouts instead."
   - 012 plan.md Alternatives considered, :1506–1508. Direct.
   - Candidate-level versions of the same rejection (012 `.temp/architect/`):
     - candidate-1.md :831–833: "**Raises on a serial background queue.** The main actor would never wait on another app. But the lift's haptic needs the outcome, so the model would have to wait or decide late, and it adds ordering and cancellation states. Bounded timeouts were chosen instead."
     - candidate-3.md :932: "**Async window reads behind a holdable port** (the `AppScanner` style). It hides IPC latency, but exposes a loading state to the model and the shell, and a lift that can arrive before the read lands. Rejected: for a 1 to 2 ms read it moves complexity onto callers instead of hiding it. The timeout bounds the bad case."
     - candidate-3.md :180: "The read is synchronous on the main actor, bounded by a process-wide 100 ms AX messaging timeout set once (F15), with no async port. It costs 1 to 2 ms for an app that answers, so a two-phase begin would hide nothing."
   - Relevance: the new design's asynchronous, multi-app, never-blocking read is the alternative these three passages rejected; the stated reasons are (a) a loading state in model and shell, (b) a lift that can arrive before the read lands, (c) the lift's haptic needs the outcome, (d) the read is only ~1 ms so async hides nothing.

3. **Frame-thread read rejected (change 1).**
   - "**Change 1: read the windows on the frame thread at the start frame.** … But the frame thread would make AX calls into another app, waiting up to the 0.2 s timeout with every trackpad's recognition stalled; `FrontmostAppWindows` and its raise handles would be shared across threads; the touch adapter would depend on the window reader and the read would ride a touch event to the model. Lost on locality and on the frame thread's promise never to wait."
   - 012 plan.md :1509–1513. Also dev log Plan (change 1) :65: "Rejected: a frame-thread window read, a pushed window count, a read when the pair lands, starting blocked then releasing (the scroll filter never relaxes)."

4. **Why "no further raises to an app that timed out" (and its rejected variant).**
   - Port contract: "About 2 ms per raise; once the app has timed out, no further calls go to it for that read." (012 plan.md `SystemActions.raiseWindows` doc, :986–991). Adapter sketch: "kAXErrorCannotComplete → mark the listing unanswering and stop" (:1111–1115); read step 3: "Stop at the first cannot-complete; the listing is then marked unanswering." (:1103–1104).
   - Synthesis "Rejected … From candidate-3: … a timeout that stops only the current call" (:1418–1423). No sentence gives the reason beyond the stall bound in item 1.
   - Manual check M18 states the intended effect: "start the window swipe before the stop and keep sliding across rows past it: at most one short hitch, then no further hitches" (:1719).
   - Dev log Implement :47: "S3 committed (ffa025d). A hung app mid-swipe can cost a second 0.2 s timeout at the lift's read → kept: the plan's Tradeoffs accept a stall 'at the raise that meets it and again at the lift's read'."
   - S3 slice doc text for architecture.md: "each bounded by a short messaging timeout, after which that app gets no further raises until it is read again." (`.temp/slices/S3.md` :140).

5. **Timeout set process-wide on the system-wide element (a review finding).**
   - Dev log Plan :24: "Cross-judge: the AX messaging timeout was set on the app element only → set once on the system-wide element, process-wide per `AXUIElement.h`."
   - plan.md :1095–1098: "Sets the messaging timeout once on the system-wide element (process-wide; set on any other element it covers that element only, `AXUIElement.h`), resolves `_AXUIElementGetWindow` with dlsym, and pays the window list's first-call cost (about 50 ms) off the main actor now, not at the first window swipe."
   - Grounding F15 (`.temp/architect/grounding/index.md` :78–81): "each AX call is synchronous IPC bounded by a per-element timeout; `kAXErrorCannotComplete` (-25204) when the app does not answer in time … The begin path runs on the main actor, so the adapter should set a short timeout on the app element."

6. **Why 0.2 s specifically: not recorded.** Candidates 2 and 3 used 0.1 s (candidate-2 :450 `AXUIElementSetMessagingTimeout(element, 0.1)`, :673 open question "Is a 100 ms AX messaging timeout the right bound"; candidate-3 :617 `messagingTimeout: Float = 0.1`); candidate-1 used 0.2 (:589). The final plan keeps 0.2 and asks: open question 5, "Is 0.2 s the right AX messaging timeout? Apps whose accessibility tree wakes on the first query (Chromium, O5) may read as having no windows on the first slide down, which is then no window swipe and scrolls after the blocking window." (plan.md :1546–1548).

7. **The timeout has no automated test, by decision.**
   - Dev log Plan :35: "test-planner: the AX messaging timeout has no test handle → rejected: faking the AX calls would test our model of the API, not the API; `FakeWindows.answers` is the high seam's handle and M18 checks the real timeout; open question 13 for the human."
   - Open question 13 (:1566–1568).

8. **Confinement to one file: origin and scan rule.**
   - Source policy: "Confined, each to one file: … `AXUIElement` (which covers `_AXUIElementGetWindow`) and `CGWindowList` to `FrontmostAppWindows.swift` … The scan matches comments, so no other file may spell a confined name, even in a doc comment." (012 plan.md :1317–1325). T18: "`AXUIElement` and `CGWindowList` appear only in `FrontmostAppWindows.swift`, comments included." Source of truth: "`docs/architecture.md` Privacy: the Accessibility element API with the window list confined to one file." (:1640).
   - The confinement mechanism itself is plan 002's (grounding why.md :44: "The `Confined` table is plan 002's mechanism"; :173 Preserve 8: "Every new sensitive API gets a `Confined` row naming its one adapter file").
   - why.md Risk 6 (:210) flagged before 012 that "No `AXUIElement*`, `CGWindowList*` … token is banned or confined … a second file using them would pass the scan while the architecture claims otherwise."
   - Design: "the real work lives in one small platform type, `FrontmostAppWindows`, which `WorkspaceActions` creates once and delegates to, as it does `RunningAppsReader`. It holds no window, so its tests construct it alone" (:656–660). "The only file that may name `AXUIElement` (and so `_AXUIElementGetWindow`) or `CGWindowList`." (:1092).
   - **See Contradictions: plan 017 widened this confinement to a second file.**

9. **Why only the frontmost app.**
   - Non-goal: "**Windows of other apps.** The window swipe stays within the frontmost app; the swipe reaches other apps." (012 plan.md :371).
   - Non-goal: "**Hidden apps.** The window swipe works on the frontmost app, which is never hidden." (:377).
   - Non-goal: "**Windows on other Spaces and full-screen windows other than the front window.** Reaching them makes macOS switch Spaces, and macOS does not reliably reveal them. Deferred." (:370).
   - Plan 021 grounding fact F29, used in two decisions: "Bring to front is `NSWorkspace.openApplication(at:configuration:)` with `activates = true` everywhere; window raising is `kAXRaiseAction` only and relies on the app already being frontmost." (`plans/021-background-agent-lifecycle/.temp/architect/grounding/index.md` :79). plan.md decision 8 (:497): "`FrontmostAppWindows` is unchanged: while Trackpad Launcher is active a slide up or down is no window swipe, because raising windows needs their app frontmost (F29)." Rejected alternative (:1049): "`FrontmostApp` activation memory for R15: an extra observer and state, Spotlight could become 'the app before', and it claimed a window swipe that `kAXRaiseAction` cannot do while another app is active (F29)."
   - Original task brief scoped design item 3 to "the frontmost app's windows with title, minimised state and order" (012 `.temp/architect/task.md`).
   - Grounding facts relevant to reading other apps' windows: F10 "the window left on the previous Space **disappeared from `kAXWindowsAttribute`** … `AXRaise` on that other-Space window … **switched Spaces**" (index.md :58–62); F11 CGWindowList "52 ms on the first call in a process, 1.26 ms warm, 0.40 ms with a pid filter" (:63–68); O5 "apps whose accessibility tree is off until an assistive client connects (Chromium enables it on first AX query; Java apps need the access bridge): what `kAXWindowsAttribute` returns for them was not probed" (:289–291).

#### Q2. Window swipe only with 2+ windows; the answer hop (WindowSwipeConfirmation)

10. **The human's change, recorded as such; no reason recorded with it.**
    - Dev log "Specify (change 1)" :56: "Human: no window swipe and no switcher when the frontmost app has fewer than two windows, no frontmost app, or no Accessibility → Solution, R1, R3, R13, R14 rewritten; the slide behaves as with the setting off."
    - Solution (012 plan.md :11): "The window swipe exists only when there is something to switch to: the frontmost app has at least two windows. Otherwise, a slide up or down is no window swipe. Nothing appears, and the slide behaves exactly as if the window swipe switch were off. The same holds without the Accessibility permission, since windows cannot be read without it."
    - R13 (:255): "…The slide MUST then behave exactly as it does with the window swipe setting off (R16): it scrolls once the blocking window has passed, and it never becomes a swipe, since its first movement was up or down. The count MUST be fixed when the direction is decided…"
    - Non-goal (:380): "**An app whose only window is minimised.** One window is nothing to switch between; the Dock restores it."
    - R1 (:26): "Deciding this MUST add no delay the user can notice: the switcher MUST appear within 50 ms of the movement that starts the window swipe. The window count MUST be the number of rows the switcher shows, so a switcher never appears with fewer than two rows."

11. **The human's ORIGINAL brief asked for the opposite (a switcher even with one window).**
    - 012 `.temp/architect/task.md` :58–62, verbatim human instruction: "If app does not have multiple windows, the windows switcher still should be shown so you are sure that the feature is working, but it should just not switch apps and indicate only once screen."
    - S1–S4 built that ("a single 'No open windows' or 'Allow Accessibility to switch windows' row", Slices S2, plan.md :1747); change 1 (S6) removed it ("The 'No open windows' and 'Allow Accessibility' message rows go away entirely", `.temp/slices/S6.md` :16).
    - Relevance: the new design's "card with 0 or 1 window" returns toward the original brief and reverses change 1.

12. **Why the answer hops back to the frame thread.**
    - Design Problem (:395–399): "Change 1 overturns the original 'the recognizer never learns whether the app has windows': a slide up or down is a window swipe only when the frontmost app has two or more windows (R13) and Accessibility is granted (R14), and otherwise must be exactly the slide the window swipe setting off makes. Only the main actor can read windows, so the recognizer learns the verdict as the model's answer to the start, before its next frame."
    - Load-bearing decision (:605–625): "Whether a slide up or down is a window swipe depends on the frontmost app's windows, which only the main actor reads, while the slide's blocking is decided frame by frame on the frame thread. So `beginOrSpoil` still begins a `.swiping` slide for `.windowSwipe` … but the `Swipe` is born unconfirmed … it blocks only by the thumb rules, exactly what the spoiled slide of the setting off would block on that frame … The answer names its start by the frame time it began on, so an answer to an earlier start, one after its slide ended and a second answer change nothing … No timer, no poll."
    - Dev log :65 (Decision point): "the recognizer decides on the frame thread, only the main actor reads windows → a window swipe's start became a question the model answers before the next frame, the unconfirmed slide blocking by the thumb rules so a declined slide is exactly the setting-off slide."
    - Why it is a class in `LauncherCore` (WindowSwipeConfirmation): dev log :67 "plan-reviewer W1: the main-actor reply bookkeeping written twice (real and in-memory adapters), checked only by review → one `WindowSwipeConfirmation` in `LauncherCore` both adapters use, T73 for its edges; M21 shrinks to wiring." Dev log :87: "Declined: moving `WindowSwipeConfirmation` out of `LauncherCore`, a `WindowSwipeAnswer` parameter, a non-optional `deliver` result (all plan decisions)".
    - Tradeoffs (change 1): "We accept one main-to-frame answer per window swipe start, through a slot only the main actor writes and a reply only the adapter calls, in exchange for every window read staying on the main actor and the frame thread never waiting on another app." (:1471–1473). "We accept one window read on the main actor for every slide up or down, declined or not (about a millisecond), in exchange for the confirmation and the rows coming from one read, so the count that decides is the count the user sees (R1)." (:1474–1476). "…a window swipe's blocking starting on the frame after its start, about 10 ms later, in exchange for a declined slide being exactly the setting-off slide … because a scroll the filter has once stilled stays stilled until the fingers lift." (:1465–1470).

13. **Other change-1 alternatives rejected (each collides with parts of the new design).**
    - "**Change 1: a window count the frame thread reads, kept current by pushes.** Accessibility observers on the frontmost app … No round trip, but no push exists for a window entering full screen or moving Space, Chromium and Electron trees are unreliable observers, a read would run on every window change even when no slide happens, and a pushed count could disagree with the begin read's rows, which R1 forbids. Rejected." (:1514–1518)
    - "**Change 1: read when the pair lands, decide at the start.** … a pair may rest for seconds (R1 has no time limit), so the count would not be the one at the decision (R13), and every 2-finger tap under the thumb would pay a read. Rejected." (:1519–1521)
    - "**Change 1: start blocked, and release on a decline.** … the scroll filter never relaxes a scroll it has stilled, so a declined slide after the blocking window would stop scrolling (R13's 'One window scrolls after the blocking window') … Rejected." (:1522–1524)
    - "**Change 1: the answer as `onEvent`'s return value, or as a reply handle inside the event.** … Lost narrowly." (:1525–1528)

#### Q4. No window state across window swipes; list fixed at begin; only latest read's ids raisable

16. **"Deliberately not done … No window state in the model between window swipes."** (012 plan.md :690–693, full: "No main-to-frame channel beyond the one answer per window swipe start. No window read on the frame thread. No window state in the model between window swipes. No restore while sliding. No raise of an unlisted window. No prompt from a gesture. No live previews, no stream. No attribute writes…").

17. **Grounding constraint it came from** (012 `.temp/architect/grounding/why.md`):
    - Preserve 5 (:170): "**List fixed at begin; system state pulled at begin and again at the lift; nothing stored; a lift that changes nothing is silent** (006 R4; 008 R5, R7, decisions 1 and 4; 009 Solution). A window closed mid-swipe is the analogue of an app that quit: silent, never re-created."
    - Avoid 9 (:198): "Re-ordering the list mid-swipe as windows are raised (006 R4; 008 R5), or storing window state in the model between swipes (008 decision 1)."
    - Risk 4 (:208): "Mid-swipe raises race the system's state … raising on each pass changes what the lift's second read compares against … The begin/end double-read pattern was designed for one effect at the lift."
    - Competing hypotheses for "row fixed at begin" (:124–127): "Hypothesis A: stability under the fingers … Evidence for: none stated anywhere; only the requirement sentences (006 R4, 008 R5). [Speculative]" and "Hypothesis B: a consequence of 'the model keeps none of it' … [Speculative]".

18. **The precedent it cites** (`plans/008-recent-apps-switcher/plan.md`):
    - Decision 1 (:262): "The read is a pull at the moment it is needed (a swipe's begin and end), never stored: the order changes with every activation and LaunchServices is its one source of truth."
    - Further Notes (:346): "**Why the model reads the order and the presenter reads the apps.** The order is needed only at a swipe's begin and end and changes on every activation: a pull from the source of truth, no state. Icon readiness is a shell concern tied to AppKit's notifications and types; pushing the running apps through the model only to feed the presenter would add state the model never decides on."
    - R5 (:107): "The row MUST be decided when the swipe begins and MUST NOT change during the swipe…"

19. **Only the latest read's ids are raisable — port contract and reason.**
    - `frontmostWindows()` doc: "The windows it lists are the only ones a later `raiseWindows` may name, until the next read." `raiseWindows` doc: "…an id the latest read did not list is skipped, so nothing on another Space is ever raised." (012 plan.md :981–991).
    - Grounding F24 (index.md :107): "raising a window on another Space switches Spaces. Never raise an unlisted window."; F14 (:76–77) closed window → `-25202`, "R10/R11 'a window that has closed changes nothing' falls out of ignoring that error."
    - Tradeoff (:1446–1449): "…The ordering rule '`raiseWindows` names windows of the latest read' is stated on both methods."
    - Candidate-1 tradeoff (candidate-1.md, Tradeoffs): "The adapter keeps the latest listing's AX elements until the next read, so there is no lifecycle method on the port." Candidate-3 (:184): "The adapter keeps the AX elements of its latest read keyed by `WindowID` … It is idempotent state with one writer (main), replaced by every read."

20. **How the "toggle" works without model state:** the order comes back from the system. "`FakeWindows` … `frontmostWindows()` answers from the existing `frontmost` field and the stack, so a second window swipe sees the first one's order (R11's toggle scenario). All policy stays in the model's pure functions, so the fake carries none." (012 plan.md :1309–1313).

#### Q5. Icons drawn before any swipe; running apps read from LaunchServices at begin; layout types in LauncherCore; selected-icon grow

21. **Icons pre-drawn because the first draw is too slow for a gesture.**

Decision 9 (:286): "Icons are drawn before any swipe, from the running apps, only while the swipe is on … redraws off the main actor for each app the workspace reports launched (a push, never a poll) … The presenter reads `NSWorkspace` itself: AppKit types stay in the shell, and the model keeps no running-apps state."
    - 006 (`plans/006-five-finger-tap-and-corner-swipe/plan.md`) :491 "the list's 80 pt icons take up to 220 ms to draw cold (F4) and must be ready before the swipe"; R10 :241 "It MUST appear as the swipe begins with no perceptible delay"; decision 9 :647.
    - 008 Further Notes (:348): "**Cost on the swipe path after this plan:** one LaunchServices read (1.4 ms warm, under 4 ms cold, for 14 apps) and cache hits for icons; a second read at the lift. The first swipe after launch waits for nothing: the icon pass ran at start."
    - 012 shell analogue: "The panel is created now, so a window swipe never pays the first window's cost. Its own `AppIcons` takes the frontmost app's icon from the running app (about 0.1 ms)" (plan.md :1236–1243).

22. **LaunchServices read at begin and again at lift.** 008 decision 1 (:262, quoted in 18) and decision 4 (:276): "On `ended` with a switcher up: index 0 is silent … otherwise a second `runningApps()` read decides whether the selected entry's location is still among the running apps … if not, nothing happens and nothing plays, so an app that quit mid-swipe is never relaunched." Probe numbers (:260): the private LaunchServices order call "costs 1.4 ms warm and under 4 ms cold" and "`AppCatalog.entry(at:)` costs about 5 ms per app … would stall the swipe's first frame by 70 ms with 14 apps."

23. **Layout types in LauncherCore.**
    - 008 decision 10 (:288): "`SwitcherRowLayout`, a value in the core beside `Switcher` … one function, `centreX(at:)` … which the panel uses for both the icon layers … and the highlight …, so the two cannot drift apart … The core's travel (12 mm, or 100 cursor points, per icon) never sees the layout, so the finger travel per icon is unchanged by construction." 008 dev log Plan: "T16 could not fail (the core never sees the layout) and the real risk, icons and highlight drifting apart, was untested → `SwitcherRowLayout.centreX(at:)` positions both; T15 pins it".
