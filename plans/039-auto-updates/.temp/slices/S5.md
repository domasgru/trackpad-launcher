## Requirements

This slice proves, on notarised builds, R1, R2, R3, R4, R5, R6, R7, R9, R10, R11, R12, R13, R14, R15, R18, R19, R20, R21, R22, R23. Their texts, short:

- R1: a signed copy in /Applications that can write checks once at a login start; a check failing for lack of network runs again each time a connection returns, until one completes.
- R2: a login start downloads and installs as soon as the download finishes, waiting for nothing; a failed login download does not retry until the next login start or the card.
- R3: after a login install (window closed), the new version runs with no window, no Dock icon, no dialog, no prompt, makes no check at that start, and gestures work again within 10 s of the old version stopping.
- R4: during a login update, opening the window makes no check and shows no card; the update carries on; a window open when the old version stops means the new version opens with its window.
- R5: each closed-to-open of the window checks once (unless an update is under way); re-fronting does not; a check running when the window closes is dropped; every opening starts with no card.
- R6: a window check downloads nothing until *Update now*.
- R7: no update request outside R1, R5 and a download from R2 or *Update now* (which reads the list once more before its download); no schedule or timer.
- R9: every request, download included, carries no query string, no cookie and no header naming the user, the Mac, the app's version or macOS version; headers are the same on every Mac and version.
- R10: only a published full release, higher than the running one, whose minimum macOS this Mac meets, counts; the highest wins; never older.
- R11/R12: the card as the window's first group; its arrow drifts about 4 pt about every 3 s, the tray still.
- R13: *Update now* greys out as *Updating…*, downloads, installs at once, opens the new version with its window, which makes no check at that start; one process.
- R14: a failed card update returns *Update available*; an install failing after the old version stopped brings a working copy back within 10 s with its window.
- R15: only a download signed with the update key and with the same Developer ID and bundle identifier installs; at login nothing shows.
- R18: /Applications always holds a whole version; a failed install leaves a working copy within 10 s, nothing shown, no retry until the next login start or the card.
- R19: a copy that cannot write makes no check, download or prompt at login; its window checks and shows the card; *Update now* asks for an administrator after the download; cancelling returns the card.
- R20: Quit stops the app at once in any update state; nothing restarts it.
- R21: logout, restart, shutdown end the app with no dialog and no delay.
- R22: no update code runs for a trackpad frame (the person's gesture keeps working).
- R23: no WebKit; the updater exists only during a check or update.

## Design

Decision 12: `update-e2e.sh` keeps its build, signing, notarisation, local server (`Scripts/update-e2e/server.py`, its control words `feed=ok|503|503once|404|reset|hold`, `payload=...`), sampler (`sampler.swift`), analyser (`analyze.py`), feed tools (`feed.py`), key generator, report and cleanup, and its rows are re-cut to the T28 to T37 and T41 rows below. Its builds carry `SUEnableAutomaticChecks: false` like the shipped `project.yml` (check `prepare_tree`'s awk patch of `project.yml` still matches the keys `project.yml` now declares: `SUEnableAutomaticChecks: false`, `SUEnableInstallerLauncherService: true`, no `SUAutomaticallyUpdate`), and start with `--at-login` where a login start is meant (the app reads `--at-login` as a login start; `--after-update` and `--with-window` are the hand-over's arguments). A by-hand start is the plain `open` (with the window), not `open -g -j`.

What changed in the app since revision 1 that the rows must reflect (the rows' helper assumptions must be updated to match):

- No schedule, no `SULastCheckTime` use: `set_last_check` and every row that waited on Sparkle's 24-hour schedule or on wake go. No idle minute and no contact: rows T63 and T64 go, and nothing asks the person to keep fingers off the pad.
- A login start (`--at-login`) of a copy that can write: one feed request, the `.aar` download, then at once a hand-over: the old process ends, the job opens the new copy with `--after-update` (and `--with-window` only if the window was open at that moment, or after *Update now*). The new copy makes no request at that start.
- A by-hand start, or each closed-to-open of the window: one feed request (a probe), no download. A found update shows the card. *Update now*: one more feed request, then the asset GET, then the hand-over with the window.
- The genuineness check now runs when the download finishes, before any installer exists: a refused update never starts `Autoupdate`, and the persistent download (`~/Library/Caches/<bundle id>/org.sparkle-project.Sparkle/PersistentDownloads/…`) is removed.
- A standard account: Sparkle's installer launcher XPC service shows the administrator prompt after the download, in its own process.
- Sparkle is vendored at `LauncherKit/Vendor/Sparkle/` (its tools in `bin/`); the keychain/netrc flags are gone (S1 already updated the script for both; keep it so).

The rows' report entries, `rows_table()`, `run_row`, `row_done`/`row_fail`/`row_skip`, `ask_person`/`tell_person` and `check`/`expect_count` keep their shapes. Row ids become T28 to T37 and T41, matching the plan. Where a row needs the person (their gesture, an eye check of the card, a password, a logout), it asks through `ask_person`/`tell_person` as today. T41 is by hand: the script prints its steps and records the person's answers.

Cleanup must leave no `.e2e` copy, launchd job, defaults domain, login item or standard-account leftover; check the existing `reset_world`/cleanup covers the new rows (e.g. a copy opened with its window, a standard-account run).

## Rules that apply

- `docs/architecture.md`, Distribution: the release's asset name `TrackpadLauncher-<version>-macOS-<minimum>.aar`, the one bundle in it `TrackpadLauncher.app`, and every release running `card-contract` on the archive.
- `docs/architecture.md`, Privacy: "a fixed address with no query string of ours, fixed headers that name neither the user, the Mac nor any version, cookies refused and nothing cached."
- `docs/architecture.md`, Concurrency: "the hand-over job's waits … first for the old process to end, with no limit, so that a late end still installs and still comes back, then for at most 6 s for the install."
- `docs/domain-model.md`, Login start: "For the hand tests, a release copy started with `--at-login` reads as a login start."
- The script is a test harness, not shipped code; it is not scanned by `SourcePolicyTests`.
