# Plan: The new version outlives the old one after an update

## Problem statement

After every in-app update, the new version disappears about 3 seconds after the old one ends, and nothing is left running: gestures are gone until the user opens the app by hand. It looks like a crash, but no crash report is written, because macOS itself kills the process. This is a different failure from the one `plans/035-post-update-crash` fixed; that fix was real and is still needed, and this one was hidden behind it.

**Root cause.** The app's Info.plist declares `NSSupportsSuddenTermination: true` (`project.yml`). The old version opens the new one with `NSWorkspace.openApplication`, so Launch Services records the new process as a child of the old. When a foreground-type app dies, loginwindow looks through its children for "non-visible terminatable apps". The new version, at that instant, is a UI element (`LSUIElement`) with no visible window yet, and it declares sudden termination, so loginwindow schedules it for termination in 3 seconds and then force quits it (`_LSForceQuitApplication`, SIGTERM). The new version opening its window in the meantime does not cancel that.

**Evidence.**

- Unified log of the 1.0.12 → 1.0.13 update on 2026-11-06. The old copy (pid 22948) exits with status 0 at 21:52:41.05, then loginwindow logs: `subprocess … "Trackpad Launcher" is a UI element without a visible window`, `checking children and related applications for non-visbile terminatable apps`, `terminateAppIf: app=… (23523) supports sudden termination, so terminating all subordinate processes in 3 seconds`. At 21:52:44.297: `supported sudden termination, so terminating all remaining subordinate processes now`, `_LSForceQuitApplication(… (23523)`, then `termination reported by launchd (2, 15, 15)`.
- Six of six update hand-overs in the last three days (the launchd job labels with a UUID suffix, which only a new instance gets) ended 3.2 to 3.3 s after the old copy exited. Timing this constant is a mechanism, not a race.
- No crash report exists from any version since 1.0.10. All reports in `~/Library/Logs/DiagnosticReports/Retired` are the stack `plans/035-post-update-crash` fixed.
- `repro.sh` runs the real Release app, under its own identifier, as the child of a stand-in old copy that does what `ApplicationsUpdater.openNewVersion` and `Lifecycle.replaced` do. It reads the new copy's state and loginwindow's verdict.
  - Today's Info.plist: **0 of 5 alive**, with the field's log sequence and no crash report.
  - `NSSupportsSuddenTermination` removed from the new copy, old copy using shipped 1.0.13's Info.plist: **5 of 5 alive**.
  - Removed from both: **5 of 5 alive**.
  - Removed from the new copy, old copy on shipped 1.0.13's Info.plist, watched for 75 s: alive. loginwindow logged the child as a UI element without a visible window, and ran "terminating all remaining subordinate processes" for the old copy, and left the child alone. The child's own declaration is what decides it.

**Why `plans/035-post-update-crash` missed it.** Its `repro.sh` opened the old copy with `open -g` and the old copy never showed a window, so it was never a foreground-type app. loginwindow ignores the death of such an app (`has died, is non-foreground and never tracked, so ignoring it`). The real old version always hands over from its settings window. This plan's first repro attempt fell into the same hole: 5 of 5 alive until the stand-in opened a window.

**Test coverage.** No existing test could catch this: `Lifecycle` and `Updater` tests use in-memory adapters, and nothing reads the shipped Info.plist or involves loginwindow.

## Requirements

### R1. The new version survives the end of the version that opened it
Trackpad Launcher MUST NOT declare sudden termination: `NSSupportsSuddenTermination` MUST NOT be in its Info.plist, so that loginwindow never counts a copy as a terminatable child of the copy that opened it. This MUST hold for the first update onto the fix, from a version that still declares it.

#### Scenario: Updating from a shipped version
- **GIVEN** an old copy with the shipped 1.0.13 Info.plist, in the foreground with its window open
- **WHEN** it opens the new version as a new instance and ends
- **THEN** the new version is still running well past 3 s, with its resident built and its window open
- **AND** `repro.sh <app> 5 "<1.0.13's Info.plist>"` reports 5 alive and 0 dead, and no crash report appears

#### Scenario: Every later update
- **GIVEN** an old copy with the fixed Info.plist
- **WHEN** the same hand-over runs
- **THEN** `repro.sh <app> 5` reports 5 alive and 0 dead

### R2. Quitting, logging out and shutting down behave as before
Without sudden termination the system asks the app to quit instead of killing it. `Lifecycle.shouldEnd` and `QuitSignals` already answer such a quit. Every way the process ends MUST keep its documented behaviour, and logout, restart and shutdown MUST NOT be held up by the app: `.system` requests end at once, as today. The planner MUST confirm this from the code and name any gap; it does not change `Lifecycle`'s behaviour unless a gap is found.

### R3. The declaration cannot come back unnoticed
A test MUST fail if `project.yml`, the source of the Info.plist, declares `NSSupportsSuddenTermination`, naming why. The repo's way of keeping a promise like this is `SourcePolicyTests`, which fails the build instead of relying on prose. It MUST also fail if any source enables sudden termination at run time (`ProcessInfo.enableSuddenTermination`), which has the key's effect without the key. *(The last sentence was added at planning, when the run-time route came up while confirming R2.)*

### R4. The hand-over's constraint is written down
`docs/architecture.md` MUST state the rule and its reason where it describes the update: a reader who considers adding sudden termination, or changing how the new version is opened, must find out why loginwindow matters.

## Non-goals

- **Changing how the old version opens the new one.** Starting the new version through a helper so it has no parent would also break the parent link, but it does nothing for the first update onto the fix, and the source policy bans child processes. The new copy's own declaration decides the outcome, and it is the one thing in this repo that fixes every path.
- **Catching SIGTERM, or a watchdog or relauncher.** They would hide the mechanism and add moving parts. The cause is known and removed.
- **`ApplicationsInstaller.openInstalledCopy`.** The move into /Applications opens the installed copy the same way and ends, so it had the same exposure. R1 covers it with no code of its own, because the rule is in the opened copy's Info.plist.
- **Automatic updates.** They come next, and this is their prerequisite. A silent update's new copy never opens a window, so it stays a UI element without one, and loginwindow says it schedules future checks for such a child "to see if we need to alert about it". That is an alert, not a termination, and it did nothing within the 75 s watched here; that feature's own plan must look at it.
- **A release.** Shipping the version is a separate, human step.

## Implementation Decisions

- **The declaration goes from `project.yml`, the one tracked source of the Info.plist; nothing else in production changes.** `TrackpadLauncher/Info.plist` and `TrackpadLauncher.xcodeproj` are git-ignored and written by `xcodegen generate` from `project.yml`'s `info.properties`; the generated plist holds exactly those properties plus the bundle's identity keys (executable, identifier, package type, dictionary version, development region), so once the key leaves the manifest no build carries it. The key is absent, not set to `false`: the bundle makes no statement about sudden termination, and absence is what the test checks. `project.yml` carries no comment about the absence either; the reason lives in the test's rule text and in the architecture doc, and the test scans for the key's name on any line, a comment's included, so one place holds the reason. `Lifecycle`, `QuitSignals`, `SystemRunningCopies`, the ports, the adapters and the shell are untouched.

- **R2, confirmed from the code and from loginwindow's own log: the quit route is complete; the one thing nobody has observed is named below, with the human check that settles it. `Lifecycle` keeps its behaviour.** What the key did, from the unified log of this Mac's restart on 2026-11-06 at 18:06: loginwindow's GUI-quit phase lists foreground apps only ("App is UI Element, do not add it"), so Trackpad Launcher with its window closed fell to the later `quitUIElementApps` phase, where `appIsKillable:` found it "IS killable" (a clean process: sudden termination enabled) and `tryToKillApp:` killed it with no quit event ("Trackpad Launcher killed, telling CAS"). Every app that was not killable got a quit Apple event with logout attributes (`addLogOutAttibutesToQuitAppleEvent`) and a termination timer, and was logged `App:<name> quit, tear down entries` when it ended. Without the key the process is not clean (its sudden-termination counter stays at one, per `NSProcessInfo.h`), so at logout it takes the quit-event route, for the first time in this app's history. That route is complete in the code:
  - The delegate answers `applicationShouldTerminate` with `Lifecycle.shouldEnd(QuitSignals.request(for: event))`: `.terminateNow` on yes, `.terminateCancel` on no, never `.terminateLater`. The answer is synchronous, so the app holds up nothing and loginwindow's termination timer never runs out on it.
  - `QuitSignals` reads a quit as the system's on any one of three independent signs: the event carries a `kAEQuitReason` (shut down, restart, log out, quit all), the sender pid is loginwindow's, or `willPowerOffNotification` was seen earlier in the process. Any one sign makes `.system`.
  - `Lifecycle.shouldEnd(.system)` is true in every stage: `.ending`, `.idle`, `.replacingOthers`, `.askingToMove` and `.moveFailed` unconditionally; `.moving` exactly for `.system`; `.resident` before it looks at the window or the install. So a system quit ends the process at once, mid-move and mid-install too, as the glossary promises, and the install's atomic swap already allows that (/Applications holds a whole version at every moment).
  - Every end the app makes itself (the *Quit Trackpad Launcher* button, the hand-over's `replaced`, the move's end, the move dialog's *Quit*) goes through one `end()`: stage `.ending`, then `endThisCopy()`, which is `NSApp.terminate(nil)`, which asks `shouldEnd` again and gets yes from `.ending`. None of them relied on sudden termination.
  - No source calls `ProcessInfo`'s `enableSuddenTermination` or `disableSuddenTermination`, and no source names the key; the manifest was the only place.
  - The existing suite already asserts the `.system` answer in every stage after launch over the in-memory adapters (the system-quit test in the lifecycle tests; the asking, moving and failed cases in the move tests; the installing case in the update install tests; the replacing case; `.idle` shares `.ending`'s branch and is not asserted on its own) and `QuitSignals`' three signs and four reasons (its own tests). It stays green with no edit.
  - **The gap, named.** No one in this repo has observed a real loginwindow quit event's attributes: plan 021 recorded the quit reason as "if present" and `willPowerOffNotification`'s order as unprobed, and every quit event seen since came from `osascript` or a peer's `terminate()`, the `.other` route. With the key, the kill made that unknown harmless; this fix removes the kill. If a logout's quit read as `.other`: a copy with its window closed still ends (`.resident` with the window closed answers yes unless an update installs), but a copy with its window open, mid-move or mid-install would answer `.terminateCancel` and cancel the logout, which R2 forbids. The sender-pid sign alone should make that impossible, since loginwindow itself sends the event and the Apple Event Manager stamps the sender, but "should" is not observed. The proof is one human logout with the throwaway build's window open, in Verified without a test and in S1; if it fails, `QuitSignals` is the place to change, and plan 021's probe app, which logs the reason and sender at `applicationShouldTerminate`, is the diagnostic tool.
  - **Residual, accepted.** In `.askingToMove` and `.moveFailed` the main thread is inside the move dialog's `runModal`. Apple events are delivered in the modal panel run-loop mode, which is how the Dock's Quit reaches an app with an alert up, and that is the same route the dialog already takes today for an ordinary quit; the exposure is a release copy outside /Applications with its dialog up at the moment of a logout, with the user present. Not checked by hand: the only way to show the dialog with a throwaway build is the hand-testing argument, and a slip on its *Move to Applications* would install that build over `/Applications/Trackpad Launcher.app`.
  - This route was already live before the fix: Foundation and AppKit disable sudden termination on their own at times (Foundation while `UserDefaults` holds unsaved changes, per `NSProcessInfo.h`), and a quit arriving then took this path. The fix makes the route the only one; it introduces none.

- **R3: the test lives in `SourcePolicyTests`, which reaches `project.yml` the way it already reaches the app target.** The suite computes the package root from its own file path and scans the app target's directory one level above the package; `project.yml` sits beside that directory, so it is reached by the same path arithmetic. Two entries keep the promise:
  1. A manifest policy, the new piece: a small list of Info.plist keys the bundle must never declare, with their rule, one entry today, `NSSupportsSuddenTermination`, whose rule states the mechanism (loginwindow force-quits, 3 s after a foreground app ends, every child of it that is a UI element without a visible window and declares sudden termination; the new version is that child for its first moments). A parameterised test scans `project.yml`'s lines for each key and reports hits as `project.yml:<line>: <key>`, the scanner's shape. A missing `project.yml` is a failure, not a skip: the app-target root is filtered on existence because it may not exist yet, but a manifest that moved or was renamed must not void the check silently. The scan has the file's customary self-checks: a planted key in a temporary manifest is reported with its line, and a temporary directory without a manifest fails the scan.
  2. The Swift-source ban gains `SuddenTermination`, with the same rule. `ProcessInfo.enableSuddenTermination()` enables sudden termination at run time even without the key (the process's counter starts at one without the key and the call decrements it), so it is the one other route to the state the key produced; `disableSuddenTermination()` is pointless without the key and a sign someone believes it is on. Both match the token.
  The suite's header comment, which says it scans every Swift source file, widens to name the manifest; no existing test function changes.

- **R4: the architecture doc states the rule where it describes the hand-over.** In the Shape section, right after "The new version arrives as an ordinary opening by hand": the bundle never declares the key and no code enables sudden termination, why (the child link and loginwindow's rule), that the opened copy's own declaration decides so the rule protects even the first update from a version that still declares it, that without the key a logout, restart or shutdown reaches the app as the quit event which `Lifecycle` answers at once, and that the source-scan test keeps both halves. The toolchain line also names `project.yml` as the one tracked source of the Info.plist, so R3's reader finds why the test reads it. Edited with this plan.

- **No domain-model change.** The glossary already promises that an update "opens the new version with its settings window open and stops the old one" and that "Logging out, restarting and shutting down end Trackpad Launcher without asking, mid-update too." The fix makes the first promise true and keeps the second by the quit event's route; no term moves.

- **`repro.sh` and `old-copy.swift` stay in the plan folder, unchanged, as the end-to-end check.** They are this plan's evidence tooling, as `plans/035-post-update-crash/repro.sh` is that plan's; nothing in the product depends on them.

## Testing Decisions

### Strategy

One seam, existing: `SourcePolicyTests` (`LauncherKit/Tests/LauncherCoreTests/SourcePolicyTests.swift`), the suite that turns a product promise into a failing build by reading the repository's own files from the package root. It gains a scan of the tracked source of the Info.plist, `project.yml`, and one more token in the Swift-source ban; the new tests resemble the file's parameterised `noSourceUses` and its planted-hit self-checks. The seam observes that the key is absent from the manifest and the API from the code. It misses the generated plist and the built bundle, which only restate the manifest, and loginwindow's behaviour, which only a real hand-over on the live login session shows; that is the end-to-end run under Verified without a test. Nothing is faked: the tests read the real files, and the self-checks write their own temporary ones. No new test for `Lifecycle`, `QuitSignals` or the shell: none changes, and the existing suite covers the `.system` quit in every stage after launch; the real logout signal is a human check.

## Further Notes

- **Why the key is absent rather than `false`.** `false` is harmless to loginwindow, but then the test would have to parse YAML to tell `true` from `false`, and the reader would have to know both forms; absence is one rule, one token scan.
- **The token scan trips on a comment.** So `project.yml` gets no comment naming the key. The rule text in the test and the architecture doc are the explanation; the test's failure message points there.
- **The end-to-end run's build.** Release configuration, `CODE_SIGN_IDENTITY="Apple Development"`, `PRODUCT_BUNDLE_IDENTIFIER=com.example.TrackpadLauncherHandover`, under `build/repro`: so the copy reads as a development build and runs where it is (no move dialog), and its identifier family is outside the installed app's, so a round never stops `/Applications/Trackpad Launcher.app` or a Debug copy. `build/repro` may already hold the diagnosis's build, which still declares the key: the slice builds again after the change, since the plist is baked at build time. Never build under `com.domasgru.TrackpadLauncherApp`; never modify or launch `/Applications/Trackpad Launcher.app`; only read its Info.plist, as the third argument.
- **What `repro.sh` reads.** `new version sudden termination:` and `old copy sudden termination:` print the key from each plist; for a plist without it PlistBuddy prints `Print: Entry, ":NSSupportsSuddenTermination", Does Not Exist`. A round is alive only when the new copy still runs, is `type="Foreground"` (its window opened, so its resident was built) and loginwindow never scheduled its termination. Each round waits 11 s, so five rounds take about a minute.
- **`.terminateLater` was considered and is not needed.** Nothing in `shouldEnd` is asynchronous; the model's answer is a switch over its stage.
- **Reading loginwindow's logout log.** `/usr/bin/log show --start "<time>" --end "<time>" --style compact --info --debug --predicate 'process == "loginwindow"'` over the logout minute. Milestones are `logout state: StartGUIAppsQuit` and then the UI-element phase (`allUIElementApps`, `quitUIElementApps`). In the GUI phase each foreground app is checked with `appIsKillable:` (`proc_get_dirty`; a clean process is killable); a non-killable app gets `firstNonKillableApp : <name>`, a quit Apple event with logout attributes and a termination timer, and `App:<name> quit, tear down entries` when it ends. In the UI-element phase a killable app gets `<name> (<pid>) is running and IS killable` and `<name> killed, telling CAS`, which is what the 1.0.13 copy got on 2026-11-06. The installed 1.0.13 copy still declares the key, so during the human check it will show those kill lines under its own pid; the throwaway copy's lines are told apart by its pid and by the GUI-phase vocabulary, which only a foreground copy gets.
