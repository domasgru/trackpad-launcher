# Architecture

The decisions that hold across the whole codebase. Feature-level decisions live in their plan under `plans/` and then in the code.

## Language, platform, toolchain
- Swift 6 language mode with complete strict concurrency, on the Xcode 26 toolchain (macOS 26 SDK). Deployment target macOS 26, universal binary (arm64 + x86_64).
- Build: a local SwiftPM package holds every library and test target; an xcodegen-generated Xcode project builds only the app bundle (Info.plist, resources, hardened runtime, signing, archiving). `swift test` runs the whole behavioural suite; `xcodebuild` is used only for the bundle. The Debug configuration builds the app under its own bundle identifier, the release's with `.debug` appended, so macOS keeps a Debug build's permission grants, settings and login item apart from the installed release's; the Release configuration, the notarized release and the perf build alike, keeps the release identifier.
- Tests use Swift Testing.

## Shape
- Three `@MainActor @Observable` models own every decision. `Lifecycle` owns the process: what it does when it starts, is opened again or is asked to quit, and moving it into /Applications; it builds `Launcher`, which owns gestures, settings and the settings window, only once the process runs gestures. `Updater` owns the update check, the update card and replacing this copy with a newer version. It exists only in a copy truly signed with a Developer ID that lies in /Applications. `Launcher` reports the window's openings and closings to it, and `Lifecycle` reads whether it installs and ends the process once the new version has started. The new version arrives as an ordinary opening by hand. At most one Trackpad Launcher runs gestures: an opening by hand stops every other running copy, Debug or release, and waits for their exit. Platform adapters sense and act behind small ports; the AppKit/SwiftUI shell renders the models' state and forwards user intents. Policy lives in pure functions and value types; the shell stays thin.
- Modules by ownership, not by execution order: `LauncherCore` (domain types, pure policy, ports, the models; imports Foundation and Observation only), `LauncherPlatform` (the real adapters over AppKit, Core Animation, IOKit, CoreGraphics (the window list), CoreServices (FSEvents, MDItem, Apple events), ServiceManagement, Security (the code signature, Authorization, two private translocation functions), URL Loading (the update check and its download, one file), AppleArchive (unpacking an update), DiskArbitration, the Accessibility element API, two private LaunchServices functions, one private Accessibility function and the private MultitouchSupport framework), `LauncherUI` (the settings window shell, the move dialog and SwiftUI views, plus the window previews it captures with ScreenCaptureKit, a rendered asset like the icons it draws), and the app target (composition root and the app delegate only).
- Framework and wire types never cross a port: `MTTouch`, `CFTypeRef`, `CGEvent`, `CFMachPort`, `UserDefaults` keys, `NSRunningApplication`, `NSImage` stay inside adapters and views. External data is parsed into domain types at the adapter.
- Every port has exactly two adapters: the real one in `LauncherPlatform` and an in-memory one in the tests. Concrete types that can be pointed at a temp directory or a throwaway `UserDefaults` suite are not put behind a port, unless they deliver asynchronously: those sit behind a port so the model's tests stay synchronous.

## Concurrency
- `LauncherCore` and `LauncherPlatform` are nonisolated by default; the model, the ports and the public surface of every real adapter are `@MainActor`. `LauncherUI` and the app target use main-actor default isolation.
- Multitouch frames are recognised on the framework's own thread; only recognised events hop to the main actor: a fired tap, a swap, and the begin, moves and end of a swipe or of a slide up or down that may be a window swipe, in frame order on the main queue and never from a session a later `run` replaced. One thing hops back: the model's answer to a window swipe's start, whether the slide is a window swipe, which only the main actor can tell because it reads the frontmost app's windows. The model gives it while it handles the start; the adapter replies once that call returns, and the frame thread hands the reply to that trackpad's recognizer before its next frame. The recognizer ignores an answer to any other start. Until the answer arrives the slide blocks clicks and scrolling only by the thumb rules, and Dock swipes as any thumb touch does, and the frame thread never waits for it. State shared with that thread lives behind a `Mutex` with one writer.
- Work that would delay a click (folder scans, Spotlight reads, icon drawing) runs off the main actor in explicitly concurrent functions, including inside `LauncherUI`; only its results hop back. The first scan and the first icon pass are the exception: they run, and are waited for, before gestures run and before the settings window can show, so no click can arrive before their results exist. The other exception is `AppIcons.iconDrawingIfMissing(for:)`, which draws a missing icon on the main actor, but only for the closed button showing a row app outside the list that was just picked through Other…. The launch overlay, and the launch bounce, which shares its icons, likewise draw an icon at gesture time only when the off-main pass has not drawn one yet (the app moved, or a sharper display was connected since). The switcher's icons are drawn before any swipe: every running Dock app's in the first icon pass at start, and each newly launched app's off the main actor on the workspace's launch notification, again on an appearance change; a swipe begins by reading the running apps from LaunchServices, a few milliseconds at most, and draws an icon on the main actor only for an app whose pass has not finished yet or that no pass covers (a frontmost menu bar app, from the running app's already-loaded icon). With the swipe setting off nothing is drawn or observed for the switcher. Every slide up or down reads the frontmost app's windows when it starts, and a window swipe raises them, through the Accessibility API on the main actor: synchronous calls into another app, about a millisecond each, each bounded by a short messaging timeout, after which that app gets no further raises until it is read again; the window list's first call in the process (about 50 ms) is paid off the main actor at launch. Window previews are captured off the main actor inside `LauncherUI`, and only the pictures hop back.
- No timers, no polling, no background loops: every input is a push (frames, cfprefs KVO, IOKit notifications, workspace notifications, the TCC Darwin notification, FSEvents for the app folders, user events, Apple events, the termination of other running copies, the move's install and eject completions, the release list's answer, an update's download progress and outcome, LaunchServices' answer to opening the new version, and, only while a launch bounce shows, its launch's progress (`openApplication`'s answer, KVO on the launched process, an Accessibility window observer) and pointer moves). This is what keeps idle CPU at zero. Time passes only on Core Animation's clock, and in one network request's own idle timeout (30 s without a byte, reset by every byte, the system's and not a timer of ours): a deadline, such as a launch bounce's cap or its wait after the app finished launching, is an animation on a layer of the effect it belongs to, its completion is the push, and it cannot outlive that effect. The one deadline outside both is the lift window: a frame thread stamps its end on the process's monotonic clock (read at receipt, never the frame's own time, which is the driver's clock) and the click tap's thread compares the stamp with that clock when an event arrives; nothing fires at the end, and the gate it held open closes on the next frame or event. The one repeating read is bounded the same way: a launch bounce whose app finished launching but whose next window it cannot be told of (no Accessibility, or the app's Accessibility server not answering yet) re-reads the window list every 50 ms on that bounce's deadlines, for at most the 2 s it then waits. The one extra thread is the click tap's run loop, which exists only while click blocking is armed and serves two event taps. One, over presses and their releases, is on for as long as it exists, and only a click wakes it. The other, over drags, pressure, scrolling and the system's gesture events, is turned on by that thread only while some trackpad is in a thumb touch (from a thumb in the anchor corner until its pad is empty) or in its lift window (the 0.5 s after fingers lift under the thumb, in which the system's tap actions are blocked), or while a press, a scroll gesture with its momentum or a Dock swipe is still withheld or altered, and turned off once none is, so ordinary pointing, dragging and scrolling never reach the app. A lift window's end is noticed on the next frame or the next event, never by a timer; a port left on while nothing touches the pad is sent nothing but a mouse's own events (a wheel, a drag), the first of which closes it. A trackpad's frame thread only wakes that thread when what it needs flips, a lift window ending included; no frame thread enables or disables a tap.
- Animation is Core Animation keyframes, which the render server plays. Whatever an animation leaves behind is cleaned up from its completion callback. No code of ours runs per display frame, and display links are banned along with timers. Code may run per input event while the effect it serves is on screen: the switchers' highlight on trackpad frames, the launch bounce's row on pointer moves.
- Developer tools live in `#if DEBUG` and never ship. Today that is the animation tuner in `LauncherPlatform`: a SwiftUI window over `LaunchTuning`, whose defaults are the shipped launch animation, launch bounce and pick animation. The settings window's pick animation reads the tuner through one Debug-only hook on the shell that the composition root wires; Release builds never set it.

## Privacy and permissions
- The app may ask for two permissions, both optional. Accessibility, asked for on first launch, is used only to block trackpad clicks, suppress trackpad scrolling, block the system's desktop and Mission Control swipes during gestures and block the system's tap actions (the click Tap to click makes, Look up, Smart zoom) under the anchored thumb and in the half second after fingers lift under the thumb, to list the frontmost app's windows when two fingers start sliding up or down under the thumb, to raise and restore them during a window swipe, and to notice the first window of an app a gesture is launching, while its launch bounce shows. Screen Recording, asked for only from the screen recording hint's button and never by a gesture, is used only to take one picture of each listed visible window when a window swipe begins; the pictures are kept in memory and dropped when the window swipe ends, never streamed, recorded, encoded or written to a file. The app never asks for Input Monitoring or any other permission and never reads keyboard events. It reads the pointer's position only while a launch bounce shows, to keep the icon above it, through NSEvent monitors that exist only then; it keeps nothing it reads. Without Accessibility everything works except click blocking, scroll suppression, Dock swipe blocking, tap-action blocking and switching windows, and gestures are off while Tap to click or Look up: Tap with three fingers is on for a connected trackpad, since a gesture would then click or look up; without Screen Recording the window switcher shows app icons instead of previews. The permission checks and their TCC push, screen capture, the event taps and the scroll-event API are each confined to one file by the source-scan test; the Accessibility element API with the window list to two (the frontmost app's window read and the launch bounce's launch watch); pointer-move events to the launch bounce's overlay (and the click tap, which only rewrites to one); the NSEvent monitors to the launch bounce's overlay.
- Trackpad touches come from `MultitouchSupport.framework` via `dlopen` (no link flags, no entitlements, no permission); it is Apple-signed, so the hardened runtime needs no library-validation exception. The ⌘-Tab order comes from two private LaunchServices functions resolved with `dlsym` from the LaunchServices already loaded (no link flag, no permission), confined to one adapter file by the source-scan test; when either is missing, the order falls back to the app in front at launch and the activations observed since, then launch order. A window's number comes from the private `_AXUIElementGetWindow`, resolved the same way and confined to the window adapter's file; when it is missing, windows are matched to the window list by their frames, and by their titles where the list names windows, and a window that matches none is not listed.
- No network code except the update check and the download the user starts with *Update now*, confined to one file: one ephemeral session per request, a fixed address with no query string, and fixed headers that name neither the user, the Mac nor any version. No logging of any kind (`print`, `NSLog`, `os_log`, `Logger`). No files written other than:
  - settings in `UserDefaults`;
  - the app's own bundle copied into /Applications when the user chooses *Move to Applications*;
  - a newer version, unpacked from memory into a staging folder beside /Applications and swapped in when the user chooses *Update now*.

  The unprivileged file operations of both are confined to one file. The administrator's, one atomic exchange, are confined to the one script that runs them, in one more file. A source-scan test in `LauncherCoreTests` fails the build on any banned API; add to its list rather than adding prose.

## Distribution
- Direct download only, as a disk image: the app and the image are each signed with Developer ID, notarized with `notarytool` and stapled; hardened runtime, no entitlements. One command builds it from the repository. Never sign with `--deep`; the main executable is signed last.
- Releases are GitHub releases on the public repository, tagged `v<version>`, each carrying the disk image and `TrackpadLauncher-<version>-macOS-<minimum>.aar`, an Apple Archive of the stapled app. That asset name, the one bundle in it, `TrackpadLauncher.app`, and the repository's path are a contract with every shipped version's update check. The disk image ships the bundle as `Trackpad Launcher.app`, because Finder, the Dock and Spotlight show a bundle's file name, never its `CFBundleDisplayName`; an update goes over the installed copy, whatever it is named, so copies installed as `TrackpadLauncher.app` keep that name. The release command, `Scripts/release.sh patch` (or `minor`, `major`; alone, it releases the version already set), releases main: it checks every credential and that main is clean and equal to origin's, runs the tests, raises the version and the build number, builds, notarises and checks, and only then pushes the version commit and publishes the release, after it has uploaded both assets; a failure before the push undoes the version commit. A release's version is above every earlier one's.
